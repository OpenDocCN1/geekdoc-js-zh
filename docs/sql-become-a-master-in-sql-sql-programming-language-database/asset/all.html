Constraints in SQL

A constraint is going to be the different rules that the SQL system is going to enforce when it is dealing with the columns on your table. Essentially, your table is going to be limited on the different types of data that are going to be allowed to go into the data base. Constraints are used so that you are able to make sure that the data base has accurate and reliable data in it. This is particularly helpful when your data base is being used by other people for a job.

Constraints are not limited to just the columns, but they can be placed on an entire table as well. The restrictions you place on a column are going to be only enforced on the column in question. But, when you are putting them on the table, they will be implemented on the entire table.

There are just a few limitations that you are going to use most often when you are working with constraints.

•Not NULL: the column is not going to have the ability to have any null values

•Index: the index constraints will not only create, but they will retrieve data that you have in your data base.

•Default constraint: if you do not set a default value, then one will be provided for that column.

•Check constraint: this limitation will make sure that any conditions placed on the column are met.

•Unique constraint: there are not going to be any values in your column that are going to be the same, each value is going to be unique.

•Foreign key: records in other data base tables are going to be identified with the key.

•Primary key: in the table that you are currently working in, each record is going to be identified.

When you are creating your table, you will have the opportunity to put your constraints into the code so that the constraints are done from the beginning. Or, if you forget to do that, you are going to be able to use the alter table statement so that the constraints can be created even though your table is already in place on your data base.

Dropping constraints

Even though your constraint has been put into place, you have the choice to drop the constraint by using the command that you use to alter your table, and from there you will select the drop constraint option.

Depending on the constraint, you are going to be provided with a shortcut that you can use to drop that constraint. It will also depend on which application you use. As mentioned at the beginning of this book, not every command is going to work in the programs that you will use as you create your SQL code.

Along with short cuts, some implementations make it to where you can disable constraints. This is not going to delete the constraint from the data base permanently, but rather, disable it so that it can be used in that data base later when you need it.

Integrity constraints

An integrity constraint will be used when you want to be sure that your data is accurate and consistent throughout the entire data base. The integrity of your data is going to be dealt with a different data base than what you are using thanks to the concept that has been put into SQL for referential integrity. Besides, how are you going to know if your data has integrity if you do not have something to check it against?

While multiple integrity constraints can be used when using referential integrity, you are primarily going to use the foreign key, primary key, and all the other constraints that we talked about in the section above.

Chapter 10

Transactions That You Can Use in SQL

Transactions are the units that you are going to use against what it was originally created for. Units like this are going to be used so that you can accomplish a function to make sense of the data base to you or the data base in question.

However, transactions will be the propagation for all of the changes that have been established on the data base. Therefore, at the point in time that you update records, you will have a transaction that has been completed on the data base. Ensure that you have total control of your data bases so that you have the ability to change what is placed in your table so that the data can still maintain its integrity and any errors that are thrown out by the data base can be handled in the proper fashion.

Ultimately, you will be clubbing the SQL searches that you do into a group so that they are handled at once rather than individually.

Transaction properties

The word that you want to remember when you are working with transactions is going to be ACID. This is because of the letters ACID all stand for one of the properties that you can use with SQL.

A: Atomicity: the operations that you place into your equation will give you a favorable result. However, if the equation fails, then the process you have put into place is going to be terminated and any operation done before this is going to be void as everything is going to return to its former state.

C: Consistency: any changes that are made are going to be watched to ensure they are being made correctly in order for that transaction to be considered successful.

I: Isolation: transactions do not have to run together, they can run seperately while remaining transparent from other transactions being made on that data base.

D: Durability: all your transactions should be successful in order to survive, this means that they need to be able to withstand any system failures that may occur.

Transaction control

As you are managing your transactions in order to ensure they are successful, you are going to be using four different commands.

Set transaction: you can title your transaction so it can be located easier.

Commit: all your changes for your transaction will be saved.

Save point: you will save your transaction and should it have to be rolled back due to some error, it will roll back to the last save point.

Roll back: any changes that have been made will be undone and will go back to the last save point.

You do not have the ability to use create or drop table commands with transactions being that they are standard data base commands. You can still use delete, update, and insert.

Commit command

Indexes in SQL

If you have to find data quickly in your table, you are going to want to use an index. An index is going to save time because you are not going to have to read through everything in order to find the one thing that you are looking for. It is much like the index you find in books!

An index is going to be used whenever you try to locate data from a particular table. In the event that you have not created an index, then SQL is going to read through the entire table before it finds what you are looking for, which is not only time-consuming, but it can give you results that you are not looking for. The goal with an index is to have it created in such a way that you are able to go straight to what you are looking for in a couple of minutes, not hours.

Here are just several reasons as to why you are going to want to create an index.

1.It can cover multiple columns

Sometimes you know what you are looking for is in a general area, and with that, you can use an index to cover just those columns.

2.Indexes and integer data types

The integer data type is not going to take up as much room as some of the data types; therefore, searching integers is faster. In the event that what you are looking for does not have an integer on your index, you will want to think about putting in a temporary integer so that all the data you are putting in your index for that column is mapped.

3.An index needs to be kept narrow

The closer you create your index, the less room it will take up, so the less time SQL is going to spend trying to search for the information you are wanting. The less room that is used, the faster the data base is going to run.

4.The order of your columns is utterly important

Sometimes and an index has to cover several columns. When this happens, you have to keep your columns in order, or else, you are going to cross data over into an area where it does not belong. Try and keep yourself focused as you begin with the column that ranks lowest on your scan working your way up to the one that holds the highest priority. The level of your column will depend on how many values are located in that column.

5.Ensure your column is not marked as null before you make your index

Columns that are marked as null does not need to be in your index. So, only put the columns that have been marked as not null so that processing takes less time and you are able to work with a faster system.

6.Indexes should only be created when they are needed

If you can get away without a guide, then do it! Indexes, just like everything else, take up space on the SQL disk making it to where commands you use end up returning results slower than normal. Being that indexes do not have any rules set into place as to how they should be built or when they should be constructed, the creation of an index is going to be a process that continues to change until a process can be found that works.

Constructing an index statement

The purpose of an index is meant to make SQL code run faster than before. This is done by making it to where queries do not scan the entire table or data base unless necessary.

The syntax for creating an index is as follows:

CREATE INDEX “index_title” ON “table_title” (column_title);

The downside of an index is that it can only cover a single table. Many indexes are only going to cover a single column however while composite indexes cover several columns at once.

While you create your index, you are going to notice that there are no rules that you are going to have to follow as to what the index is titled or what is placed in the index. Therefore, your index is going to be completely unique to you and the data that you are putting in it. It is a good plan to attempt to add in as much information as you can so you do not get confused which table or columns you are working with. Keep in mind, however, the bigger the index, the more disk space it will take up.
