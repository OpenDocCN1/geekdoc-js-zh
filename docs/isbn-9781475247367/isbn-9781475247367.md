## 前言

JavaScript 是一门富有表现力、功能强大且用途独特的语言。但每种语言都有其局限性。JavaScript 最初是为了增强在 Netscape 2.0 中浏览的网页而设计的，如今却面临着在一个多媒体、多任务、多核的世界中作为单线程语言运行的挑战。

然而，JavaScript 自 1995 年以来不仅顽强生存了下来，更是蓬勃发展。在浏览器中，潜在的竞争对手——比如 Flash、Silverlight 和 Java applets——随着 HTML5 的兴起已经来了又（大体上）去了。与此同时，当一位名叫 Ryan Dahl 的程序员想要为事件驱动服务器构建一个新框架时，他四处寻找一种既是动态语言又是单线程语言的工具，最后才意识到答案就在他眼前。于是，Node.js 诞生了，JavaScript 作为一种服务器语言也成为一股不可忽视的力量。

事实证明，事件是多线程的一个强有力替代方案。基于事件的代码避免了线程切换的开销，更不用说保持多线程代码安全所需的互斥锁、信号量以及其他样板代码了。现在 JavaScript 程序员面临的挑战是将自己从俄罗斯套娃式的编程风格中解放出来：回调嵌套着回调，一个接一个，直到他们的文本编辑器拒绝添加更多缩进。这种可怕的代码惯用法被戏称为*回调金字塔*：²

```
step1(function(result1) {
  step2(function(result2) {
    step3(function(result3) {
      ...
    });
  });
});
```

“我爱异步，但我没法这样写代码，”一位开发者曾在 Node.js 的 Google 群组中如此抱怨。³ 但问题不在于语言本身，而在于程序员使用该语言的模式。通常，在多线程语言中很简单的代码，移植到 JavaScript 后就会变得一团糟。处理无数的异步任务是 JavaScript 的前沿领域，正如它曾经在 Java、Ruby 以及其他语言中一样。

**让我们推动前沿前进。** 让我们向世界证明，即使是最复杂的问题也能用干净、优雅的 JavaScript 代码来解决。

## 本书面向谁？

本书面向中级到高级的 JavaScript 开发者。你应该了解变量的作用域。像 `typeof`、`arguments` 和 `this` 这样的关键字不应该让你感到困惑。或许最重要的是，你应该理解


除了 `next` 需要在特定上下文中调用的情况外（请参阅 Reg Braithwaite 的优秀文章《Captain Obvious on JavaScript》），这只是编写以下代码的一种冗长啰嗦的方式：

```
func(next);
```

## 本书中的代码风格

JavaScript 有许多风格上的变体。对于本书，我采用了流行的双空格软制表符和驼峰命名标识符的组合。

稍微更专业一点的是，我试图采用 Reg Braithwaite 所青睐的链式调用约定，其中缩进级别用于区分不同的对象。例如，我会将 jQuery 表达式

```
$('h1').first().addClass('first').end().last().addClass('last');
```

写成

```
$('h1')
  .first()
  .addClass('first')
.end()
  .last()
  .addClass('last');
```

因为 `end` 方法返回与原始选择器相同的对象，而 `first` 和 `last` 返回的是不同的东西。

按照 Braithwaite 的术语，在类似

```
turtle
  .turnRight(90)
  .moveForward(5);
```

代码中使用的技术被称为*链式调用*（因为每个方法都返回调用该方法的同一对象），而在类似

```
[1, 2, 3, 4, 5]
    .filter(function(int) { return int % 2 === 1; })
    .forEach(function(odd) { console.log(odd); })
```

代码中使用的技术被称为*管道调用*，因为 `filter` 和 `forEach` 返回的是不同的东西。

# 1 JavaScript 事件模型

事件。它们是如何工作的？对 JavaScript 事件模型的困惑与 JavaScript 本身一样古老。特别是对于从 Java 和 Ruby 等多线程语言转向 JavaScript 的程序员来说，以下情况完全令人费解：

```
for (var i = 1; i <= 3; i++) {
  setTimeout(function(){ console.log(i); }, 0);
};

4
4
4
```

在本章中，我们将游览 JavaScript 的异步机制，并 dispel 一些常见的误解。一旦我们站稳脚跟，我们将简要介绍一些预编译器和替代运行时，它们可以让异步 JS 代码更加人性化。

## 1.1 现在或稍后

让我们从解释上面的 `setTimeout` 示例开始。大多数 JavaScript 新手会期望循环产生输出 1、2、3，或者当三个超时（每个都计划在 0 毫秒内触发）争先恐后地首先触发时，这三个数字的某种随机排列。要理解为什么输出是 4、4、4 而不是其他结果，你需要知道三件事：

1. 只有一个变量 `i`，由声明 `var i` 作用域。

2. 循环结束后，`i === 4`。

3. JavaScript 事件被阻塞，直到线程空闲为止。

前两个概念属于 JavaScript 101 的范畴，但第三个可能听起来陌生。当我第一次接触 JavaScript 时，我并不完全相信所有这些"阻塞"的说法。Java 让我担心我的代码可能随时被中断。百万个边缘情况占据了我的脑后，我想知道，"如果在这两行代码之间发生了罕见的事件怎么办？"直到有一天，我意识到我自由了。以下是解放我的代码：

```
var start = new Date();
setTimeout(function(){
    var end = new Date();
    console.log('Time elapsed:', end - start, 'ms');
}, 500);
while (new Date() - start < 1000) {}
```

在我多线程的思维模式中，我预计定时函数运行前只会过去 500 毫秒。但这需要设计为持续 1000 毫秒的循环被中断。相反，如果你运行这段代码，你会得到输出

Time elapsed: 1002ms

（或多或少几毫秒——遗憾的是，`setTimeout` 和 `setInterval` 远不如你希望的那么精确，特别是在旧版浏览器中）。

那么，`setTimeout` 到底在做什么？

### 认识队列

当我们调用 `setTimeout` 时，一个超时事件被*排队*。只有当我们的 JavaScript 代码运行完毕后，运行时才会问："好的，队列上有什么？"如果队列上至少有一个事件有资格"触发"（比如一个 500 毫秒的超时在 1002 毫秒前被设置），运行时就会选择一个并调用其"处理程序"（例如我们传给 `setTimeout` 的函数）。当该处理程序返回后，我们回到队列。

输入事件的工作原理相同：当你点击一个已附加点击处理程序的 DOM 元素时，点击事件被排队。但该事件不会触发，直到任何正在运行的代码完成。当网页停止响应你的输入时，这通常是原因。（参见下一节的示例。）

有时"事件循环"这个术语被用来描述运行时是如何工作的。就好像你的代码是从这样一个循环中运行的：

```
runYourScript();
while (atLeastOneEventIsQueued) {
    fireNextQueuedEvent();
}
```

这意味着每个触发的事件都将是堆栈跟踪的根。本章稍后会详细介绍。

**总结：** 事件可以在代码运行时*排队*，但它们不能*触发*，直到运行时空闲。

### 细节，细节

你可能想知道运行时究竟如何决定触发哪些排队的事件。不幸的是，具体细节因 JavaScript 环境而异，即使在现代网络浏览器之间也是如此。我设置了 jsFiddle 示例来说明这一点。³ HTML 包含一个带有 id `masochist` 的单一链接，代码如下：

```
var clickCount = 0, link;
link = document.getElementById('masochist');
link.innerHTML = 'How many times can you click me?';
link.onclick = function(){
    clickCount++;
    link.onclick = function(){ clickCount++; };

    start = new Date();
    while (new Date() - start < 5000) {}
    console.log(clickCount); // this will always be 1

    setTimeout(function(){
        link.innerHTML = 'You clicked me ' + clickCount + ' times. Ow!';
    }, 0);
};
```

尝试在你最喜欢的浏览器中加载此示例，并在 5 秒内尽可能多次地点击链接。根据你使用的浏览器，你会得到非常不同的结果。

在 Chrome 中，即使浏览器在第一次点击后的那 5 秒内基本上被冻结（由于 `while` 循环），你仍然会获得准确的点击次数。如果 `setTimeout` 在循环之前运行，计数将为 0，因为旧的超时会被赋予比新点击事件更高的事件队列优先级。

在 Firefox 中，超时在任何点击事件之前触发，这些点击事件则分散在时间中。如果你将延迟从 0 毫秒提高到 200 毫秒，你会看到几次点击。提高到 300 毫秒，你会看到更多次。

注意到那个 `console.log` 行了吗？如果你查看控制台，无论点击链接多少次，你只会看到一个 1。我添加它是为了说明事件和处理程序之间的区别：原始点击处理程序直到所有点击事件都已排队后才会被调用。然后它附加一个新的处理程序，替换掉自己。当剩余的排队点击事件触发时，运行时会调用新的处理程序。

当然，当你正确地进行事件驱动的 JavaScript 编程时，这些细节往往并不重要。确保你的代码不包含运行 5 秒的 `while` 循环是第一步。

## 1.2 函数何时是异步的？

术语*异步函数*有点用词不当，因为 JavaScript 代码本身总是同步的。如果你调用一个函数，你的程序将不会继续直到该函数返回。我说的"异步函数"是指一个接受另一个函数（一个*回调*）的函数，该回调直到我们到达事件队列时才会运行。所以异步函数永远不会失败这个测试：

```
var a = false;
asyncFunction(function() { console.assert(a, 'a should be true'); })
a = true;
```

我们看到即使传递给 `setTimeout` 的延迟是 0，它也通过了这个测试。

异步函数的另一个术语是**非阻塞**。这强调了它们通常的速度有多快：使用异步 MySQL 驱动程序进行的 SQL 查询可能需要一个小时，但发出查询的函数会在不到一毫秒的时间内返回——这对于需要同时处理多个传入请求的 Web 服务器来说是一个福音。

通常，回调作为函数的最后一个参数给出。（遗憾的是，老牌的 `setTimeout` 和 `setInterval` 是这个约定的例外。）但有些异步函数通过返回 Promise 或使用 `EventEmitter` 间接地接受回调。我们将在接下来的几章中学习这些模式。

不幸的是，确定一个函数是否是异步的唯一方法是查看其源代码（以及可能地，它依次调用的每个函数的源代码）。有些同步函数具有看起来是异步的 API，因为它们将来可能变成异步的，或者因为回调提供了一种返回多个参数的好方法。如有疑问，不要依赖一个函数是异步的。

### 可能异步，可能不是

有些函数有时是异步的，有时则不是。例如，jQuery 的同名函数（通常别名为 `$`）可以用来延迟一个函数直到 DOM 完成加载。但如果 DOM 已经完成加载，就没有延迟；回调立即触发。

同样，jQuery 的 Promises（一个很棒的功能，在 1.5 版本中添加，我们将在后面的章节中介绍）允许你在任务完成前后添加回调，例如 Ajax 调用。如果回调是在之后添加的，它会立即触发。

如果你不小心，这些"可能异步"的函数可能会给你带来很多麻烦，因为你无法指望函数之后的代码会在回调之前运行：

```
var h1FontSize;
$(function() {
  $('#h1').css('fontSize', h1FontSize);
});
h1FontSize = 24;
```

信不信由你，我确实见过这样的代码。它运行正常——直到浏览器从缓存中加载页面，在脚本运行之前 DOM 就已经准备就绪。

*永远*不要定义一个"可能异步"的函数，使其返回的值可能在回调中有用：

```
var connection = ssh.connect(serverAddress, function() {
  connection.send('Hello, client!');
});
```

如果 `ssh.connect` 是同步执行的，`connection` 在回调中将是 `undefined`，调用 `send` 的尝试将会抛出错误。

现在请将自己置于 API 设计者的角度来思考。假设你希望每个 `serverAddress` 只维护一个连接。那么当有人调用 `ssh.connect` 并传入一个你已经拥有连接的 `serverAddress` 时，你只需要调用回调并返回该连接即可。但我们已经看到立即调用回调会造成灾难性后果。解决方案是什么？将回调包装在 `setTimeout` 中：

```
var connectionCache = {}
ssh.connect = function(serverAddress, callback) {
  var connection;
  if (serverAddress in connectionCache) {
    connection = connectionCache[serverAddress];
    setTimeout(callback, 0);
  } else {
    connection = makeConnection(serverAddress, callback);
  }
  return connection;
};
```

（在 Node 中，当你希望一个函数尽可能快地从事件队列中触发时，请使用 `process.nextTick` 而不是 `setTimeout`；详见下一节。）

## 1.3 异步原语

在所有主要的 JavaScript 环境中，只能找到两个异步函数：`setTimeout` 和 `setInterval`。除此之外，每个环境都添加了自己特有的异步机制。

### 异步输入

JavaScript 开发者很早就知道，无论何时需要输入——无论是来自用户还是某个远程服务器——都需要在某处定义一个回调并等待它被触发。在浏览器中，这一点尤为突出，因为同步等待输入很可能会给用户带来旋转的死亡彩球。² 值得注意的是，Ajax——尽管其名称中就带有"异步"——有一个 `async` 选项，该选项可以（但*永远、永远不应该*）被设置为 `false`。

Node 的输入函数基本上是非阻塞的，但有一些提供了带 `Sync` 后缀的同步替代方案。例如，你可以使用 `readFileSync` 代替 `readFile`。这些并非总是糟糕的选择；例如，在启动时使用 `readFileSync` 加载 Web 服务器的配置并没有什么问题。另一方面，如果你想每五秒自动重新加载该配置文件，使用 `readFileSync` 代替 `readFile` 可能会显著降低服务器性能。在复杂的 Node 应用中使用同步 I/O 方法是一个糟糕的习惯。

### 异步输出

JavaScript 的输出几乎总是异步的。例如，你可以在一段长代码中随心所欲地更新 DOM，但用户在你返回事件队列之前不会看到任何变化。隐含地，你所做的任何更改都会将一个"重绘"事件放入队列。

即使无处不在的 `console.log` 在某些环境中也是异步的。在基于 WebKit 的浏览器（Chrome 和 Safari）中，以下代码将输出 `{foo: bar}`：

```
var obj = {};
console.log(obj);
obj.foo = 'bar';
```

（而 Node 的 `console.log` 是同步的，因此相同的代码将输出 `{}`。）

这里的关键是，并非所有的异步行为都是显而易见的。页面重绘对用户体验至关重要，但它们没有回调（尽管任何 `setTimeout` 都可以胜任，因为重绘具有优先级，至少在现代浏览器中如此）。而 WebKit 的 `console.log` 以其看起来很像量子纠缠的行为困扰了许多开发者。

当输出函数接受回调时，回调通常是可选的。例如，你可以向 Node 的 `fs.writeFile` 提供一个回调，以便在文件保存完成时得到通知并处理可能发生的错误，但如果文件不是必需的，你也可以不提供回调。

### 高级定时方法

回顾一下，`setTimeout` 和 `setInterval` 是不精确的。有多不精确？这取决于环境。以下是一个测试用例：

```
var fireCount = 0;
var start = new Date();
var timer = setInterval(function() {
    if (new Date() - start > 1000) {
        clearInterval(timer);
        console.log(fireCount);
        return;
    }
    fireCount++;
}, 0);
```

当我们使用 `setInterval` 和 0ms 延迟来调度一个事件时，它应该尽可能频繁地运行，对吧？那么在那一秒钟内，在一台搭载高速 Intel i7 处理器的现代浏览器中，事件触发了多少次？

大约每秒 200 次。这在 Chrome、Safari 和 Firefox 中都是一样的。在 Node.js 下，事件以大约每秒 1000 次的速率触发。作为对比，将 `setInterval` 替换为简单的 `while` 循环，在 Chrome 中该速率可达到每秒 400 万次，在 Node 中可达到每秒 500 万次！

这是怎么回事？表面上看，在现代浏览器中，每次进入事件队列都会增加大约 5ms 的开销（在 Node 中为 1ms）。*天哪。*

幸运的是，开销主要来自 `setInterval`，它被设计为低优先级。`setTimeout` 的优先级稍高一些。但根据 HTML 规范，`setInterval` 和 `setTimeout` 都有 4ms 的最小延迟。<sup>3</sup>

那么当你需要更精细的定时精度时该怎么办？一些运行时提供了专用的替代方案：

- 在 Node 中，`process.nextTick` 名义上等同于延迟 0ms 的 `setTimeout`，但效率要高得多。在我的系统上，`process.nextTick` 事件的触发速率约为每秒 100,000 次。

- 前沿浏览器提供了 `requestAnimationFrame` 方法，它具有双重用途：它允许可见动画以每秒 60 帧以上的速率运行，同时对后台标签页中的动画进行节流以节省 CPU 资源。

尽管 `setTimeout` 和 `setInterval` 是异步 JavaScript 的基石，但永远不要忘记它们是不精确的工具。

## 1.4 嵌套回调

到目前为止，我们一直将事件视为一次处理一件事务。从运行时的角度来看，这是准确的。但要将这种概念理解映射到如下这样的示例可能很困难：

```
function checkPassword(username, passwordGuess, callback) {
  var selectUser = 'SELECT * FROM user WHERE username = ?'
  db.query(selectUser, username, function (err, result) {
    if (err) throw err;
    if (!result['password_hash']) return callback(false);
    hash(passwordGuess, function(passwordGuessHash) {
      callback(passwordGuessHash === result['password_hash']);
    });
  });
}
```

在这里，我们定义了一个异步函数（`checkPassword`），它触发另一个异步函数（`db.query`），而后者又可能触发另一个异步函数（`hash`）。（如果不实际阅读这些函数的代码，就无法确定它们是否是异步的，但在这里这样假设是合理的。）请注意，我们不可能定义一个使用相同内部函数的阻塞式 `checkPassword`。从 `db.query` 获取响应的唯一方式是使用回调，而该回调在我们的代码执行完毕、轮到事件队列之前不会被调用。这是许多 JavaScript 开发者的噩梦：一旦你以异步方式做了一件事，你就必须以异步方式做所有事情。

这些事件的嵌套仅对作用域有意义。例如，我们的 `hash` 回调需要能够看到 SQL 查询的结果。如果我们以其他方式共享状态，就可以将它们拆开：

```
function checkPassword(username, passwordGuess, callback) {
  // Store all state in a hash
  var state = {};

  // Define callbacks in the order in which we expect them to run
  function sqlCallback (err, result) {
    if (err) throw err;
    if (!result['password_hash']) return callback(false);
    state.passwordHash = result['password_hash'];
    hash(passwordGuess, hashCallback);
  }

  function hashCallback (passwordGuessHash) {
    callback(passwordGuessHash === state.passwordHash);
  }

  // Start the async process
  var queryStr = 'SELECT * FROM user WHERE username = ?';
  db.query(queryStr, username, sqlCallback);
}
```

这种方法虽然更冗长，但在大规模应用时清晰得多。一般来说，**避免超过两层函数嵌套**。关键在于找到除作用域之外的共享状态的方式。如果听起来很复杂，也不用担心；我们将在后续章节中看到大量异步事件按顺序运行而无需嵌套处理程序的示例。

## 1.5 回调中的异常

你是否注意到我们的 SQL 回调顶部的这行代码？

```
if (err) throw err;
```

这在 Node 世界中是非常常见的惯用写法。（浏览器类库倾向于遵循 jQuery 的做法，使用单独的回调来处理错误。）但是抛出错误之后到底发生了什么？让我们来运行一个测试：

```
setTimeout(function A() {
  setTimeout(function B() {
    setTimeout(function C() {
      throw new Error('Something terrible has happened!');
    }, 0);
  }, 0);
}, 0);
```

运行这段代码，你会发现堆栈跟踪异常简短：

```
Error: Something terrible has happened!
    at Timer.C (/AsyncJS/nestedErrors.js:4:13)
```

等一下——A 和 B 去哪了？为什么它们不在堆栈跟踪中？因为它们不在调用栈上。A 和 B 已经执行完毕，C 是直接从事件队列中运行的。

这会使 JavaScript 的堆栈跟踪变得非常令人困惑。如果在我们的 SQL 示例中我们抛出 `err`，堆栈跟踪将只包含 SQL 库和我们回调中的函数与行号。它无法提供关键的上下文信息：查询是从哪里发起的？

一个常见的新手错误是在异步代码周围放置 `try...catch` 块。例如：

```
try {
    checkPassword(username, passwordGuess, matchHandler);
} catch (e) {
    console.log(e);
}
```

你看出问题了吗？如我们所定义的 `checkPassword` 本身永远不会抛出错误。只有**嵌套在其中**的异步回调才会抛出错误。而该回调仅出于作用域目的才与 `checkPassword` 有关。试图在异步回调周围放置 `try...catch` 块是毫无意义的。这就是为什么 Node 回调几乎总是将错误作为第一个参数。

### 未捕获的异常

当我们从回调中抛出异常时，由运行回调的代码负责捕获它。如果它没有捕获，则由运行时处理。现代浏览器通常会在开发者控制台中记录错误并返回事件队列，不过这种行为可以通过将处理程序附加到 `window.onerror` 来使用"全局捕获"进行覆盖。

Node 中与 `window.onerror` 等效的是全局 `process` 对象的 `'uncaughtException'` 事件：

```
process.on('uncaughtException', function (err) {
    console.log(err); // shutdown averted.
});
```

通常情况下，Node 应用在遇到未捕获的异常时会立即退出。但只要存在至少一个 `uncaughtException` 处理程序，应用就会简单地返回事件队列。Node 服务器通常使用这种方式，使 `throw` 变得安全。这样做的缺点是它不够透明：当你抛出一个异常时，它可能会触发你应用程序中任何模块注册的任意数量的 `uncaughtException` 处理程序。使用 `return log(err);` 而不是 `throw err` 会让人更清楚地了解 `err` 的最终命运。

一些 JavaScript 开发者，特别是 Isaac Schlueter，更广泛地认为 `try/catch` 是一种反模式。⁵ 他希望 `throws` 仅用作断言，在出现异常行为时将程序终止。

**记住：** 异常严格存在于同步世界中。当你到达事件队列时，调用栈会被重置。每一段堆栈跟踪都是一条不间断的阻塞代码链。

## 1.6 驯服 JavaScript 的工具

本书的其余部分关注的是在纯 JavaScript 中处理事件的库和设计模式。但在继续之前，你应该了解一些替代方案，我将在此简要介绍。

⁵ https://groups.google.com/forum/#!topic/nodejs/1E5ssslxrrU

### ES6 和 Task.js

ECMAScript 6（目前仍在制定中，但在 Firefox 中可用）添加了一个名为 **generators（生成器）** 的新特性。生成器是包含 `yield` 关键字的函数，允许你以一种只阻塞生成器本身的方式运行异步函数，从而无需回调。生成器本身理解起来有些棘手，但一个名为 Task.js[^1] 的 Mozilla 项目通过提供基于 Promise 的标准 API 使它们更易使用。（Promise 将是后续章节的主题。）

这可能就是 JavaScript 的未来。不幸的是，规范要正式发布还需要一段时间，全世界的每个浏览器都支持生成器更是需要数年时间……

### TameJS

OkCupid 的优秀程序员们创建了一个巧妙的预编译器[^2]，拥有超过 500 个 GitHub 关注者，它为 JavaScript 添加了两个关键字：`await` 和 `defer`。`await` 块的作用类似于生成器，定义的代码不会返回，直到用 `defer` 定义的每个异步任务都已完成。

Tame.js 团队还创建了一个具有 `await`/`defer` 功能的 CoffeeScript 分支，名为 IcedCoffeeScript[^3]。

### StratifiedJS

StratifiedJS 是 `yield` 范式的替代方案，提供了更细粒度的控制结构，具有直观的名称如 `waitfor` 和 `resume`。虽然没有被广泛使用，但它获得了 jQuery 创建者 John Resig 等人的赞誉。其创建者 Oni Labs 对它有着雄心勃勃的计划。

请注意，StratifiedJS 是规范的名称，而非实现的名称。官方参考实现称为 Oni Apollo[^4]。

### Kaffeine

如果你难以理解 `yield`/`await`，Kaffeine 提供了简单的语法糖：只需在异步函数名后添加 `!`。Kaffeine 假设该函数将回调作为最后一个参数，并简单地将该函数调用后的所有代码转换为回调。例如：

```
var sleep = function(delay, callback) { setTimeout(callback, delay); }
console.log('Wait a second...');
sleep(1000)
console.log('OK, that was one second.');
```

虽然它的追随者不如 CoffeeScript 多，但这样的特性使得 Kaffeine 值得一试。

### Streamline.js

与 Kaffeine 类似，Streamline.js 允许你使用特殊语法将异步函数视为同步函数：只需用 `_` 代替回调。有趣的是，Streamline 可以生成标准的基于回调的 JavaScript 代码，也可以生成用于 node-fibers（见下文）的基于纤维的代码。另外，与大多数其他 JavaScript 预编译器不同，Streamline 可以与 CoffeeScript 配合使用。

请注意，Kaffeine 和 Streamline 都依赖于回调遵循参数列表约定（`err, results...`），这在 Node 世界中无处不在，但在浏览器中不太常见。

### node-fibers

虽然上述其他项目仅编译为普通 JavaScript，但 node-fibers 实际上扩展了 Node.js 运行时所理解的语言，添加了称为 fibers 的类似线程的构造。node-fibers 相对于 JS 预编译器的主要优势在于调试。node-fibers 堆栈跟踪中的行号与 node-fibers 源代码中的行号相对应，从 fibers 中抛出的异常比从异步回调中抛出的异常表现得好得多。

这是一个非常酷的项目，拥有少量但热情的追随者。但要注意，它并不总是能与主流 Node 工具良好配合。

在本章中，我们了解了 JavaScript 的单线程特性如何既是祝福又是诅咒。在适当的人手中，它能产出优美的代码，免受困扰多线程应用的可怕竞态条件之苦。但你需要培养正确的思维方式——以及正确的技术。

在此值得一提的是，JavaScript 中有一种多线程形式：你可以生成 worker 进程。每个生成的进程可以在与其他 I/O 相同的限制下与其他进程交换数据。这使得利用多核成为可能，同时不违反 JavaScript 的正常规则（代码不能被中断；变量只能在其作用域内访问）。关于 workers 的更多内容，请跳转到本书的倒数第二章。

在下一章中，我们将讨论如何组织和堆叠事件回调。如果我们做得好，我们的异步应用应该拥有你能想到的尽可能多的回调——每一个都有清晰而单一的用途。

# 2 分布式事件

在上一章中，我们探讨了JavaScript中异步事件的工作原理。但在实践中，我们应该如何处理这些事件呢？

这可能听起来像个傻问题。只需为你应用关心的每个事件附加一个处理器，对吧？但当一个事件产生多种后果时，“一个事件，一个处理器”的方法迫使处理器变得*极其*庞大。

以基于Web的文字处理器（如Google Docs）为例。当用户按下按键时，需要发生多件事情：新字符必须被添加到DOM中并且光标移动；操作必须被推送到撤销历史记录并同步到服务器；新单词必须进行拼写检查；字数和页数可能需要更新。从单个事件处理器中执行所有这些任务乃至更多，是一个艰巨的任务。

从机械的角度来看，我们希望在响应事件时执行的每项任务确实都必须从事件处理器启动。但为了我们人类的便利，通常最好用一个更灵活、动态的构造来替代那个一刀切的事件处理器——一个我们可以随时添加任务和移除任务的构造。简而言之，我们想使用*分布式事件*，其中一个事件可以触发整个应用程序中的反应。

在本章中，我们将学习PubSub模式和事件化模型，它们是JavaScript应用程序中越来越普遍的特性。我们还将看看jQuery中的自定义事件，并认识一个名为LucidJS的新库，它非常适合将PubSub对象连接在一起。

## 2.1 PubSub

自从JavaScript诞生以来，浏览器就允许将事件处理器附加到DOM元素，像这样：

```
link.onclick = clickHandler;
```

啊，极其简单！只有一个注意事项：如果你想为一个元素设置*两个*点击处理器，你就必须用一个包装函数自己将它们聚合起来：

```
link.onclick = function() {
  clickHandler1.apply(this, arguments);
  clickHandler2.apply(this, arguments);
};
```

这不仅乏味，也是导致处理器函数臃肿、万能的根源。

这就是为什么W3C在2000年将`addEventListener`添加到DOM规范中，而jQuery用`bind`方法对其进行了抽象。`bind`可以轻松地为任何元素（或元素集）上的任何事件添加任意数量的处理器，而不用担心妨碍其他人：

```
$(link)
    .bind('click', clickHandler1)
    .bind('click', clickHandler2);
```

（在jQuery 1.7+中，新的`on`语法<sup>1</sup>比`bind`更受青睐。还有`click(...)`方法，它是`bind('click', ...)`的简写；然而，我更喜欢始终使用更强大的`bind`/`on`。）

从软件架构的角度来看，jQuery正在向任何想要订阅的人发布`link`元素的事件。因此有了术语“PubSub”。

鉴于DOM的经验教训，Node的API设计者摒弃了`object.onevent = ...`技术，转而采用一个名为`EventEmitter`的通用PubSub接口。Node中几乎每个I/O源都是一个`EventEmitter`：文件流、HTTP服务器，甚至应用程序进程本身。例如：

```
['julz', 'norah', 'fiona'].forEach(function(name) {
    process.on('exit', function() {
        console.log('Goodbye, ' + name);
    });
});
```

浏览器上存在无数纯PubSub实现。此外，像Backbone.js和Spine这样的许多MVC库也提供了它们自己的`EventEmitter`类似模块。我们将在本章后面讨论这些。

### EventEmitter

让我们以Node的`EventEmitter`作为PubSub接口的一个例子。它有一个简单的、近乎最小化的设计。

要向`EventEmitter`添加事件处理器，只需调用`on`并传入事件类型和处理器：

```
emitter.on('evacuate', function(message) {
    console.log(message);
});
```

恰如其名的`emit`方法发出给定类型的事件。例如，

```
emitter.emit('evacuate');
```

会调用所有的`'evacuate'`处理器。

（注意，这里的术语“事件”与事件队列无关。请参见下面的“同步性”部分。）

你可以在发出事件时添加任意数量的附加参数。所有参数都会传递给所有处理器：

```
emitter.emit('evacuate', 'Woman and children first!');
```

对事件名称没有限制，不过Node文档提供了一个有用的约定：

通常，事件名称用驼峰式字符串表示。

`EventEmitter`的所有方法都是公共的，但通常的约定是事件只从`EventEmitter`“内部”发出。相反，通常的约定禁止`EventEmitter`将处理器附加到自身。

### 自己动手实现PubSub

PubSub实现非常简单，我们可以在大约十几行代码中创建一个。我们需要存储的唯一状态是每个我们支持的事件类型的处理器列表：

```
PubSub = {handlers: {}}
```

当我们添加一个监听器时，我们将其推送到数组的末尾（这意味着监听器将总是按照它们被添加的顺序被调用）：

```
PubSub.on = function(eventType, handler) {
    if (!(eventType in this.handlers)) {
        this.handlers[eventType] = [];
    }
    this.handlers[eventType].push(handler);
    return this;
}
```

然后，当一个事件被发出时，我们遍历所有处理器：

```
PubSub.emit = function(eventType) {
    var handlerArgs = Array.prototype.slice.call(arguments, 1);
    for (var i = 0; i < this.handlers[eventType].length; i++) {
        this.handlers[eventType][i].apply(this, handlerArgs);
    }
    return this;
}
```

就这样：我们刚刚实现了Node `EventEmitter`的核心。（我们唯一缺少的主要功能是移除处理器和附加一次性处理器的能力。）

当然，PubSub实现在功能上略有不同。当jQuery团队注意到库中使用了多种不同的PubSub实现时，他们决定在jQuery 1.7中用`$.Callbacks`来抽象它们。<sup>2</sup> 你可以不使用数组来存储与事件类型对应的处理器，而是使用一个`$.Callbacks`实例，它接受几个选项：

- **once**：回调列表只会触发一次。这用于Promise，我们将在后面的章节中学习。
- **memory**：如果在添加新回调时回调列表已经触发过，新回调会立即被调用。同样，这主要是为了Promise。
- **stopOnFalse**：如果一个回调返回`false`，则该事件将不再调用其他回调。如果你熟悉jQuery事件，这应该听起来很熟悉。
- **unique**：如果某个特定的回调已经被附加过，尝试再次附加它将被忽略。

奇怪的是，`$.Callbacks`将其选项作为一个以空格分隔的字符串：

```
$.Callbacks('unique memory');
```

更常见的是，许多PubSub实现会解析事件字符串以提供特殊功能。例如，你可能熟悉jQuery中的命名空间事件，我可以通过绑定一个`click.uniqueName`事件以便于后续解绑。Backbone.js（我们很快会更多地了解）允许你将处理器绑定到`all`事件类型，使得它们在任何事件发生时都会触发。jQuery和Backbone都允许你通过用空格分隔（例如 `keypress mousemove`）来同时绑定或发出多个事件类型。

### 同步性

尽管PubSub是处理异步事件的一项重要技术，但它本身并没有任何异步的特性。考虑这段代码：

```
$('input[type=submit]')
  .on('click', function() { console.log('foo'); })
  .trigger('click');

console.log('bar');
```

输出是

```
foo
bar
```

证明`click`处理器是由`trigger`立即调用的。事实上，每当一个事件触发时，它的所有处理器都会按顺序执行，不会中断。

所以让我们明确一点：当用户点击“提交”按钮时，那是一个*异步事件*：第一个点击处理器从事件队列中触发。但作为一个整体，因该点击而发生的一切都是*同步的*，除非某个点击处理器使用了像`setTimeout`这样的东西。这很重要，因为如果太多处理器连续触发，你就有阻塞线程并使浏览器无响应的风险。

回想一下本章开头文字处理器的例子。当用户按键时，需要发生很多件事，其中一些可能需要非常复杂的计算。在返回事件队列之前完成所有这些事情，将是应用程序无响应的根源。

一个好的解决方案是维护一个你自己的队列，用于存放不需要立即处理的事情，并使用定时函数来定期处理队列。

## 2.2 事件化模型

PubSub的一个特例是，当一个用于存储数据的对象（“模型”）在其内容被修改时发出事件。让我们看看流行的Backbone.js[^3]框架，它曾被37signals、Pandora和*《纽约时报》*等公司使用。你可以这样创建一个新模型：

```
style = new Backbone.Model(
  {font: 'Georgia'}
);
```

`model`只表示传入的简单对象：

```
style.toJSON()  // {font: 'Georgia'}
```

但与普通对象不同的是，这个对象可以在发生更改时发布通知：

```
style.on('change:font', function(model, font) {
  alert('Thank you for choosing ' + font + '!');
});
```

> [^3]: http://documentcloud.github.com/backbone/

需要注意的是，我们必须使用模型的 `set` 方法进行这些更改，并用 `get` 方法来检索值：

```
style.set({font: 'Palatino'});  // 触发警报
style.get('font');
```

事件驱动模型在过去几年中已变得非常流行，随着像 Backbone 这样的 MVC 框架的兴起。传统的 JavaScript 直接从输入事件处理程序修改 DOM。而现代的 JavaScript 则修改模型，模型随后会发出事件，从而导致 DOM 更新。除了最小的应用之外，这种关注点分离使得功能更容易跟踪。

此外，Backbone 模型使得通过 Ajax 与服务器同步变得轻而易举：

```
hello.save();      // 将模型发送到服务器
goodbye.fetch();   // 从服务器更新模型
```

Backbone 是由 DocumentCloud 的优秀团队在开发同名的基于 Web 的文档搜索工具时创建的。⁵ 当用户在 DocumentCloud 中输入查询时，服务器会对数千份扫描文档进行全文搜索，几秒钟内，用户就能获得结果的标题、缩略图、元数据以及第一页的摘要。用户可以在网格视图和列表视图之间切换，甚至可以使用时间线可视化。他们还可以添加注释，并查看其他用户添加的注释。这是一个非常令人印象深刻的 JavaScript 应用程序，很难想象没有 Backbone 的功能它会是什么样子。

### 传播模型事件

通常，Backbone 模型被组织成 *集合*，这本质上是事件驱动的数组：你可以监听何时向其中添加或移除模型。此外，Backbone 集合会传播其包含的模型的事件。例如，你可能有一个 `spriteCollection` 对象，其中包含数百个代表你在画布元素上绘制内容的模型。每当其中任何一个精灵发生变化时，你都需要重绘画布。与其将重绘函数单独作为每个精灵 `change` 事件的处理程序，你只需编写

```
spriteCollection.on('change', redraw);
```

请注意，这种自动传播只向下一级。Backbone 没有“集合的集合”的概念。然而，手动传播事件很容易。假设我们想将 `spriteCollection` 分成几个部分，每部分对应几十种精灵中的一种。我们可以将每个这些集合添加到一个名为 `spriteCollectionSet` 的模型中，如下创建：

```
var spriteCollectionSet = new Backbone.Model();

spriteCollectionSet.on('change', function(model, name, collection) {
    collection.on('change', spriteCollectionSet.change());
});
```

其中 `change` 方法只是强制 Backbone 从集合中发出 `change` 事件。

### 循环与静默

假设我们想确保 `x` 始终等于 `2 * y`：

```
var x = new Backbone.Model({value: 0});
var y = new Backbone.Model({value: 0});

x.on('change:value', function(x, xVal) { y.set({value: xVal / 2}); });
y.on('change:value', function(y, yVal) { x.set({value: 2 * yVal}); });
```

你可能期望这段代码在 `x` 或 `y` 的值被更改时导致无限循环。但实际上，这是相当安全的，原因有二：首先，如果新值与旧值匹配，`set` 不会发出 `change` 事件。其次，也是更重要的，Backbone 的设计者决定，任何模型都不应在自身的 `change` 事件期间发出 `change` 事件。更改仍然会执行，但它们是 *静默地* 完成的。

这本身就是一个问题。如果对模型进行了嵌套更改，观察者将只看到最外层的更改，并且可能会不同步。这是为避免无限循环的可能性而付出的代价。

显然，在 Backbone 中维护数据点之间的双向连接是一个挑战。另一个主要的 MVC 框架 Ember.js 允许显式声明双向绑定。那么问题是什么？当一个值改变时，另一个值会从超时事件异步更新。因此，在该事件触发之前，应用程序的数据将处于不一致状态。

对于纠缠模型的问题没有简单的解决方案，但对抗它们的一个主要武器是 Backbone 的 `silent` 标志。如果你在 `set` 事件中添加 `{silent: true}`，就不会发生 `change` 事件。因此，如果多个模型需要同时更新，一个好方法是静默地设置它们，然后仅在它们处于一致状态后才调用它们的 `change` 方法。

## 2.3 自定义 jQuery 事件

自定义事件是 jQuery 中一个被低估的特性，它使得将强大的分布式事件系统嫁接到任何 Web 应用程序变得非常容易，无需额外的库。你可以使用 `trigger` 从任何 DOM 元素发出任何你想要的事件：

```
$('#ozzy, #sten').on('meow', function() {
  console.log(this.id + ' meowed');
});

$('#ozzy').trigger('meow');  // "ozzy meowed"
$('#sten').trigger('meow');  // "sten meowed"
```

如果你之前处理过 DOM 事件，你肯定熟悉 *冒泡*：每当一个元素发出一个事件（比如 `'click'`），它的父元素也会发出该事件，然后是它的祖父元素，如此向上直到根元素 `document`——除非在某个时刻调用了事件的 `stopPropagation` 方法。（当我们从处理程序返回 `false` 时，jQuery 会自动为我们做这件事）。但你知道 jQuery 的自定义事件也会冒泡吗？例如，如果我们有一个名为 `soda` 的 span 嵌套在一个名为 `bottle` 的 div 中，代码

```
$('#soda, #bottle').on('fizz', function() {
  console.log(this.id + ' emitted fizz');
});

$('#soda').trigger('fizz');
```

将输出

```
soda emitted fizz
bottle emitted fizz
```

这种冒泡并不总是可取的，正如我们将在下面的工具提示示例中看到的那样。幸运的是，jQuery 也提供了非冒泡的 `triggerHandler` 方法。

### 示例：工具提示

当事件可以直观地映射到页面元素时，jQuery 是分发它们的理想方式。例如，假设你正在编写一个工具提示库，并且希望一次只显示一个工具提示。所以你可以简单地添加这行

```
$('.tooltip').remove()
```

```
// $container 可以是 $('#sidebar') 或 $(document)
$container.triggerHandler('newTooltip');
$container.one('newTooltip', $tooltip.remove);
```

（注意使用了 jQuery 的 `one` 而不是 `on`。区别在于 `one` 在处理程序触发后会自动移除它。）

通过这两行代码，每个工具提示都会监听其容器，并在容器获得新工具提示时移除自身。这是一种非常直接、高效的方法，使我们无需存储任何状态或设计复杂的选择器（这会拖慢旧版浏览器的速度——IE7 及以下版本甚至没有方法在不遍历整个文档的情况下选择所有具有 `tooltip` 类的元素！）。

请注意，事件冒泡实际上会破坏我们在此处的意图：当我们在侧边栏中创建一个新的工具提示时，我们只希望监听侧边栏本身 `newTooltip` 事件的工具提示消失，而不是监听周围文档的工具提示。始终仔细考虑 `trigger` 还是 `triggerHandler` 才是完成此工作的合适工具。

## 2.4 使用 LucidJS 管道事件

正如我们所看到的，PubSub 有大量的选择。这实际上是一个问题，因为大多数应用程序都会涉及具有细微不同 API 的多个事件源。如果我们能够统一这些发射器并连贯地路由事件，岂不是很好？

LucidJS 就是这样一个新的事件库（实际上，它在本书首次出版前几周才出现在 GitHub 上），它可以监听来自 DOM 元素和 jQuery 对象的事件。这样，你就可以通过 Lucid 自己的类似 `EventEmitter` 的对象“管道”这些事件：

```
// Sailor Moon 粉丝服务
var riniEmitter = LucidJS.emitter();

riniEmitter.pipe($('#serenity'));
riniEmitter.pipe(blackLadyEmitter);

riniEmitter.on('fight', function() {
    console.log('Pink sugar heart attack!');
});
```

现在，每当 `$('#serenity')` jQuery 对象或 `blackLadyEmitter` 发出 `fight` 事件时，`riniEmitter` 都会将该事件转发给给定的处理程序。

随着 PubSub 接口在 JavaScript 中日益普及，`pipe` 技术必将变得更加普遍，因为它允许在一个地方监控来自多个来源的事件。

⁵ http://www.documentcloud.org/public/search/

在本章中，我们学习了通过PubSub分发事件——这是JavaScript最基本的设计模式之一。关键在于决定通过哪些实体来分发事件。我们看到jQuery非常适合分发与DOM变化相关的事件，但用它来分发与应用程序状态相关的事件通常是个错误，因为稍后更改页面的标记可能会改变事件的传播方式。这正是Backbone等框架的用武之地，它们允许您将数据层次结构与数据呈现方式分离。一些应用程序，特别是Node服务器，使用单个全局PubSub对象来连接原本孤立的模块，从而实现松散耦合和轻松测试。PubSub的一大优点是，当您没有订阅正在发布的事件时，它完全不会造成干扰。在下一章中，我们将探讨另一种处理事件的无侵入方式：Promise。

# 3 Promise与Deferred

早在2010年，我与我那位多才多艺的同事Ajax先生有过这样一段对话：

> **我：** 嘿，能帮我从这个URL获取一些数据吗？
>
> **Ajax先生：** 正在处理！给我一个*成功*回调，这样我完成后就能通知你。
>
> **我：** 好的，给你。谢谢。
>
> **Ajax先生：** 哦，你还应该给我一个*失败*回调。你知道的，以防万一。
>
> **我：** 说得好。还有别的吗？
>
> **Ajax先生：** 嘿，我注意到那两个回调之间有一些重复代码！你可以把那部分移到第三个*总是*回调里。
>
> **我：**（不耐烦地）好吧，我来重构它们。这样吧：你现在先去运行，我稍后再给你回调？
>
> **Ajax先生：**（恼怒地）我看起来像个EventEmitter吗？

幸好，jQuery 1.5改变了Ajax先生这种“现在就要”的态度。您所熟知和喜爱的所有Ajax函数现在都返回Promise。*Promise是一个代表具有两种可能结果（成功或失败）的任务*的对象，并持有当其中一种结果发生时触发的回调。例如，在jQuery 1.4下，我不得不这样写：

```
$.get('/mydata', {
  success: onSuccess,
  failure: onFailure,
  always: onAlways
});
```

但在jQuery 1.5+下，我可以改写为：

```
var promise = $.get('/mydata');
promise.done(onSuccess);
promise.fail(onFailure);
promise.always(onAlways);
```

你可能会想，这个变化有什么了不起的？为什么要在Ajax调用触发之后才附加回调？用一个词概括：*封装*。如果一个Ajax调用有多种效果（触发动画、插入HTML、锁定/解锁用户输入……），让发起请求的应用程序部分处理所有意外情况会很笨拙。传递一个Promise要优雅得多。

Promise的另一个优点是（至少在jQuery的实现中）你可以随心所欲地堆叠回调。这大大减少了代码重复，当某个小功能（比如“加载中”动画）在多个Ajax调用中共享时。我建议尽可能堆叠回调，以保持回调尽可能简单：**一个任务，一个回调。**

但使用Promise最大的优点是，你可以轻松地从现有的Promise派生出新的Promise。你可能会请求两个代表并行任务的Promise，让你获得一个通知你它们共同完成的Promise。或者你可能会请求一个代表一系列任务中第一个任务的Promise，让你获得一个代表该系列中*最终*任务的Promise。我们很快就会看到，这些操作对Promise来说是自然而然的。

## 3.1 Promise简史

Promise在许多语言中以多种形式存在过。这个术语最早由C++工程师在Xanadu项目（互联网的前身）上使用。后来，Promise在E编程语言中被使用，这启发了Python开发者以Twisted框架的Deferred形式来实现它们。

Promise在2007年大举进入JavaScript领域，当时开创性的Dojo框架借鉴了Twisted，添加了一个名为`dojo.Deferred`的对象。当时，相对成熟的Dojo在流行度上与尚处于起步阶段的jQuery框架不相上下。2009年，Kris Zyp提出了CommonJS Promises/A规范，<sup>1</sup>并指出受到了`dojo.Deferred`的启发。同年，Node.js首次亮相。Node的早期版本在其文件I/O和DNS的API中使用了Promise。然而，在2010年2月，Ryan Dahl决定转向现在熟悉的`callback(err, results...)`格式，理由是Promise是属于“用户领域”的更高层次的构造。

这一决定为面向Node的竞争性Promise实现铺平了道路，尤其是Kris Kowal的Q.js<sup>2</sup>和AJ O'Neal的Futures。<sup>3</sup>（在通常用法中，“Promise”、“Deferred”和“Future”这些术语大致是同义的。）Q是Promises/A规范的一个相当直接的实现。Futures则是一个更广泛的工具包，包含了Async.js等库中常见的许多流程控制特性。

但Promise如今引起如此多关注的原因，当然是jQuery。伴随着2011年1月`$.ajax`的重大重写，jQuery 1.5的Promise实现让无数第一次接触Promise的开发者兴奋不已。然而，其他人则对Promises/A规范被忽视感到沮丧，这导致了API上的细微差别。

在本章的剩余部分，我们将重点关注jQuery Promise，除了最后关于Promises/A和Q.js的部分。我们还将从jQuery中获取我们的词汇提示，特别是我们将在下一节看到的Deferred和Promise之间的区别，以及使用“resolve”作为“reject”的反义词。

## 3.2 制造Promise

我们通过展示jQuery 1.5+中的Ajax方法（`$.ajax`、`$.get`和`$.post`）返回Promise来开始本章。但要真正理解Promise，我们需要自己制造几个。

让我们给用户一个提示，按Y或N键。（你可以在jsFiddle上看到这个示例的运行效果。）

我们要做的第一件事是创建一个表示用户决定的`$.Deferred`实例：

```
var promptDeferred = new $.Deferred();

promptDeferred.always(function(){ console.log('A choice was made:'); });
promptDeferred.done(function(){ console.log('Starting game...'); });
promptDeferred.fail(function(){ console.log('No game today.'); });
```

> （注意：在jQuery 1.5下，`always`方法被称为`complete`。在jQuery 1.6/1.7下，`always`和`complete`是同义的，但推荐使用`always`。`complete`别名已弃用，并可能在未来版本中移除。）

你可能想知道，既然本节叫做“制造Promise”，为什么我创建的是Deferred实例。别担心——Deferred就是Promise！更准确地说，它是Promise的超集，增加了一个关键特性：你可以直接触发Deferred。纯Promise只允许你添加更多回调；必须由其他人来触发它们。

我们可以用`resolve`和`reject`方法来触发我们的Deferred：

```
$('#playGame').focus().on('keypress', function(e) {
    var Y = 121, N = 110;
    if (e.keyCode === Y) {
        promptDeferred.resolve();
    } else if (e.keyCode === N) {
        promptDeferred.reject();
    } else {
        return false;  // 我们的Deferred保持pending状态
    }
});
```

现在加载页面并按Y键。控制台将显示：

```
A choice was made:
Starting game...
```

你看到发生了什么吗？当Deferred被resolve时，它的`always`和`done`回调被运行了。

刷新页面并按N键：

http://jsfiddle.net/TrevorBurnham/Pj6Bf/

```
A choice was made:
No game today.
```

所以当Deferred被reject时，它的`always`和`fail`回调被运行了。注意回调总是按照它们绑定的顺序运行。如果`always`回调是最后绑定的，控制台输出的顺序就会相反。

尝试反复按Y和N键。在做出第一个选择后，就没有效果了！这是因为Promise只能被resolve或reject一次；之后，它就是惰性的。我们说一个Promise在被resolve或reject之前是`pending`（待定）状态。你可以通过调用它的`state`方法来查明Promise是“pending”、“resolved”还是“rejected”。（`state`是在jQuery 1.7中添加的；在早期版本中，使用`isResolved`和`isRejected`。）

我喜欢说，当我resolve或reject一个Promise时，我就是在触发它，而一个被resolve或reject的Promise是被触发的。这是非标准术语，但我会在本章中一直使用它，因为“触发”/“被触发”这个词比“resolve或reject”/“被resolve或reject”这些短语要直接得多。

Promises/A规范及其包括Q在内的实现使用了一个更合理的术语：一个Promise要么是`fulfilled`（已实现），要么是`rejected`（已拒绝）；无论哪种情况，它都是`resolved`（已解决）的。不幸的是，jQuery似乎被困在了resolved与rejected的二分法中。

### 获取一个纯Promise

我答应给你一个Promise，所以它来了：

```
var promptPromise = promptDeferred.promise();
```

`promptPromise`只是`promptDeferred`的一个副本，没有`resolve`/`reject`方法。无论我们是将回调绑定到Deferred还是其Promise上都没有关系，因为它们在内部共享相同的回调。它们也共享相同的状态（“pending”、“resolved”或“rejected”）。这意味着为单个Deferred创建多个Promise是毫无意义的。事实上，jQuery只会给你同一个对象：

```
var promise1 = promptDeferred.promise();
var promise2 = promptDeferred.promise();
console.log(promise1 === promise2);  // true
```

使用`promise`方法的唯一原因是安全性。如果我们传递`promptPromise`但保留`promptDeferred`给自己，我们就可以放心，在我们希望之前，我们的任何回调都不会触发。

重申一遍：每个Deferred都有一个唯一的Promise，每个Promise都代表一个Deferred。

## 3.3 向回调函数传递参数

当你向 `resolve`/`reject` 传递额外参数时，每个回调函数都会接收到这些参数：

```
var aDreamDeferred = new $.Deferred();
aDreamDeferred.done(function(subject) {
    console.log('I had the most wonderful dream about', subject);
});
aDreamDeferred.resolve('the JS event model');
```

关于 JavaScript 事件模型，我做了一个最美好的梦。

（这可能会让你想起 `EventEmitter` 的回忆。）还有一些特殊方法用于在特定上下文中运行回调（即，将 `this` 设置为特定值）：`resolveWith` 和 `rejectWith`。只需将上下文作为第一个参数传入，并将所有其他参数以数组形式传入：

```
var slashdotter = {
    comment: function(editor){
        console.log('Obviously', editor, 'is the best text editor.');
    }
};
var grammarDeferred = new $.Deferred();
grammarDeferred.done(function(verb, object) {
    this[verb](object);
});
grammarDeferred.resolveWith(slashdotter, ['comment', 'Emacs']);
```

显然 `Emacs` 是最佳文本编辑器。

不过，将参数包装在数组中很麻烦。所以这里有个实用技巧：你可以直接在所需的上下文中调用普通的 `resolve`/`reject`，而不使用 `resolveWith`/`rejectWith`。这是因为 `resolve`/`reject` 会将其上下文直接传递给触发的回调函数。所以在上面的例子中，我们可以用以下方式达到相同的结果：

```
grammarDeferred.resolve.call(slashdotter, 'comment', 'Emacs');
```

## 3.4 进度通知

Promise 是一组当进程结束时想要发生的事情的集合。但难道没有一张励志海报曾告诉你，旅程和目的地同样重要吗？你从那张海报上*什么都没*学到吗？

幸运的是，jQuery 团队吸收了这份智慧（以及 Promises/A 规范），并在 jQuery 1.7 中添加了一种新的 Promise 回调，可以被调用任意次数。它被称为 *progress*。例如，假设我们想要更新一个指示器，显示一个人在"全国小说写作月"（NaNoWriMo）中距离每日字数目标的进度：

```
var nanowrimoing = $.Deferred();
var wordGoal = 5000;
nanowrimoing.progress(function(wordCount) {
    var percentComplete = Math.floor(wordCount / wordGoal * 100);
    $('#indicator').text(percentComplete + '% complete');
});
nanowrimoing.done(function(){
    $('#indicator').text('Good job!');
});
```

（这不是标准约定，但我喜欢用现在进行时 *-ing* 来命名 Promise 和表示并发任务的其他对象的变量名。）

有了可用的 `nanowrimoing` 延迟对象，以下是我们如何响应字数变化的方式：

```
$('#document').on('keypress', function(){
    var wordCount = $(this).val().split(/\s+/).length;
    if (wordCount >= wordGoal) {
        nanowrimoing.resolve();
    } else {
        nanowrimoing.notify(wordCount);
    }
});
```

（实际上，我们可以省略 `else`，每次都运行 `nanowrimoing.notify`，因为在 Promise 被触发后 `notify` 调用会被忽略，就像额外的 `resolve` 和 `reject` 调用被忽略一样。）

Deferred 上的 `notify` 调用会触发我们的 *progress* 回调。就像 `resolve` 和 `reject` 一样，`notify` 可以接受任意参数。（也像 `resolve` 和 `reject` 一样，有一个 `notifyWith` 变体，它将上下文作为第一个参数。）

所以总结一下：Promise 接受三种回调：`done`、`fail` 和 `progress`。`done` 回调在 Promise 完成时运行，`fail` 回调在被拒绝时运行，而 `progress` 回调在挂起的 Deferred 上调用 `notify` 时运行。

### 使用 `then` 绑定多个回调

如果你想同时绑定多种回调，有一个方便的快捷方法：`then`。调用

```
promise.then(doneCallback, failCallback, progressCallback);
```

等同于

```
promise
    .done(doneCallback)
    .fail(failCallback)
    .progress(progressCallback);
```

`then`、`done`、`fail` 和 `progress` 都只是返回它们所附加的对象，就像 jQuery 方法通常的那样。

（正如我们稍后将看到的，`then` 的含义是 jQuery Promises 与 Promises/A 规范之间的关键差异之一。）

## 3.5 动画 Promise

到目前为止，我们已经看到 jQuery 的 Ajax 方法如何返回 Promise，以及如何使用 `$.Deferred` 创建自己的 Promise。但 jQuery 1.6+ 提供了另一个 Promise 来源：普通的 jQuery 对象。当你调用

```
$('#elem').promise()
```

你会得到一个代表 `$('#elem')` 动画队列的 Promise。当 `$('#elem')` 上的所有动画完成时，Promise 会被完成。无论动画是正常完成、调用了 `stop()`，还是一开始就没有待处理的动画，Promise 都会被完成。简而言之，动画 Promise 永远不会失败。

动画 Promise 使查找多个不同元素上的动画何时完成变得容易：

```
$('#header').slideDown('slow');
$('#notification').fadeIn('fast').fadeOut('fast').fadeIn('fast');
$('#header, #notification').promise().done(function() {
    // 上述所有效果都已运行
});
```

正如我们将在下一节中看到的，`$.when` 提供了一种更通用的方式来实现相同的目标。

## 3.6 使用 when 组合 Promise

进度通知的存在并不改变这样一个事实：最终，每个 Promise 要么完成，要么被拒绝。（或者，永远保持挂起状态。）但为什么？为什么不让 Promise 在任何时候改变到任何状态呢？

主要是因为程序员* thrives *于二进制。我们确切地知道如何将 1 和 0 组合在一起，以执行惊人的逻辑壮举。这是 Promise 如此强大的一个重要原因：**Promise 让我们将并发任务视为布尔值。**

逻辑组合 Promise 的最常见用例是找出一组异步任务何时完成。假设你在从服务器加载游戏的同时播放教程视频。你希望在以下两件事发生后的任何顺序下立即开始游戏：

1. 教程视频已结束
2. 游戏已加载

给定代表这些过程的 Promise，你的任务是在两个 Promise 都完成时启动游戏。这就用到了 jQuery 的 `when` 方法：

```
var gameReadying = $.when(tutorialPromise, gameLoadedPromise);
gameReadying.done(startGame);
```

`when` 充当 Promise 完成的逻辑 AND：它生成的 Promise 在所有给定的 Promise 都完成时完成，或在任何一个给定的 Promise 被拒绝时被拒绝。`when` 的一个绝佳用例是组合多个 Ajax 调用。如果你需要同时进行两个 POST 调用，并在两者都成功时获得通知，无需为每个请求定义单独的回调：

```
$.when($.post('/1', data1), $.post('/2', data2))
    .then(onPosted, onFailure);
```

成功时，`when` 可以访问其每个组成 Promise 的回调参数，但这样做很棘手：它们以数组列表的形式传递，顺序与 Promise 传递给 `when` 的顺序相同。（修正一下：Promise 的回调参数只有在其发出多个值时才表示为数组，就像 `$.post` 那样。参见"传递非 Promise"的示例。）所以要获取传递给 `$.when` 的所有 Promise 的所有回调参数，我们需要这样开始：

```
$.when(promise1, promise2, promise3)
    .done(function(promise1args, promise2args, promise3args) {
        // ...
    });
```

解析数组列表是一场噩梦。除非必须，否则不要这样做。例如，如果你想从两个来源 GET 数据，直接将回调附加到各个 GET promise，而不是试图从 `when` 回调中处理所有事情：

```
var serverData = {};
var getting1 = $.get('/1')
    .done(function(result) {serverData[1] = result;});
var getting2 = $.get('/2')
    .done(function(result) {serverData[2] = result;});
$.when(getting1, getting2)
    .done(onServerDataLoaded);
```

### 传递非 Promise

`$.when` 和其他接受 Promise 的 jQuery 方法允许你传入非 Promise。这些被当作已在相应参数位置用给定值完成的 Promise 处理。例如，

```
$.when('foo')
```

会给你一个立即以值 `'foo'` 完成的 Promise；

```
$.when('test', [1, 2, 3])
```

将会返回一个立即解析的 Promise，其值为 `'test'` 和 `[1, 2, 3]`。（请记住，当 Deferred 向 `resolve` 传递多个参数时，这些参数会被 `$.when` 强制转换为数组。）

这就引出了一个问题：`$.when` 如何知道一个参数是否是 Promise 呢？原来，jQuery 只是检查是否存在 `promise` 方法，并使用该方法返回的值。Promise 的 `promise` 方法简单地返回自身。

正如你在关于动画 Promise 的章节中回忆起的，jQuery 对象也有一个 `promise` 方法，这意味着 `$.when` 将 jQuery 对象"强制"转换为它们的动画 Promise。所以，如果我们想要创建一个 Promise，使其在我们获取一些数据并且 `#loading` 动画完成时解析，我们只需写：

```
var fetching = $.get('/myData');
$.when(fetching, $('#loading'));
```

请记住，我们必须在启动动画*之后*执行此操作。如果 `#loading` 的动画队列为空，其 Promise 会立即解析。

### 其他逻辑运算

由于 `$.when` 是逻辑与，你可能会想：jQuery Promises 有逻辑或吗？那 NOT 呢？

答案是没有，不是开箱即用的。但我们可以很轻松地自己编写这些功能。先从 NOT 开始：

```
function not(promise) {
    var result = new $.Deferred();
    promise.done(result.reject);
    promise.fail(result.resolve);
    return result;
}
```

如果你曾经上过逻辑课，你就会知道 OR 可以用 AND 和 NOT 来定义，就像这样：

```
function or() {
    var promises = Array.prototype.slice.call(arguments);
    var negatedPromises = promises.map(not);
    return not($.when.apply(this, negatedPromises));
}
```

这里有一个简短的证明：

1. 当传递给 `or` 的 Promise 被解析时，其否定将被拒绝，`$.when` 返回的 Promise 也将被拒绝，因此 `or` 返回的 Promise 将立即被解析。

2. 当传递给 `and` 的所有 Promise 都被拒绝时，它们的否定都将被解析，`$.when` 返回的 Promise 也将被解析，因此 `or` 返回的 Promise 将被拒绝。

很酷吧？这些惯用法不像 `$.when` 那样广泛使用，但它们确实展示了将 Promises 作为布尔值来操作是多么容易。

## 3.7 使用 pipe 绑定到未来

在 JavaScript 中执行一系列异步任务往往不方便，部分原因是直到第一个任务完成之前，你无法为第二个任务附加处理程序。例如，让我们先从某个 URL GET 数据，然后将其 POST 到另一个 URL：

```
var getPromise = $.get('/query');
getPromise.done(function(data) {
  var postPromise = $.post('/search', data);
});

// 现在我们想要为 postPromise 附加处理程序...
```

你看到这里的问题了吗？在我们的 GET 操作完成之前，我们无法为 `postPromise` 绑定回调，因为它还不存在！它是由我们无法进行的 `$.post` 调用创建的，除非我们先异步地从 `$.get` 调用中获取数据。

这就是为什么 jQuery 1.6 为 Promises 添加了 `pipe` 方法。本质上，`pipe` 的意思是："给我一个此 Promise 的回调，我将给你一个代表该回调结果的 Promise。"

```
var getPromise = $.get('/query');
var postPromise = getPromise.pipe(function(data) {
  return $.post('/search', data);
});
```

看起来像黑魔法吧？以下是详细解析：`pipe` 接受与 `then` 相同的三个参数，每种回调类型各一个：`done`、`fail` 和 `progress`。所以在这个例子中，我们只提供了一个在 `getPromise` 解析时运行的回调。`pipe` 方法返回一个新的 Promise，该 Promise 在我们回调返回的 Promise 解析/拒绝时被解析/拒绝。实际上，`pipe` 是一扇通往未来的窗口。

你也可以使用 `pipe` 来"过滤" Promise，通过修改回调参数实现。如果 `pipe` 回调返回的是非 Promise/Deferred 的内容，那么该值将成为回调参数。例如，如果你有一个发出介于 0 和 1 之间数字的进度通知的 Promise，你可以使用 `pipe` 创建一个相同的 Promise，但发出人类可读的字符串作为进度通知：

```
var promise2 = promise1.pipe(null, null, function(progress) {
  return Math.floor(progress * 100) + '% complete';
});
```

总结一下，从 `pipe` 回调中可以执行两种操作：

1. 如果你返回一个 Promise，`pipe` 返回的 Promise 将模仿它。

2. 如果你返回一个非 Promise 值（或什么都不返回），`pipe` 返回的 Promise 将立即被解析、拒绝或通知该值，具体取决于原始 Promise 刚刚发生了什么。

`pipe` 判断某物是否为 Promise 的规则与 `$.when` 相同：如果它有 `promise` 方法，该方法的返回值将被用作代表原始对象的 Promise。同样，`promise.promise() === promise`。

### Pipe 级联

`pipe` 不要求你提供所有可能的回调。事实上，通常你只想写：

```
var pipedPromise = originalPromise.pipe(successCallback);
```

或

```
var pipedPromise = originalPromise.pipe(null, failCallback);
```

我们已经看到了在第一种情况下原始 Promise 成功时会发生什么，或者在第二种情况下原始 Promise 失败时会发生什么，这样 piped Promise 的行为取决于 `successCallback` 或 `failCallback` 的返回值。但如果我们在原始 Promise 执行时没有给 `pipe` 提供回调呢？

很简单：在这些情况下，piped promise 会模仿原始 Promise。我们可以说原始 Promise 的行为通过 piped Promise 级联传递。这种级联非常方便，因为它允许我们以最小的努力为异步任务定义分支逻辑。假设我们有一个三步流程：

```
var step1 = $.post('/step1', data1);
var step2 = step1.pipe(function() {
  return $.post('/step2', data2);
});
var lastStep = step2.pipe(function() {
  return $.post('/step3', data3);
});
```

这里，`lastStep` 只有在所有三个 Ajax 调用都成功时才会解析，并且如果*任何*一个失败，它将被拒绝。如果我们只关心整个流程，可以省略前面步骤的变量声明：

```
var posting = $.post('/step1', data1)
  .pipe(function() {
    return $.post('/step2', data2);
  })
  .pipe(function() {
    return $.post('/step3', data3);
  });
```

等价地，我们可以将第二个 `pipe` 嵌套在另一个里面：

```
var posting = $.post('/step1', data1)
  .pipe(function() {
    return $.post('/step2', data2)
      .pipe(function() {
        return $.post('/step3', data3);
      });
  });
```

当然，这又回到了"末日金字塔"。你应该了解这种风格，但作为一般规则，尝试单独声明你的 piped Promises。变量名可能不是必需的，但它们使代码更具自文档性。

这就结束了我们对 jQuery Promises 的 tour。现在让我们快速看一下主要的替代方案：CommonJS Promises/A 规范及其旗舰实现 Q.js。

## 3.8 jQuery 与 Promises/A 的比较

就功能而言，jQuery Promises 和 Promises/A 基本上是等效的。它们可以相互映射。关键的差异是表面的：它们使用相同的词来表示不同的含义。

最明显的区别是，像 Q.js 这样的忠实 Promises/A 实现中的 `then` 方法返回一个*新的* Promise，代表成功/失败处理程序的返回值。这很像 jQuery 的 `pipe` 方法。

另一个很大的区别，前面提到过，是 jQuery 使用术语 "resolve" 作为 "fail" 的反义词，而 Promises/A 使用 "fulfill"。在 Promises/A 中，当 Promise 被 fulfill 或 fail 时，称为 "resolved"。

还有其他更细微的差异。例如：在 Promises/A 中，从 `then` 返回的 Promise 是被 fulfill 还是 reject，取决于被调用的回调是返回一个值还是抛出错误。（从 jQuery Promise 回调中抛出错误是个坏主意，因为它们将不会被捕获。）

由于这些问题，你应该避免在同一个项目中与多个 Promise 实现交互。如果你只是从 jQuery 方法获取 Promises，就使用 jQuery Promises。如果你使用的另一个库给你 CommonJS Promises，就采用 Promises/A。如果你两者都用，Q.js 可以很容易地"同化" jQuery Promises：

```
var qPromise = Q.when(jqPromise);
```

只要这两个标准保持分歧，这就是让它们友好协作的最佳方式。更多信息，请参阅 Q.js 文档⁵。

## 3.9 用 Promises 替换回调

当我们与普通的异步函数交互时，我们可以通过将 Deferred 的 `resolve` 方法作为回调传递，用 Promise 来表示其完成：

```
var timing = new $.Deferred();
setTimeout(timing.resolve, 500);
```

当一个 API 同时接受成功和失败回调时，我们可以将 `resolve` 和 `reject` 作为这些回调传递。当一个 API 遵循将错误作为回调第一个参数传递的 Node 约定时，我们可以根据该参数是否存在来调用 `resolve` 或 `reject`。例如：

```
var fileReading = new $.Deferred();
fs.readFile(filename, 'utf8', function(err) {
  if (err) {
    fileReading.reject(err);
  } else {
    fileReading.resolve(Array.prototype.slice.call(arguments, 1));
  }
});
```

（是的，你可以在 Node 中使用 jQuery。只需 `npm install jquery` 并像任何其他模块一样使用它。或者你可以使用 Q.js 或 Futures，如前所述。）

每次都这样写会很麻烦，所以为什么不创建一个工具函数，从任何给定的 Deferred 生成一个 Node 风格的回调呢？

```
deferredCallback = function(deferred) {
  return function(err) {
    if (err) {
      deferred.reject(err);
    } else {
      deferred.resolve(Array.prototype.slice.call(arguments, 1));
    };
  };
}
```

有了这个，我们可以将上面的示例改写为：

```
var fileReading = new $.Deferred();
fs.readFile(filename, 'utf8', deferredCallback(fileReading));
```

在 Q.js 中，Deferred 开箱即带有用于此目的的 `node` 方法：

```
var fileReading = Q.defer();
fs.readFile(filename, 'utf8', fileReading.node());
```

在我看来，Promise 是多年来添加到 jQuery 中最令人兴奋的功能之一。它们不仅极大地帮助理顺了典型富 Ajax 应用中特征性的回调“意大利面条”，而且使得协调各种异步任务变得容易得多。

使用 Promise 需要一些练习，特别是使用 `pipe`（或 CommonJS 的 `then`）时，但这是非常值得养成的习惯。你将窥见 JavaScript 的未来。

# 4 使用 Async.js 进行流控制

在 npm 注册表ⁱ中搜索 "flow"，会涌现出大量令人目不暇接的流控制库。因为 JavaScript 函数可以自由传递，所以有无数种可能性来清除嵌套异步函数造成的混乱。这些库中的每一个都规定了特定的约定，只要遵循这些约定，就能编写出极其清晰的代码。

这些库中最流行的是 Caolan McMahon 的 Async.js。² 事实上，在撰写本文时，Async.js 是 npm 注册表中第六个最被需要的库，与 Underscore.js、CoffeeScript 和 Express 等明星库共享光芒。Async.js 不仅仅是为 Node 而生；它在浏览器中也运行得很好！（是的，甚至包括 IE6。）

在本章的大部分示例中，我们将使用 Node.js。如果你的系统上已经安装了 Node 和 npm，你可以通过以下命令安装 Async.js：

```
npm install -g async
```

然后在任何文件顶部放入 `async = require('async')` 即可引入该模块。

## 4.1 异步排序问题

假设我们有一个 Node 应用，希望按字母顺序读取目录中的所有文件，然后将它们的内容连接成一个字符串并显示出来。使用同步方法，我们可以非常容易地做到这一点：

```
var fs = require('fs');
var concatenation = '';

fs.readdirSync('recipes')
  .filter(function(filename) {
    return fs.statSync(filename).isFile();
  })
  .forEach(function(filename) {
    concatenation += fs.readFileSync(filename, 'utf8');
  });

console.log(concatenation);
```

（通过使用 `forEach` 迭代器而不是 `for` 循环，我们避免了第 1 章中看到的 `i` 变量作用域问题。但要注意，如果没有 polyfill，`forEach` 在旧版浏览器中不可用。）

但所有这些阻塞都极其低效，特别是如果我们的应用程序可以同时做其他事情的话。问题在于，我们不能天真地将

```
concatenation += fs.readFileSync(filename, 'utf8');
```

替换为

```
fs.readFile(filename, 'utf8', function(err, contents) {
  if (err) throw err;
  concatenation += contents;
});
```

因为无法保证 `readFile` 回调会按照 `readFile` 调用发出的顺序触发。`readFile` 只是告诉操作系统**开始**读取一个文件。很可能，较短的文件比较长的文件读取得更快。

## 4.2 Async.js 集合方法

解决异步排序问题最简单的方法是，在上一个 `readFile` 完成后才开始下一个：

```
var fs = require('fs');
var concatenation = '';
var dirContents = fs.readdirSync('recipes');

function readFileAt(i) {
  if (i === dirContents.length) return console.log(concatenation);
  fs.stat(filename, function(err, stats) {
    if (err) throw err;
    if (!stats.isFile()) return readFileAt(i + 1);
    fs.readFile(dirContents[i], 'utf8', function(err, fileContents) {
      if (err) throw err;
      concatenation += fileContents;
      readFileAt(i + 1);
    });
  });
}

readFileAt(0);
```

你可能已经注意到，这不是一个非常优雅的解决方案。对于如此简单的任务，涉及了太多样板代码。当我们使用同步的 `filter` 和 `forEach` 方法时，这只花了 10 行！如果我们能直接使用那些强大的迭代方法的异步等效物，岂不是很好？

这正是 Async.js 提供给我们的功能之一（还有其他功能）。事实上，我们有两个选择来替代 `Array` 原型的 `filter` 和 `forEach` 方法：

1.  `async.filter` 和 `async.forEach`，它们*并行*处理给定的数组，或者
2.  `async.filterSeries` 和 `async.forEachSeries`，它们*按顺序*处理给定的数组

显然，并行运行异步操作更快，那为什么我们要使用串行方法呢？嗯，有两个原因：

首先，Node（或任何应用程序进程）同时尝试读取的文件数量是有限的。如果达到这个限制，操作系统会给我们一个错误，我们必须在 `fs.readFile` 回调中处理。如果我们按顺序读取文件，就不必处理这个限制。

其次，如果我们并行运行 `readFile` 回调，我们就不能简单地写：

```
concatenation += fileContents;
```

因为无法保证 `readFile` 操作会按照它们开始的顺序完成。我们必须想办法存储结果，并按正确的顺序连接它们。

所以，我们现在坚持使用 `async.forEachSeries`。这是将我们的同步代码改编为使用 Async.js 集合方法的一个简单示例：

```
var async = require('async');
var fs = require('fs');
var concatenation = '';
var dirContents = fs.readdirSync('recipes');

async.filter(dirContents, isFilename, function(filenames) {
  async.forEachSeries(filenames, readAndConcat, onComplete);
});

function onComplete(err) {
  if (err) throw err;
  console.log(concatenation);
}

function isFilename(filename, callback) {
  fs.stat(filename, function(err, stats) {
    callback(err ? false : stats.isFile());
  });
}

function readAndConcat(filename, callback) {
  fs.readFile(filename, 'utf8', function(err, fileContents) {
    if (err) return callback(err);
    concatenation += fileContents;
    callback();
  });
}
```

现在我们的代码很好地分成了两部分：整体任务和实现细节（以迭代器函数的形式）。

`filter` 和 `forEach` 并不是 Async.js 中唯一对应 `Array` 原型方法的实用工具。还有：

-   `reject`/`rejectSeries`，`filter` 的逆操作
-   `map`/`mapSeries`，用于一对一转换
-   `reduce` 和 `reduceRight`，用于在每一步转换一个值
-   `detect`/`detectSeries`，用于查找匹配过滤器的值
-   `sortBy`，用于生成排序后的副本
-   `some` 用于测试是否至少有一个值匹配给定条件
-   `every` 用于测试是否*所有*值都匹配给定条件

在我们的文件读取示例中，我们可以采用更简洁的函数式风格，使用 `async.reduce`，让 Async.js 为我们存储连接结果：

```
var async = require('async');
var fs = require('fs');
var dirContents = fs.readdirSync('recipes');

async.filter(dirContents, isFilename, function(filenames) {
  async.reduce(filenames, '', readReduce, onComplete);
});

function onComplete(err, concatenation) {
  if (err) throw err;
  console.log(concatenation);
}

function isFilename(filename, callback) {
  fs.stat(filename, function(err, stats) {
    callback(err ? false : stats.isFile());
  });
}

function readReduce(concatenation, filename, callback) {
  fs.readFile(filename, 'utf8', function(err, fileContents) {
    if (err) callback(err);
    callback(null, concatenation + fileContents);
  });
}
```

`readReduce` 在第一个回调参数中使用 `null` 是什么意思，为什么在没有错误时传递 `null`？请参见下一节。

### Async.js 中的错误处理

注意，我们提供给 `async.filter` 的迭代器 `isFilename` 将布尔值作为第一个参数传递给它的回调。相比之下，`readAndConcat` 将错误作为第一个参数传递给回调。为什么？

Async.js 使用 Node 风格的回调：第一个回调参数是错误。**产生布尔值的方法的回调是这条规则的例外。** 这意味着集合方法（`filter`、`reject`、`detect`、`some` 和 `every`）的迭代器无法报告错误。这要怪 Node 的 `path.exists` 开了这个先例，而 Async.js 忠实地遵循了这一惯例。

当一个普通迭代器将 `null` 或 `undefined` 以外的值作为第一个参数传递给回调时，Async 会立即调用完成回调并传入该错误。因此，在上面的代码中，如果 `fs.readFile` 在回调中收到错误，它会将其传递给 `readAndConcat` 回调，这会短路 `async.forEachSeries`，导致错误立即从我们的 `onComplete` 函数中抛出。

## 4.3 链式调用异步函数

Async.js 的集合方法解决了将单个异步函数应用于数据序列的问题。但如果我们要处理的不是数据序列，而是一系列*函数*呢？

这就是 `async.series` 和 `async.waterfall` 的用武之地。每个方法都接受一个函数数组（*任务列表*）并按顺序执行它们，同时传入一个 Node 风格的回调。两者的区别在于，`async.series` 仅向每个任务提供回调，而 `async.waterfall` 还会提供前一个任务的结果。（这里的"结果"指的是每个任务传递给回调的非错误值。）

让我们看一个使用超时的简单示例：

```
var async = require('async');
var start = new Date();

async.series([
  function(callback) { setTimeout(callback, 100); },
  function(callback) { setTimeout(callback, 300); },
  function(callback) { setTimeout(callback, 200); }
], function(err, results) {
  console.log('Completed in ' + (new Date() - start) + 'ms');
});
```

（在这个示例中，将 `async.waterfall` 替换为 `async.series` 不会产生任何影响，因为每个任务的回调都是在没有参数的情况下运行的。）

完成处理器将在 600 多毫秒后运行，因为数组中的每个任务按顺序依次完成。Async.js 注入到每个任务函数中的回调只是询问："是否有错误（第一个参数）？如果没有，那么我将收集结果（第二个参数）并运行下一个任务。"

作为练习，让我们使用 `map` 将文件名数组转换为异步任务函数数组，来重写我们的顺序文件读取代码：

```
var async = require('async');
var fs = require('fs');
var concatenation = '';

var fileTasks = fs.readdirSync('recipes')
  .filter(function(filename) {
    return fs.statSync(filename).isFile();
  })
  .map(function (filename, i) {
    return function(callback) {
      fs.readFile(filename, 'utf8', callback);
    };
  });

async.series(fileTasks, function(err, results) {
  if (err) throw err;
  console.log(concatenation = results.join(''));
});
```

注意，我们可以方便地将任务回调直接提供给 `fs.readFile`，因为它使用了常规的 Node 回调签名：`(err, result)`。如果我们的任何 `readFile` 尝试确实导致了错误，`series` 将会终止，并且完成处理器会立即被调用并传入该错误。

## 4.4 并行化异步函数

假设我们想一次性读取所有文件（暂时忽略文件系统的限制）。如果不使用 Async.js，我们可能会尝试将读取状态存储在一个数组中，如下所示：

```
var fs = require('fs');
var dirContents = [];

fs.readdirSync('recipes')
  .filter(function(filename) {
    return fs.statSync(filename).isFile();
  })
  .forEach(function(filename, i) {
    fs.readFile(filename, 'utf8', function(err, fileContents) {
      if (err) throw err;
      dirContents[i] = fileContents;
    });
  });
```

只有一件事缺失了：我们想把这行代码

```
var concatenation = dirContents.join('');
```

放在某个地方……但是放在*哪里*呢？它必须在一个完成处理器中运行，而该处理器需要在最后一个 `fs.readFile` 操作完成后触发。注意——这里的"最后"指的是"最后一个完成的"，不一定是 `i` 值最大的那个。因此我们需要跟踪待处理的 `readFile` 回调数量，然后在该数量达到 0 时触发另一个回调。这就是所谓的*异步队列*模式。

Async.js 使用诸如 `async.forEach` 和 `async.map` 之类的集合方法为我们完成了所有这些工作，它们的 API 与我们之前使用的顺序版本相同。但还有一个更通用的方法可以使用，那就是 `async.parallel`。与 `async.series` 一样，它接受一个形式为 `function(callback) {...}` 的函数数组，以及一个（可选的）完成处理器。让我们重复之前的超时示例：

```
var async = require('async');
var start = new Date();

async.parallel([
  function(callback) { setTimeout(callback, 100); },
  function(callback) { setTimeout(callback, 300); },
  function(callback) { setTimeout(callback, 200); }
], function(err, results) {
  console.log('Completed in ' + (new Date() - start) + 'ms');
});
```

`async.series` 需要超时时间之和（约 600ms）才能完成，而 `async.parallel` 只需要最长的超时时间（约 300ms）。

方便的是，Async.js 将结果按照任务数组对应的顺序传递给完成处理器，而不是按照结果生成的顺序。这意味着我们可以用与顺序版本完全相同的方式编写同时读取文件的代码——只需将 `async.series` 替换为 `async.parallel`：

```
var async = require('async');
var fs = require('fs');
var concatenation = '';

var fileTasks = fs.readdirSync('recipes')
  .filter(function(filename) {
    return fs.statSync(filename).isFile();
  })
  .map(function (filename, i) {
    return function(callback) {
      fs.readFile(filename, 'utf8', callback);
    };
  });

async.parallel(fileTasks, function(err, results) {
  if (err) throw err;
  console.log(concatenation = results.join(''));
});
```

### 全部同时执行，还是一次一个？

`async.series` 和 `async.parallel` 为两种常见的异步模式提供了简单、统一的接口。但它们也有局限性：

1. 任务数组是静态的。一旦调用了 `async.series` 或 `async.parallel`，就无法添加或删除任务。
2. 也无法查询"已经完成了多少个任务？"它是一个黑盒，除非你从任务本身发送更新。
3. 你要么完全没有并发，要么是无限并发。

最后一点在文件读取方面是一个相当大的问题。如果一个目录中有数千个文件，我们不想通过串行执行而变得低效，但如果尝试并行读取所有文件，很可能会激怒操作系统。我们可以将任务数组分成块，然后依次并行执行每个块……但这并不太优雅。

值得庆幸的是，Async.js 提供了一个方法来解决所有这些问题：`async.queue`。

## 4.5 动态异步队列

`async.queue` 的基本概念类似于 DMV（机动车辆管理局）：他们可以同时处理多个人（最多为值班职员的数量），但不是为每个职员设置单独的队伍，而是只有一个号码牌堆。当你到达时，你会拿到一个号码。当一个职员空闲时，他们叫下一个号码。这是一个非常高效的系统——非常适合我们的文件读取示例。

`async.queue` 的接口比 `async.series` 和 `async.parallel` 更复杂一些。它接受一个称为 *worker* 的函数（而不是函数数组）和一个 *concurrency* 值（worker 可以同时处理的最大任务数）。然后返回一个队列，我们可以向其中 `push` 任意任务数据（以及一个可选的回调）。

下面是一个简单的示例：

```
var async = require('async');

function worker(data, callback) {
  console.log(data);
  callback()
}

var concurrency = 2;
var queue = async.queue(worker, concurrency);

queue.push(1);
queue.push(2);
queue.push(3);
```

无论并发数是多少（只要至少为 1），我们都会得到输出

```
1
2
3
```

不过底层是有区别的：并发数为 2 时，我们需要两次事件循环。如果并发数为 1，我们需要三次事件循环，每次处理一行。如果并发数为 3 或更多，我们只需要一次事件循环。

并发数为 0 的队列将不会执行任何操作。如果你想获得最大并发数，只需使用 `Infinity`。

### 推送任务

虽然 `queue.push` 与 `[].push` 名称相同，但有两个关键区别：

首先，

```
queue.push([1, 2, 3]);
```

等同于

```
queue.push(1);
queue.push(2);
queue.push(3);
```

这意味着你不能直接将数组用作任务数据。然而，你可以使用其他任何内容——甚至函数。事实上，如果你想使用一个函数数组，就像在 `async.series` 或 `async.parallel` 中那样，你只需要定义一个 worker，将其第二个参数传递给第一个参数：

```
function worker(task, callback) {
  task(callback);
}
var concurrency = 2;
var queue = async.queue(worker, concurrency);
queue.push(tasks);
```

其次，你可以随每次 push 提供一个回调函数；如果你提供了，它将被直接作为 callback 参数传递给 worker 函数。例如，

```
queue.push([1, 2, 3], function(err, result) {
  console.log('Task complete!');
});
```

（假设 worker 运行了它的回调）将输出 "Task complete!" 三次。push 回调非常宝贵，因为与 `async.series`/`async.parallel` 不同，`async.queue` 不会在内部存储结果。如果你想要结果，就必须自己捕获它们。

### 当任务全部完成时

与 `async.series` 和 `async.parallel` 类似，`async.queue` 的强大之处很大程度上在于它能够添加一个完成处理程序。这个处理程序被称为 `drain`。（想象一个装满任务的水槽；当最后一个任务流走时，回调就会触发。）这里有一个使用定时器的演示：

```
var async = require('async');

function worker(data, callback) {
  setTimeout(callback, data);
}
var concurrency = 2;
var queue = async.queue(worker, concurrency);
var start = new Date();
queue.drain = function() {
  console.log('Completed in ' + (new Date() - start) + 'ms');
};

queue.push([100, 300, 200]);
```

回顾一下，`async.series` 处理这些超时需要大约 600ms（总和），而 `async.parallel` 只需要大约 300ms（最大值）。这里，并发数是 2，所以最初，前两个超时将并行运行。但是当 100ms 的超时完成后，队列中的下一个任务（200ms 的超时）将立即开始。因此，在这种情况下，`async.queue` 的完成时间与 `async.parallel` 大致相同。顺序很重要：如果 300ms 是第三个超时，队列将需要大约 400ms 来完成。

请注意，我们始终可以向队列推送更多任务，并且每次队列中的最后一个任务完成时，`drain` 都会触发。它不像 `async.series` 和 `async.parallel` 那样是一次性的，后两者的任务列表是固定的。

让我们用 `async.queue` 重写我们的文件读取示例，并设定合理的并发上限：

```
var async = require('async');
var fs = require('fs');

var concatenation = '';
var filenames = fs.readdirSync('recipes')
  .filter(function(filename) {
    return fs.statSync(filename).isFile();
  });

var results = [];
function worker(i, callback) {
  fs.readFile(filenames[i], 'utf8', function(err, result) {
    if (err) throw err;
    results[i] = result;
    callback();
  });
}
var concurrency = 10;
var queue = async.queue(worker, concurrency);
for (var i = 0; i < filenames.length; i++) {
  queue.push(i);
}
queue.drain = function() {
  console.log(concatenation = results.join(' '));
};
```

在这里，`async.queue` 扮演着交通警察的角色，确保我们每次最多只读取 10 个文件。不幸的是，它并不能确保 push 回调按特定顺序被调用，迫使我们笨拙地管理自己的结果数组。

### 高级队列回调

尽管 `drain` 通常是你唯一需要的处理程序，但 `async.queue` 还提供了几个其他事件：

-   当最后一个任务开始运行时，队列会调用 `empty`。（当任务完成时，它会调用 `drain`。）

-   当达到并发限制时，队列会调用 `saturated`。

-   如果你在 push 中提供一个函数作为第二个参数，它将在给定任务（或给定数组中的每个任务）完成时被调用。

简而言之，`async.queue` 是 Async.js 中功能最齐全的函数之一，是用于限制并发性的通用阀门。

## 4.6 自动化

尽管 `async.queue` 功能强大，但有些情况它无法处理。考虑一个复杂应用程序的启动过程。该过程的一小部分可能如下所示：

1.  读取配置文件

2.  连接到配置文件指定的数据库

3.  连接到配置文件指定的缓存

4.  将数据库中最常用的对象加载到缓存中

5.  连接到外部 API

6.  开始响应 HTTP 请求

在这里，任务 2 和 3 都依赖于任务 1，任务 4 依赖于任务 2 和 3，任务 6 依赖于任务 2、3 和 5。你可以按线性顺序执行这些任务，但这会不必要地拖慢服务器的启动速度。我们希望的是在每个任务的依赖项完成后立即运行该任务。

为此，我们可以为每个任务编写一个 Promise，然后用 `when` 和 `then` 自己处理逻辑……或者，我们可以让一个算法为我们解决这个问题。毕竟，任何依赖关系集都可以转换为有向图，而解决数学问题正是计算机的专长！在第二次世界大战期间，计算机计算炸弹的轨迹。如今，它们计算愤怒的小鸟的轨迹。我的意思是，依赖图对机器来说是小菜一碟。

`async.auto` 让我们以单个对象的形式描述一个依赖图，其中键是任务名称，值是以下形式的数组：

```
[dependencies..., task]
```

其中 `dependencies` 是任务名称列表，`task` 是函数本身。如果一个任务没有依赖项，我们可以直接写

```
task
```

而不是

```
[task]
```

以下是我们如何实现服务器的启动过程，假设我们已经定义了各个组成部分的任务：

```
async.auto({
  readConfigFile: readConfigFile,
  connectToDB:    ['readConfigFile', connectToDB],
  connectToCache: ['readConfigFile', connectToCache],
  cacheObjects:   ['connectToDB', 'connectToCache', cacheObjects],
  connectToAPI:   connectToAPI,
  acceptHTTPReqs: ['connectToDB', 'connectToCache', 'connectToAPI',
                   acceptHTTPReqs]
});
```

（按照惯例，我将函数名用作依赖图的键。`async.auto` 本身并不关心函数叫什么名字。）

尽管 `auto` 没有被广泛使用，但它是一个极其强大的函数，你应该有所了解。在一个复杂的应用程序中，它可能真的是救星。

这就是我们对 Async.js 的介绍，它是使用最广泛且可以说功能最丰富的流程控制库。然而，我不想让你产生 Async.js 是每个回调驱动工作的正确工具的印象。让我们通过看几个替代方案来结束本章。

## 4.7 使用 Step 进行极简主义流程控制

最著名的 Async.js 替代方案是 Tim Caswell 的 Step。² Step 比 Async.js 轻量得多，其 API 仅包含一个函数：`Step`。`Step` 接受一个函数列表，例如

```
Step(task1, task2, task3);
```

每个函数可以通过三种方式控制流程：

1.  它可以调用 `this`，让 Step 运行列表中的下一个函数。

2.  它可以调用 `this.parallel` 或 `this.group` 生成的回调 *n* 次，告诉 Step 运行下一个函数 *n* 次。

3.  它可以返回一个值，这也会让 Step 运行列表中的下一个函数。这使得将同步函数与异步函数混合使用变得容易。

下一个函数将接收其前驱的结果（即其返回值或它传递给 `this` 的参数），或者如果前驱是使用 `this.parallel` 或 `this.group` 运行的，则接收其所有实例的结果。（区别在于，`this.parallel` 将这些结果作为单独的参数提供，而 `this.group` 将它们合并为数组。）

截至本文撰写时，整个库只有 152 行代码（包含注释），但功能足够强大，可以处理大多数异步流。这种极简主义的缺点是，用 Step 创建的流只能通过阅读其中的每个函数来理解。使用功能包罗万象的 Async.js 创建的流往往更具自解释性。

这是一个很好的折衷方案：无论你需要 Async.js 的什么功能，尝试用 Step 自己编写它。例如，以下是等效的 `async.map`，只有 11 行：

```
var Step = require('step');

function stepMap(arr, iterator, callback) {
  Step(
    function() {
      var group = this.group();
      for (var i = 0; i < arr.length; i++) {
        iterator(arr[i], group());
      };
    },
    callback
  );
}
```

## 4.8 其他流程控制库

在结束本章之前，让我提几个我们可以学习的有趣流程控制库。

### Futures

在第3章中曾提及，AJ O'Neal 的 Futures 库兼具多种功能：它部分属于流程控制，部分实现了 Promise，部分采用了发布-订阅模式。⁴ 它是满足你所有异步需求的一站式解决方案。不幸的是，这种广泛的功能导致其 API 复杂得令人筋疲力尽。

### nue

说到复杂度，Toshihiro Nakamura 的 nue⁵ 库就像是 Step 库的“超大号兄弟”。Step 只允许流程按线性顺序运行（步骤内部可并行），而 nue 则允许你创建子流程、通过附加到共享对象来共享数据、为流程和步骤命名以方便调试，并且基本上能做任何你能想到的事情。它功能强大到令人眼花缭乱，但也令人钦佩。

在本章中，我们看到了如何使用合适的流程控制函数，以最少的样板代码实现常见的异步模式。我们也看到了流程控制的最大问题：对于每一个问题，都有数量惊人的解决方案可供选择。

npm 的创建者、近期被任命为 Node.js 项目负责人的 Isaac Schlueter，制作了一个非常小的流程控制库，叫做 Slide。⁶ 在其 README 中，他写道：

> 你应该将它作为编写自己的流程控制工具的示例。你永远不会完全欣赏一个不是你自己编写的流程控制库。

我希望这不是真的。编写一个流程控制库是很好的练习，但你不应该为了了解其工作原理而不得不重复造轮子。随着 JavaScript 生态系统的成熟，流程控制应该会变得更加普及和标准化。我的预测是，将出现一个库，它对于流程控制的意义，就如同 jQuery 对于 DOM 交互，或 Underscore.js 对于（同步）函数式风格编程的意义一样。当那一天到来时，将是 JavaScript 的伟大日子。

# 5 使用 Workers 实现多线程

在本书的开头，我将事件描述为多线程的一种替代方案。更准确地说，事件取代了一种特定类型的多线程——即应用程序的多个部分同时运行（无论是通过中断实现的虚拟并行，还是在多个 CPU 核心上的物理并行）。当运行在不同线程中的代码访问相同的数据时，这就会成为问题。即使像下面这样简单的一行代码

```
i++;
```

当它允许多个线程同时修改同一个 `i` 时，也可能成为难以捉摸的 Heisenbugs（海森堡漏洞）的根源。值得庆幸的是，这种多线程在 JavaScript 中是不可能发生的。

另一方面，将任务分配到多个 CPU 核心上变得越来越重要，因为这些核心不再像我们过去所期望的那样，年复一年地实现效率的指数级增长。所以我们*需要*多线程。这是否意味着要放弃事件？

*恰恰相反！* 虽然运行在单线程上并不理想，但天真地将应用程序分布到多个核心上可能更糟。当多核系统中的核心必须不断地相互通信以避免彼此冲突时，系统会变得极其缓慢。更好的方法是给每个核心分配一个独立的任务，然后偶尔进行同步。

这正是 JavaScript 中 Workers 所做的事情。从应用程序的主线程，你可以告诉一个 Worker：“去在一个单独的线程中运行这段代码。” Worker 可以向你发送消息（反之亦然），这些消息以（还能是什么？）从事件队列运行的回调形式呈现。简而言之，你与不同线程交互的方式，与你在 JavaScript 中进行 I/O 操作的方式相同。

在本章中，我们将探讨 Workers 在浏览器和 Node.js 中的实现，并讨论一些实际应用。

## 5.1 Web Workers

Web Workers 是被称为 HTML5 的现行标准的一部分。要创建一个 Worker，你需要使用脚本的 URL 调用全局的 `Worker` 构造函数：

```
var worker = new Worker('kimptoc.js');
worker.addEventListener('error', function() {
    console.log('Chris Kimpton failed to load.');
});
```

> (**警告：** 作为安全措施，传递给 Worker 的 URL 必须与页面具有相同的源（协议、主机和端口）。)

现在，*kimptoc.js* 将被异步获取，并且假设脚本加载成功，它将在另一个线程中开始运行。恭喜：我们有了一个 Web Worker！

更具体地说，我们拥有一个*专用*（dedicated）Web Worker，它只能与创建它的浏览器进程通信。也可以创建*共享*（shared）Web Worker，用于协调多个浏览器标签页；然而，这些支持较少，因此我们不会在本章中介绍它们。

### 与 Web Workers 通信

除了 `'error'` 事件（当 Worker 脚本加载失败或脚本抛出异常时触发），Workers 还可以触发 `'message'` 事件，其中包含从 Worker 的 `self.postMessage` 函数发送的任意字符串或 JSON 可序列化对象：

```
var worker = new Worker('worker.js');
worker.addEventListener('message', function(e) {
  console.log(e.data);  // 回显通过 postMessage 发送的所有内容
});
```

（通常，我们只需要消息事件中的 `data` 属性。如果我们要将同一个事件处理器绑定到多个 Workers，我们可以使用 `e.target` 来确定是哪个 Worker 触发了该事件。）

所以，现在我们知道如何监听 Workers 了。方便的是，与 Workers 通信的接口是对称的：我们使用 `worker.postMessage` 向它发送消息，Worker 使用 `self.addEventListener('message', ...)` 来接收消息。这是一个完整的示例：

```
// 主脚本
var worker = new Worker('boknows.js');
worker.addEventListener('message', function(e) {
  console.log(e.data);
});
worker.postMessage('football');
worker.postMessage('baseball');

// boknows.js
self.addEventListener('message', function(e) {
  self.postMessage('Bo knows ' + e.data);
});
```

你可以在一个我创建的小网站 Web Worker Sandbox 上体验这个消息传递接口。¹ 每当你创建一个新示例时，它都会获得一个你可以分享的唯一 URL。

¹http://webworkersandbox.com/

### Web Workers 的限制

Web Workers 主要用于处理复杂计算，同时不影响 DOM 的响应能力。潜在用途包括：

- 使用 CoffeePhysics² 为游戏执行物理计算。

- 使用 H.264 编解码器的 Broadway 实现³在视频流式传输时进行解码。

- 使用 Stanford JavaScript Crypto Library⁴进行通信加密。

通常，Worker 会将其计算结果发送给主线程，由主线程更新页面。为什么不直接更新页面？主要是为了保持 JavaScript 异步抽象的完整性。如果一个 Worker 可以修改页面的标记，我们最终会陷入与 Java 相同的境地——需要用互斥锁和信号量来包装我们的 DOM 操作代码，以避免竞态条件。

同样，Worker 无法看到全局的 `window` 对象，或主线程（或其他 Worker 线程）中的任何其他对象。当对象通过 `postMessage` 发送时，它会被透明地序列化和反序列化（可以理解为 `JSON.parse(JSON.stringify(obj))`）。因此，对原始对象的更改不会影响另一个线程中的副本。

即使是可靠的 `console` 对 Worker 也不可用。Worker *只能*看到它自己的全局对象 `self`，以及随之捆绑的所有内容：标准的 JavaScript 对象如 `setTimeout` 和 `Math`，以及浏览器的 Ajax 方法。

啊，是的，Ajax！Worker 可以自由使用 `XMLHttpRequest`。如果浏览器支持，它甚至可以使用 `WebSocket`。从效率的角度来看，仅仅将 Ajax 功能从主脚本移到 Worker 中获益甚微，但这确实意味着 Worker 可以直接从服务器拉取数据。并且如果我们处理大量数据（如流式视频示例），将其保留在一个线程中而不是通过 `postMessage` 序列化，是一个巨大的优势。

还有一个特殊的 `importScripts` 函数，它会（同步地）加载并运行给定的脚本：

```
importScripts('https://raw.github.com/gist/1962739/danika.js');
```

通常，同步加载是一个大忌，但请记住我们这里是在辅助线程中。只要 Worker 没有其他事情要做，阻塞就完全没问题。

### 哪些浏览器支持 Web Workers？

Web Worker 标准已经在 Chrome、Firefox 和 Safari 中实现了数年，并且即将在 IE10 中推出。移动端的支持也不稳定：最新的 iOS Safari 支持它们，但最新的 Android 浏览器不支持。截至本文撰写时，根据 caniuse.com 的数据，浏览器支持率为 55.4%。

简而言之，大多数网站还不能依赖 Web Worker 支持。不过，你可以轻松地编写一个 shim，在 `window.Worker` 不可用时正常运行目标脚本。毕竟，Web Workers 只是一种性能增强手段。

务必在多个浏览器中测试 Web Workers。由于规范尚未最终确定，不同实现之间存在一些关键差异。例如，Firefox 允许 Worker 生成自己的"子 Worker"，但 Chrome 目前不支持。

### 现实世界中的 Web Workers

由于支持相对有限，而且在浏览器中进行复杂计算的需求也不常见，Web Workers 的使用并不广泛。一个使用它们的项目是 Ace 代码编辑器（以前称为 Bespin），它在你输入时在后台检查语法错误。这对于拉平基于 Web 的文本编辑器与其线程友好的桌面编辑器之间的差距至关重要。当涉及到实时解析大型文档时，单核是远远不够的。

Web Workers 是现代浏览器中令人兴奋的新增功能，有潜力显著提升性能。随着 Web 应用越来越偏向客户端，我们可以预期 Web Workers 将成为 JavaScript 领域中更为突出的组成部分。

## 5.2 使用 `cluster` 的 Node Workers

在 Node 的早期，存在许多竞争的多线程 API。大多数解决方案都很笨拙，要求用户启动多个服务器实例来监听不同的 TCP 端口，然后通过代理将它们连接到真正的服务器。直到 0.6 版本，才内置了一个标准，允许多个进程绑定到同一端口：`cluster`。

通常，`cluster` 用于每个 CPU 核心启动一个进程以获得最佳性能（尽管每个进程是否真的会获得自己的核心完全取决于底层操作系统）：

```
var cluster = require('cluster');

if (cluster.isMaster) {
  // 启动 worker
  var coreCount = require('os').cpus().length;
  for (var i = 0; i < coreCount; i++) {
    cluster.fork();
  }
  // 绑定死亡事件
  cluster.on('death', function(worker) {
    console.log('Worker ' + worker.pid + ' has died');
  });
} else {
  // 立即退出
  process.exit();
}
```

输出将类似于

```
Worker 15330 has died
Worker 15332 has died
Worker 15329 has died
Worker 15331 has died
```

每个 CPU 核心对应一行。

这段代码乍一看可能令人困惑。诀窍在于，虽然 Web Workers 加载独立的脚本，但 `cluster.fork()` 是在不同进程中运行*相同*的脚本。脚本判断自己是作为 master 还是 Worker 运行的唯一方式是检查 `cluster.isMaster`。

这种设计决策的原因是，Node 中的多线程与浏览器中的多线程有着非常不同的主要使用场景。虽然浏览器可以将任何多余的线程分配给后台任务，但 Node 服务器需要扩展其主任务可用的计算资源：处理请求。

（外部脚本可以使用 `child_process.fork` 作为独立进程运行。其功能与 `cluster.fork` 基本相同——事实上，`cluster` 底层使用 `child_process`——不同之处在于子进程不能共享 TCP 端口。）

### 与 Node Workers 通信

与 Web Workers 一样，`cluster` Worker 可以通过发送消息事件与主进程通信，反之亦然。不过 API 略有不同：

```
var cluster = require('cluster');

if (cluster.isMaster) {
  // 启动 worker
  var coreCount = require('os').cpus().length;
  for (var i = 0; i < coreCount; i++) {
    var worker = cluster.fork();
    worker.send('Hello, Worker!', 2);
    worker.on('message', function(message) {
      if (message._queryId) return;
      console.log(message);
    });
  }
} else {
  process.send('Hello, main process!');
  process.on('message', function(message) {
    console.log(message);
  });
}
```

输出将类似于

```
Hello, main process!
Hello, main process!
Hello, Worker!
Hello, Worker!
Hello, main process!
Hello, Worker!
Hello, main process!
Hello, Worker!
```

顺序是不可预测的，因为每个线程都在竞争谁先执行 `console.log`。

与 Web Workers 一样，API 是对称的，一侧的 `send` 调用会触发另一侧的 `'message'` 事件。但请注意，`send` 的参数（更确切地说，是其序列化副本）直接由 `'message'` 事件给出，而不是作为 `data` 属性附加。

注意这一行

```
if (message._queryId) return;
```

```
{ cmd: 'online', _queryId: 1, _workerId: 1 }
```

忽略这些内部消息是安全的，但要注意它们用于在幕后执行一些重要的魔法。最值得注意的是，当 Worker 尝试监听 TCP 端口时，Node 使用内部消息来允许端口被共享。

### Node Workers 的限制

在大多数情况下，`cluster` 遵循与 Web Workers 相同的规则：有一个 master，有多个 Worker；它们通过带有附加字符串或可序列化对象的事件进行通信。然而，虽然 Worker 在浏览器中显然是二等公民，但 Node 的 Worker 拥有与 master 相同的所有权利和特权，除了：

1. 关闭应用程序的能力，

2. 生成更多 Worker 的能力，以及

3. 相互通信的能力。

这使得 master 承担所有线程间通信中心节点的负担。幸运的是，正如我们将在下一节中看到的，我们可以通过库将这个不便之处抽象掉。

### Clusterhub

通常，Node 服务器将进程间通信保持在最低限度。只要 Worker 各自为政，使用 `cluster` 就很简单。但这意味着所有服务器状态都必须保存在外部数据库中。对于某些应用程序来说，这是不现实的。

Roly Fentanes 的 Clusterhub 通过为我们提供一个进程间 `EventEmitter`，结合一个名为 EventVat 的事件驱动数据存储来解决这个问题。这使得在所有进程之间共享小块状态变得容易。

例如，假设我们有一个集群服务器，显示点击次数（还记得 90 年代吗？）。我们可能会天真地以这种方式实现主进程：

```
var hitCount = 0;
worker.on('message', function(e) {
    if (e.cmd !== 'setHitCount') return;
    hitCount = e.val;
    workers.forEach(function(worker) {
        worker.send({cmd: 'updateHitCount', val: hitCount});
    });
});
```

以及以这种方式实现 Worker：

```
var hitCount = 0;
process.on('message', function(e) {
  if (e.cmd !== 'updateHitCount') return;
  hitCount = e.val;
});
function onRequest() {
  process.send({cmd: 'setHitCount', val: hitCount++});
  // ...
}
```

这里存在几个问题。最明显的是，对于如此简单的事情，代码太多了。而且由于每个进程都存储了自己的 `hitCount` 副本，如果两个请求同时命中两个进程，它们都会收到相同的点击次数作为响应。就我们的目的而言，这没关系；重要的是我们最终能达到一致性。

不幸的是，我们甚至无法保证这一点。如果两个 Worker 同时收到请求（也就是说，每个 Worker 在收到另一个 Worker 的操作导致的 `'updateHitCount'` 事件之前都发送了 `setHitCount`），主进程中的 `hitCount`（以及 consequently 第二个 Worker 的 `hitCount`）将只会递增一次。而且如果我们在任何时候启动一个新的 Worker，如果它在收到 `'updateHitCount'` 命令之前收到第一个请求，主进程的 `hitCount` 将被重置为 1！

解决方案很清楚：我们应该只在主进程中存储一个 `hitCount` 实例，并在那里进行递增。但对于更大的应用程序来说，这意味着我们需要为可能想要对数据执行的每一个操作编写一个主进程函数。这就是为什么，谢天谢地，有前面提到的 EventVat，一个存在于 Node 进程中的键值存储。Clusterhub 为每个进程提供了一个 `hub` 对象，充当进程间 `EventEmitter` 和 EventVat 存储，使我们的点击次数示例变得简单：

```
// master
var hub = require('clusterhub');
hub.set('hitCount', 0);

// Workers
var hub = require('clusterhub');
function onRequest() {
  hub.incr('hitCount', function(hitCount) {
    // ...
  });
}
```

EventVat 的 Redis 风格 API 允许我们通过单条进程间消息表达复杂的数据查询。例如，`mset` 函数允许我们一次性设置多个值。

目前，大多数 Node 应用使用 Redis 存储会话状态等数据，但若 Clusterhub 不久后能取代这一角色，我也不会感到意外。其方案承诺带来更高的性能、更好的安全性，并且无需在服务器上额外配置依赖项。

### 临时线程

`cluster`/`child_process` 方法非常适合将应用程序拆分为持续运行的进程，但如果你想在单独的线程中运行一段同步代码块呢？这正是 Threads A GoGo 的设计用例。⁹ 它是使长时间计算变为非阻塞的理想库。

遗憾的是，浏览器端没有等效方案。创建新的 Web Worker 开销很大，使其不适合用于一次性任务。在缺乏用于在独立线程中执行代码的 W3C 标准的情况下，我们能做的最好选择是自行创建和管理 Web Worker 池。随着 Web Worker 成为浏览器的普遍特性，无疑会有新的库让这件事变得更简单。

通过一系列方法调用、promise 和回调进行这种协调。App 的未来版本...

关于 Worker 在浏览器和服务器端的讨论就到这里。目前尚处于早期阶段，但我认为多核 JavaScript 的未来是光明的。对于任何可以拆分为主要独立、仅需定期相互通信的进程的应用程序，Worker 都是充分利用 CPU 能力的制胜方案。而有了 Clusterhub 这样的库，分布式计算从未如此有趣。

⁹ https://github.com/xk/node-threads-a-gogo

# 6 异步问题与解决方案

在最后一章，我们将探讨一些常见的异步难题。得益于我们从前面章节中学到的工具，解决它们应该会轻而易举。

## 6.1 问题：this 去哪了？

这是 JavaScript 开发者必经的考验：你传递了一个回调函数。你在该回调中使用 `this`，并未多想。接下来的几个小时，你都在试图弄清楚为什么代码坏了，并*诅咒自己为何要出生在这个世上*。或者，至少，你加入了成千上万在 Stack Overflow 上发布此类示例的人行列：

```
// each button has data indicating an "action" to take
$('button').click(function() {
  $(this).after('<a href="#" id="confirm">Confirm</a>');
  $('#confirm').click(function() {
    var action = $(this).data('action');
    // why is action undefined???
  });
});
```

jQuery 对这种混淆负有部分责任。那些不了解 `call` 和 `apply` 方法的开发者——这些方法可以将 `this` 变形为函数调用者期望的任何值——会期望 `this` 像普通变量一样作用域，尽管它是通过某种神秘魔法在事件处理器中设置的。但这个问题也出现在普通的 `setTimeout` 中：

```
var account = {
  balance: 500,
  showBalance: function() { console.log(this.balance); }
};
account.showBalance()           // 500
setTimeout(account.showBalance, 0); // undefined
```

`account.showBalance()` 在 account 上下文中调用该方法，但当 `account.showBalance` 传递给函数时，原始上下文就丢失了。

### 解决方案 1：捕获 this

这个问题最常见的解决方案是简单地将你想要的 `this` 值存储在一个单独的变量中。传统上，使用 `self` 这样的名称，但我更喜欢一个更清晰的标识符：

```
$('button').click(function() {
  var button = this;
  $(button).after('<a href="#" id="confirm">Confirm</a>');
  $('#confirm').click(function() {
    var action = $(button).data('action');
    // works
  });
});
```

这对我们的 `setTimeout` 示例也有效：只需将 `showBalance` 更改为

```
showBalance: function() { console.log(account.balance); }
```

### 解决方案 2：将回调绑定到 this

JavaScript 开发者早就知道，通过将函数包装在另一个函数中，可以使其免受 `call` 和 `apply` 黑魔法的影响。像 Underscore.js 这样的工具库包含一个 `bind` 方法，正是为此目的：

```
$('button').click(function() {
  $(this).after('<a href="#" id="confirm">Confirm</a>');
  $('#confirm').click(_.bind(function() {
    var action = $(this).data('action');
    // works!
  }, this));
});
```

我们在这里做的是强制内部回调与外部回调具有相同的 `this` 值。这是一个非常常见的模式，CoffeeScript 通过使用 `=>` 而不是 `->` 声明绑定函数使其变得简单。在较新的 JS 运行时（前沿浏览器和 Node）中，`bind` 方法是函数原型本身的一部分，所以我们可以这样写：

```
$('#confirm').click((function() {
  ...
}).bind(this));
```

绑定被广泛使用但略有争议。它通常比捕获 `this` 效率低，并且倾向于使堆栈跟踪复杂化。参见 Patrick Mueller 的博客文章 "bind() considered harmful。"¹ 或许更重要的是，当一些回调被绑定而另一些没有时，它往往会加剧关于代码特定行上 `this` 是什么的困惑。

¹ http://pmuellr.blogspot.com/2010/06/bind-considered-harmful.html

### 解决方案 3：绕过 this

此解决方案仅适用于 jQuery，因为大多数库都满足于允许回调中的 `this` 取其默认值，即根对象（浏览器中为 `window`，Node 中为 `global`）。jQuery 则不然，一些著名的 JavaScript 开发者（包括 CoffeeScript 和 Backbone.js 的创造者 Jeremy Ashkenas）称这是一个错误。虽然大多数 jQuery 编码者使用 `this` 来获取触发事件的 DOM 元素，但你可以使用更明确的 `e.currentTarget` 来代替（其中 `e` 是 jQuery 作为第一个参数传递给事件处理程序的事件对象）：

```
$('button').click(function(e) {
  $(e.currentTarget).after('<a href="#" id="confirm">Confirm</a>');
  $('#confirm').click(function() {
    var action = $(e.currentTarget).data('action');
    // works!
  });
});
```

当然，`e` 和 `this` 一样容易被滥用，因此可以考虑使用一个更具区分性的标识符，如 `buttonEvent`。

## 6.2 问题：重试异步任务

通常，我们会想要在宣告失败之前尝试异步任务 *n* 次，特别是当任务涉及连接远程服务器时。这个问题的基础很明显：

1. 我们需要存储失败尝试的次数

2. 当尝试失败时，我们需要增加失败尝试次数并检查是否超过最大值

这转化为大量样板代码，我们不希望每次遇到这种情况都重复，例如：

```
var callback, failedAttempts = 0, maxAttempts = 3;
asyncTask(callback = function(err) {
  if (err) {
    failedAttempts++;
    if (failedAttempts >= maxAttempts) {
      failCallback(err);
    } else {
      asyncTask(callback);
    }
  }
});
```

如何让这变得简单？

### 解决方案 1：回调风格

假设我们使用 Node 风格的回调，我们可以将上述样板代码转换为可重用的工具函数：

```
function attemptAndRetry(asyncTask, maxAttempts, callback) {
  asyncTask(function (err) {
    if (err) {
      if (maxAttempts <= 1) {
        callback(err);
      } else {
        attemptAndTry(asyncTask, maxAttempts - 1, callback);
      };
    } else {
      callback.apply(this, arguments);
    };
  });
}
```

注意我们这里使用了准递归。只要 `asyncTask` 的回调从事件队列运行，就不会有超出栈限制的风险。

这是最直接的解决方案，但有几点我不太喜欢。首先，调用这个函数有点笨拙：

```
attemptAndRetry(function(callback) {
  fs.readFile('locked.txt', 'utf8', callback);
}, 5, function(err, result) {
  ...
});
```

另一个问题是我们无法对过程进行细粒度控制。例如，如果我们想在每次失败尝试时记录错误呢？

### 解决方案 2：PubSub 风格

正如 JavaScript 中常见的情况一样，最佳解决方案是使用 `EventEmitter`。它使我们能够从一个简单的函数中暴露出一个极其多用途的 API。如下所示：

```
var EventEmitter = require('events').EventEmitter;
function attempt(asyncTask) {
  var emitter = new EventEmitter(), results;
  emitter.failedAttempts = 0;
  function retry() {
    asyncTask(function(err) {
      if (err) {
        emitter.failedAttempts++;
        emitter.emit('failure', err, retry);
      } else {
        results = Array.prototype.slice.call(arguments, 1);
        emitter.emit('success', results);
      }
    });
  }
  process.nextTick(retry);  // ensure asynchronicity
  return emitter;
}
```

这可能比我们之前的定义稍微复杂一些，但它让调用者的工作变得极其简单：

```
var reading = attempt(function(callback) {
  fs.readFile('locked.txt', 'utf8', callback);
});
reading.on('failure', function(err, retry) {
  console.error(err);
  if (reading.failedAttempts < 3) retry();
});
reading.on('success', function(contents) {
  //
});
```

现在我们已经清晰地暴露了状态，并精确控制了何时重试我们的函数。此外，由于我们可以为同一事件附加多个处理程序，因此可以很容易地从多个角度查看进程状态。例如，我们可以将任务映射到 Promise 上以便于监控：

```
var deferred = new $.Deferred();
reading.on('failure', function(err, retry) {
  if (reading.failedAttempts >= 3) deferred.reject(err);
});
reading.on('success', deferred.resolve);
```

## 6.3 问题：测试异步代码

在 Java 和 Ruby 等语言中，测试用例可以只是一系列断言。不幸的是，这在测试异步 JavaScript 代码时行不通，因为测试运行器无法知道测试用例何时完成。使用能够处理异步测试用例并产生有意义的输出（尽管断言的顺序不可预测）的 JavaScript 测试框架非常重要。

### 解决方案：使用 Mocha

作为 Expresso 的继任者，Mocha 是一个适用于浏览器和 Node 的通用测试框架。[2] 虽然异步测试在较旧的测试框架（如 QUnit，需要异步测试用例手动启动和停止运行器）中是一件痛苦的事，但 Mocha 让它"开箱即用"。以下是使用 Mocha 的 TDD 风格接口的示例（我更喜欢它的简洁性，而不是默认的 BDD 风格接口）：

```
var assert = require('assert');

suite('gamification', function() {
  setup(gamify);

  test('gamify resets points', function() {
    assert.equal(points, 0);
  });

  test('player points are loaded on login', function(done) {
    assert.equal(points, 0);
    login(mock.username, mock.password, function(err, success) {
      if (err) throw err;
      assert.ok(success);
      assert.equal(points, mock.points);
      done();
    });
  });
});
```

假设所有断言都通过了。当通过命令 `mocha -u tdd test.js` 运行此代码时，测试运行器会在第一个测试用例返回时立即报告其成功，并在第二个测试用例调用 `done` 时立即报告其成功。但是等等——它怎么知道在第二种情况下等待 `done` 被调用呢？

这里的玄妙之处在于一个名为 *arity* 的 JavaScript 特性。函数的 arity 是指它声明的参数数量。该数字作为 `length` 属性暴露出来：

```
(function() { ... }).length; // 0
(function(done) { ... }).length; // 1
```

使用这种特性来区分同步函数和异步函数是一个巧妙的方法，但它有一个注意事项：如果你不小心为同步测试用例声明了一个参数，例如

```
test('bedard', function(done) {
    assert.ok(true);
});
```

你会得到的错误输出

```
x 1 of 1 tests failed:

1) bedard:
    Error: timeout of 2000ms exceeded
```

通常，声明函数时避免不必要的参数是良好的风格。在 Mocha 中，这却是生死攸关的事。

## 6.4 问题：聚合事件

随着事件驱动模型的兴起，很容易让应用程序被事件淹没，使其运行缓慢。例如，在游戏中，我们可能会用 Backbone 模型来表示关卡中数千个角色，并在这些模型发生任何变化时执行游戏逻辑。但是当玩家投掷手榴弹，一次炸掉 100 个怪物时，我们并不想执行 100 次相同的逻辑。我们该如何避免这种情况？

### 解决方案 1：静默 change 事件

Backbone 为我们提供了一个特殊标志，可以用来在不触发 `'change'` 事件的情况下修改模型：

```
monsters.each(function(damage) {
  this.set({life: this.get('life') - damage}, {silent: true});
});
```

如果使用得当，这是解决问题的最有效方案。但这只有在我们对正在静默修改的每个模型应该发生什么变化有绝对了解的情况下才能奏效。

静默化事件就像一把手术刀。凭借稳健的双手和精确的计划，它可以成为无价的工具；否则，它只会造成混乱。

### 解决方案 2：使用简单的 timeout

请记住，即使是 0ms 的延迟也会确保一个函数在所有同步代码之后运行。我们可以利用这一点，让 `checkGameState` 函数在所有单个怪物模型更新后只运行一次：

```
var checkGameStateTimeout;
function checkGameState() {
  // if no monster allies remain, you lose
  var isTheGameLost = monsters.filter(function() {
    return this.get('ally');
  }).length === 0;
  // and so on..
}

var monsters = new Backbone.Collection;
monsters.on('change', function() {
  clearTimeout(checkGameStateTimeout);
  checkGameStateTimeout = setTimeout(checkGameState, 0);
});
```

现在，无论有多少怪物同时被改变，`checkGameState` 只会响应一次。

### 解决方案 3：节流/防抖

我们已经看过一个从更新模型的应用程序部分操作的解决方案，以及另一个从模型端工作的解决方案。但最优雅的方法通常是针对我们想要防止被过于频繁调用的特定函数进行操作。一般来说，这意味着我们要限制 `checkGameState` 每 *n* 毫秒只运行一次。对此有两种基本方法：

1. *节流（Throttling）*，如果距离上次运行不到 *n* 毫秒，则忽略对该函数的额外调用，以及

2. *防抖（Debouncing）*，将对该函数的任何调用延迟，直到自上次调用以来已经过去了 *n* 毫秒

通常，你想要节流，因为防抖会给每个函数调用增加一些延迟。此外，防抖意味着如果函数被调用得太频繁，它将*永远不会*被调用！（有时防抖会实现最大延迟来避免这一点。）然而，在想要等到输入源空闲的场景中，例如渲染预览或在用户短暂停止输入后才运行验证，防抖更为可取。

节流和防抖都很容易实现，只需创建一个元函数，返回原始函数的包装版本。以下是两个简单的实现：

```
function throttle(func, minDelay) {
  var lastHitDate = 0;
  return function() {
    var now = new Date();
    if (now - lastHitDate >= minDelay) {
      lastHitDate = now;
      return func.apply(this, arguments);
    };
  };
}
```

```
function debounce(func, delay) {
  var timeout;
  return function() {
    var args = arguments;
    clearTimeout(timeout);
    timeout = setTimeout(function() {
      func.apply(this, args);
    }, delay);
  };
}
```

（如果你正在使用 Underscore.js——你应该用！——可以直接使用 `_.throttle` 和 `_.debounce`。）

有了这些工具函数，我们可以完全覆盖 `checkGameState`，或者只是从我们的 `change` 事件中使用包装版本。就我们的目的而言，延迟为 0 的防抖最合适，因为短延迟的节流会允许 `checkGameState` 在同步代码块中运行更多次。延迟为 0 的防抖实际上等同于我们在解决方案 2 中使用的 `setTimeout`：

```
var debouncedCheckGameState = debounce(checkGameState, 0);
monsters.on('change', function() {
    debouncedCheckGameState();
});
```

注意，从我们想要限制调用的每个来源使用相同的节流/防抖函数实例是很重要的。调用

```
(debounce(checkGameState, 0))();
```

只是一种过于复杂的调用

```
setTimeout(checkGameState, 0);
```

的方式，因为再次调用 `debounce(checkGameState, 0)` 只会创建一个单独的 timeout。

## 6.5 问题：处理请求

快速问题：你是一个 Web 服务器。你收到一个请求。你该怎么办？

很可能，是很多不相关的事情。至少，你要查看请求的路由，并将其映射到你作为响应发送的文件。但你可能还会记录请求、检查请求者是否已正确认证，以及获取一些数据。也许你还会将响应缓存到内存中。这些功能中的许多功能对某些或所有路由来说都是相同的。你如何避免重复？

### 解决方案：中间件模式

在 Node.js Connect 框架中，每个中间件函数接收一个请求对象（`req`）、一个响应对象（`res`）和一个 `next` 回调。每次有新的请求进来时，它都会被传递给第一个中间件。该中间件有三个（好的）选项：

1. 自行处理请求，发送响应并在不调用 `next` 的情况下返回。

2. 不带参数调用 `next`。

3. 带一个错误参数调用 `next`。

Connect 生成的 `next` 回调要么将请求传递给栈中的下一个中间件，要么传递给错误处理程序。而这基本上就是 Connect 所做的全部。这种简单的模式（核心实现不到 200 行¹）已经证明非常成功，以至于几乎每个 Node 服务器框架都是基于 Connect 构建的，其中最著名的是 Express.js。

考虑在其他需要对某个动作进行多个离散步骤处理的场景中使用中间件模式。中间件栈与普通回调栈（如我们在第 2 章中看到的）之间的唯一区别是，栈上的每个函数都会收到一个 `next` 函数，使其能够声明已完成，从而实现异步操作序列。以下是一个最小化实现，供比较：

```
// 回调栈
function trigger() {
  handlers.forEach(function(handler) {
    handler();
  });
}

// 中间件栈
function trigger() {
  invoke(0);
}
function invoke(idx) {
  if (handlers.length <= idx) {
    return;
  } else {
    handlers[idx](function(err) {
      if (err) throw err;
      if (handlers.length > idx + 1) invoke(idx + 1);
    });
  }
}
```

敏锐的读者可能会想起第 4 章中的 `async.series`。以这种方式连接函数是一种极其常见的模式。虽然你可以自由地重新发明轮子，但要注意该轮子已经在 MIT 许可证下可用了。

¹https://github.com/senchalabs/connect/blob/master/lib/proto.js

## 6.6 问题：Ajax 意大利面

把这当作一个综合性练习。如果我们决定改变应用程序的行为，如何将高度嵌套的代码变成更清晰、更有组织、更少重复且更易于修改的东西？

```
$(function() {
  $('#menu').on('click', 'a', function clickHandler() {
    // 我们在选中的菜单项上放置一个旋转器
    var $clickedLink = $(this).spin();
    // 我们在 Ajax 调用返回前禁用菜单
    $('#menu').off('click', 'li > a');
    $.get('/content/' + $clickedLink.index(), {
      success: function successHandler(response) {
        $clickedLink.unspin();
        $('#menu').on('click', 'li > a', clickHandler);
        // 我们将内容淡出
        $('#content').fadeOut(function() {
          // .然后用 Ajax 标记淡入
          $('#content').html(response).fadeIn();
        });
      },
      error: function() {
        // 如果错误只是偶然，我们会重试一次
        $.get('/content/' + $clickedLink.index(), {
          success: successHandler,
          error: function() {
            $clickedLink.unspin();
            $('#menu').on('click', 'li > a', clickHandler);
            modal('Error retrieving content from the server.');
          }
        });
      }
    });
    return false; // 阻止默认点击行为
  });
});
```

### 解决方案：分发，分发，分发

上面代码的最大问题是它过于集中。*所有*响应菜单点击的操作都放在点击处理程序中，*所有*响应 Ajax 请求的操作都放在 Ajax 响应处理程序中。我们需要以合理的方式将这些分散开来。

这里有很多方法可以做到这一点——例如使用自定义 jQuery 事件——但我推荐的方法是使用事件驱动模型来表示菜单。该模型将封装我们需要从各种异步事件中捕获的状态，而这种抽象将使我们在未来更容易改变事件流。

让我们先问："我们需要存储什么状态？" 我能想到三件事：

1. 我们的菜单是处于"就绪"、可点击状态，还是处于"未就绪"状态并在活动链接上显示旋转器。

2. 当前哪个链接是活动的（正在加载关联内容的过程中），如果有的话。

3. 对于活动链接，我们到目前为止已向服务器请求内容的次数是多少。

前两个听起来应该与菜单相关联。因此这给了我们菜单模型：

```
window.menu = new Backbone.Model({
  ready: false,
  activeLinkIndex: -1
});
```

为什么我们的菜单以 `ready: false` 开始？因为菜单元素可能尚不存在于文档中。我们希望 `ready` 对应于点击处理程序的附加。我们还想确保当菜单变为就绪时不存在活动链接：

```
menu.on('change:ready', function(ready) {
  if (ready) {
    $('#menu').on('click', 'li > a', menu.clickHandler);
    menu.set('activeLinkIndex', -1);
  } else {
    $('#menu').off('click', 'li > a');
  }
});
```

注意对 `menu.clickHandler` 的引用。为了方便命名空间，我们将继续把所有与菜单相关的事件处理程序附加到菜单模型：

```
menu.clickHandler = function() {
  menu.set({ready: false, activeLinkIndex: $(this).index()});
  return false;
}
```

声明菜单就绪是唯一必须等待 DOM 的事情。所以我们最初包裹*所有内容*的 jQuery 回调现在只是一行代码：

```
$(function() { menu.set({ready: true}); });
```

（注意这一行必须放在 `menu.clickHandler` 定义之后，因为如果文档已经就绪，回调将同步运行。）

点击处理程序修改菜单的 `activeLinkIndex`，因此让我们通过获取相应内容并给正确的菜单项添加 Ajax 旋转器来响应：

```
menu.on('change:activeLinkIndex', function(activeLinkIndex) {
    $('#menu').children().unspin()
        .eq(activeLinkIndex).spin();
    menu.fetchSelectedContent();
});
```

如果 `activeLinkIndex` 被改为 -1（表示没有链接是活动的），`eq(activeLinkIndex)` 选择器将匹配不到任何元素，因此不会出现 Ajax 旋转器。而我们的 `fetchSelectedContent` 的第一行将简单地返回：

```
menu.fetchSelectedContent = function() {
    if (menu.get('activeLinkIndex') === -1) return;
    $.ajax({
        url: '/content/' + menu.get('activeLinkIndex'),
        tryCount: 0
    })
    .done($('#content').fadeHtml)
    .done(function() { menu.set({ready: true}); })
    .failure(function() {
        this.tryCount++;
        if (this.tryCount >= 2) {
            modal('Error retrieving content from the server.');
        } else {
            $.ajax(this);
        };
    });
}
```

这是我们最复杂的函数，但每一行都有明确的目的。当 Ajax 调用成功时：

1. 内容元素的 `fadeHtml` 方法被调用，传入从服务器检索到的数据。`fadeHtml` 是我们即将定义的简单插件。

2. 菜单恢复到就绪状态。回想一下，这也会将 `activeLinkIndex` 重置为 -1。

当 Ajax 调用失败时：

1. jQuery Ajax 回调中的 `this` 指向 `jqXHR` 对象，该对象除其他外还存储了传递给 `$.ajax` 的所有设置。我们用它来存储 `tryCount`。

2. 因为 `this` 也包含我们的 `url` 属性，所以我们可以简单地写 `$.ajax(this)` 来重试 Ajax 调用。这种技术因一篇题为 "Defensive Ajax and Ajax retries in jQuery" 的博客文章而流行起来。

如果我们觉得 `fetchSelectedContent` 方法太大，我们可以将 `failure` 处理程序移出。这就是事件驱动代码的妙处：只要状态被合理地存储，你就拥有无限的灵活性。

现在唯一需要填补的空缺是定义 `fadeHtml`：

```
$.fn.fadeHtml = function(markup) {
  return this.fadeOut(function() {
    $(this).html(markup).fadeIn();
  });
};
```

就是这样！我们的代码比开始时多了一些，但它比原来容易使用很多倍。
