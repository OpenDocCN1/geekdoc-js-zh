# 第 1 章
## 什么是 JSON？

在我们从低层次的角度来看 JSON 之前，让我们从大约 6000 英尺的高度来看看 JSON。从山顶上，我们可以看到 JSON 在世界上飞来飞去，以其轻量级的格式携带数据。如果我们通过望远镜观察 JSON，我们会看到在许多花括号字符（{}）之间的数据。然而，如果我们退后一步，观察它*如何*被使用，我们最终会发现它是一种数据交换格式。

### JSON 是一种数据交换格式

数据交换格式是一种用于在平台之间交换数据的文本格式。你可能已经听说过的另一种数据交换格式是 XML。世界需要数据交换格式，如 XML 和 JSON，以便在非常不同的系统之间交换数据。

想象一下，一个世界由广阔海洋中的数百个 tiny、孤立的岛屿组成。每个岛屿都有自己独特的语言和习俗。所有岛屿都有在岛屿之间长途旅行的海上商人。对外贸易是所有岛屿经济不可或缺的一部分，为岛民带来了高生活水平。如果没有训练有素的信海鸥，这将是不可能的。

信海鸥从一个岛屿飞到另一个岛屿，携带一份关于哪些商品需求量最高的数据报告。这样，商人就能知道他们接下来应该前往哪里，以及在踏上穿越大洋的漫长航程之前应该获取哪些商品。这些重要数据使所有岛屿都能繁荣发展，而不受短缺的威胁。

请记住，每个岛屿都说不同的语言。如果数据以几种语言传递，每个岛屿都需要投入研究人员来学习所有

世界上的各种语言，并雇佣一支翻译团队。这将既昂贵又耗时。然而，这是一个智能的世界，因此所有岛屿都同意使用一种单一的语言，并采用标准格式来传递它们的贸易数据。每个岛屿只需雇佣一名翻译人员，就能理解由信使海鸥带来的、采用统一数据格式的贸易报告。

技术的现实世界与想象中的岛屿世界非常相似。那里有一片广阔的海洋，遍布着拥有不同语言、风俗和建筑的岛屿。这些独特系统之间的通信能力对许多企业和组织来说至关重要。如果每个系统都需要为其他系统 structuring 数据的各种方式配备翻译人员，那么通信将消耗不合理的时间和资源。相反，各系统约定采用单一的数据格式，并只配备一名翻译人员。

JSON 是一种数据交换格式，许多系统已同意使用它来进行数据通信。你可能听到它被称为"数据交换格式"或简称为"数据格式"。在本书中，我将把 JSON 称为数据**交换**格式，因为"交换"的定义提醒我们，这种数据格式是为两个或多个实体之间的交换而设计的。

许多系统，但并非所有系统，已同意使用 JSON 进行数据通信。还有一些数据交换格式，比如可扩展标记语言（XML），在 JSON 被构想出来之前就已经存在了。现实世界并不像岛屿例子那样简单。许多系统曾经并且仍然在使用其他格式，如 XML，或更具表格性的、带分隔符的格式，如逗号分隔值（CSV）。现实世界中每个岛屿决定接受哪种数据格式进行通信，往往与该数据格式如何与岛屿的习俗、语言和架构相关联有关。

在岛屿世界的例子中，数百个岛屿各自拥有不同的语言。信使海鸥携带的纸质报告中的数据采用了一种约定格式，这种格式与语言无关。这样，每个岛屿就可以只雇佣一名贸易报告数据的翻译人员。JSON 也是如此，只不过数据是通过网络以零和一传输的，而不是由海鸥运送。翻译人员不是人类，而是由消费数据的系统所采用的解析器，以便数据能够在进入的系统中被读取。

## JSON 独立于编程语言

JSON 代表 JavaScript Object Notation（JavaScript 对象表示法）。这种数据交换格式的名称可能会误导人们，让他们以为自己需要学习 JavaScript 才能理解和使用 JSON。在学习 JSON 之前学习一些 JavaScript 会有一定价值，因为它诞生于 JavaScript 的一个子集，但如果你短期内不会使用 JavaScript，那就没有必要了。你可以继续专注于你自己岛屿的语言或语言们，因为数据交换格式的精神就是要独立于语言。

JSON 基于 JavaScript 对象字面量。关于"如何"实现这一点的详细解释，更适合在我们讨论语法（第 2 章）和数据类型（第 3 章）时进行。对于本章而言，"为什么"才是重要的。如果数据交换格式旨在独立于语言，那么一种不仅源自单一语言、还在其名称中宣传这一点的数据格式——JavaScript Object Notation——似乎就显得矛盾了。那么，为什么呢？

如果我们回到岛屿的例子，想象一下选择数据格式的会议会是什么样子。当来自数百个岛屿的代表们到达这个会议，并试图创建一种单一的数据格式时 seeking 找到共同点。

每个岛屿的语言可能是独特的，但岛民们发现他们有一些共同点。大多数语言主要通过人类的声音来说，并包含以某种字符表示的书面形式。此外，面部表情和手部动作也存在。有几个麻烦的岛屿，那里的人们通过其他方式交流，比如敲击木棍或眨眼，但大多数岛屿在书面和口头语言形式方面找到了共同点。

在现实世界中，有数百种编程语言。有些比其他更流行、更常用，但语言景观是多样的。当大学生主修计算机科学，为编程职业生涯做准备时，他们不会学习所有的编程语言。学生通常从一种语言开始，而语言本身不如学习普遍接受的编程概念重要。一旦学生掌握了这些概念，他们就能够通过识别共同特征和功能，更容易地学习其他编程语言。

如果我们将"JavaScript"这个词从"JavaScript Object Notation"的名称中去掉，我们就只剩下"Object Notation"。事实上，让我们把 JavaScript  altogether 忘掉。我们可以说我们正在使用一种对象表示法数据交换格式。"对象"是一个常见的编程概念，特别是对于面向对象编程（OOP）而言。大多数学习编程的计算机科学学生都会学习对象的概念。

在不深入解释对象的情况下，让我们把注意力集中在"表示法"这个词上。*表示法*（*Notation*）意味着一套用于表示数据（如数字或元素）的字符系统。无论是否理解编程中的对象，都不难看出拥有一种表示法来描述跨编程语言共通事物的价值。

再次回到岛屿的例子，岛民们自己找到了一种表示法，这种表示法代表了大多数语言之间的共同联系。大多数岛民有类似的方式用 tally marks 来表示数字，并且他们一致认为可以用一系列符号来表示小麦或布料等现实世界中的物体。即使是以眨眼交流的岛屿也认为这种格式可以接受。

尽管绝大多数岛屿达成了共识，但仍有一些岛屿，比如那个通过敲击木棍交流的岛屿，无法理解这种格式。良好的数据交换格式覆盖大多数情况，但通常会有一些*异常值*（outliers）。当我们谈论这种覆盖范围时，经常提到的一个术语是*可移植性*（*portability*）。可移植性，即在平台和系统之间传输信息的兼容性，正是数据交换格式的目标。

回到表示法，JSON 的表示法可能起源于 JavaScript，但表示法本身才是重要的部分。JSON 不仅独立于语言，而且以一种与许多编程语言的共同元素对话的方式来表示数据。就数据表示方式而言，比如数字和文字，即使不是面向对象的编程语言也能发现这种格式是可以接受的。

## 关键术语和概念

本章涵盖了以下关键术语：

**JSON**
：JavaScript 对象表示法（JavaScript Object Notation）

**表示法**（**Notation**）
：一套用于表示数据（如数字或元素）的字符系统

**数据交换格式**（**Data interchange format**）
：用于在平台或系统之间交换数据的文本

**可移植性**（**Portability**）
：以与两个系统都兼容的方式在平台之间传输信息

我们还讨论了以下关键概念：

- JSON 是一种数据交换格式
- JSON 独立于编程语言（使用 JSON 不需要 JavaScript）
- JSON 基于 JavaScript 的对象字面量表示法（重点是"表示法"一词）
- JSON 以一种对通用编程概念友好的方式表示数据

JSON 语法

## JSON 基于 JavaScript 对象字面量

在英语中，"literal"这个词是形容词，用于暗示所说的话是字面的、不是比喻。当你的朋友说"她不知从哪里冒出来，我 literally 掉了三明治"时，他在说掉三明治不是比喻。

在编程中，"literal"是名词。*字面量*（*literal*）是用数据 literally 表示的值。它精确地按照其本意来书写。如果你不熟悉编程概念，这可能看起来很奇怪。让我们快速看一下字面量。

你的钱包里会放现金，还是借记卡？当我在三明治店停下来，递给收银员一张五美元的钞票买三明治时，我眼睁睁地看着我的五美元离开钱包。当我刷借记卡买三明治时，我知道我的银行账户少了五美元，即使我没有看到它发生。

在编程中，我们经常使用变量来表示值。例如，我可能会在一个表达式中使用一个称为*x*的*变量*：

```
x = 5
```

然后，稍后，我可能想再给*x*加五：

```
x = x + 5
```

此时，我们知道*x*的值是 10，但我们*看不到*10。在这个例子中，*x*是变量，而 5 是字面量。在我们的三明治店例子中，我们可以说五美元现金是字面量，而借记卡是变量。当我们*看到*实际值时，它就是字面量值。



在 "x = 5" 这个例子中，5 是一个数字字面量。数字是一种数据类型。其他数据类型包括字符串（由字符组成）、布尔值（true 或 false）、null（空值）、值的集合以及对象。以一种我们可以看到的方式表示一个数字值很简单，我们使用数字字符。表示布尔值也很简单，我们可以使用 true/false 或 0/1。如果你熟悉对象的概念，你就会明白表示一个对象并非易事。如果你不熟悉对象的概念，那也没关系。

在编程中，对象的概念类似于你如何描述一个真实世界的物体，比如你的鞋子。你可以用属性或特征来描述你的鞋子，例如颜色、款式、品牌和鞋垫类型。其中一些属性值可以是数字，例如鞋码，其他的可以是布尔值（true/false），比如 "hasLaces"（是否有鞋带）。示例 2-1 展示了一个例子。

## 示例 2-1. 使用 JSON 描述我目前穿的鞋子

```
{
    "brand": "Crocs",
    "color": "pink",
    "size": 9,
    "hasLaces": false
}
```

现在不必担心鞋子例子中的语法；我们将在本章稍后介绍。鞋子例子的主要观点是，你（即使是人类）可以直观地读出我鞋子的属性。我的 JSON 鞋子例子的数据类型是对象。我们可以看到对象的字面值，它以我们可见（且可读）的方式暴露了属性或特征。这个鞋子对象的这些属性或特征以名称-值对的形式表示。

JSON 基于 JavaScript 对象字面量。这里的关键词是 "基于"。在 JavaScript（以及大多数具有对象的编程语言）中，对象可以包含函数。因此，我不仅可以使用 JavaScript 对象表示鞋子的属性，还可以创建一个名为 "walk"（行走）的函数。

然而，数据交换是关于数据的，因此 JSON 不包括 JavaScript 对象字面量的函数。JSON 基于 JavaScript 对象字面量的方式纯粹在于对象字面量及其属性的语法表示。这种属性的表示是通过名称-值对实现的。

## 名称-值对

名称-值对的概念在计算领域非常普遍。它们也有其他名称：键-值对、属性-值对和字段-值对。在本书中，我们将它们称为名称-值对。

如果你熟悉名称-值对的概念，JSON 对你来说会显得很自然。如果你不熟悉名称-值对，那也没关系。让我们快速了解一下名称-值对。

在一个名称-值对中，你首先声明名称。例如，"animal"（动物）。现在，对（pair）意味着两样东西：一个名称和一个值。那么，让我们给我们的名称 "animal" 赋一个值。为了在本章简化这个概念，让我们使用一个字符串值。在 JSON 的名称-值对中，值也可以是数字、布尔值、null、数组或对象。我们将在第 3 章更深入地介绍字符串之外的其他值数据类型。所以，对于我们的名称-值对，名称是 "animal"，我们将使用字符串值 "cat"（猫）：

```
"animal" : "cat"
```

"animal" 是名称，"cat" 是值。我们可以用多种方式来界定或分隔名称和值。如果我给你提供一个公司员工的目录及其职位，我可能会给你一份看起来像这样的列表：

- Bob Jackson, Chief Executive Officer
- Janet Jackson, Chief Operations Officer
- Mr. Ed, Chief Financial Officer

在我的员工目录中，我使用逗号分隔职位（名称）和员工姓名（值）。我还把值放在了左边，把名称放在了右边。

JSON 使用冒号（:）来分隔名称和值。名称总是在左边，值总是在右边。让我们再看几个例子：

```
"animal" : "horse"

"animal" : "dog"
```

很简单，对吧？一个名称和一个值，你就有了一个名称-值对。

## 正确的 JSON 语法

现在让我们看看正确的 JSON 语法。名称，在我们的例子中是 "animal"，总是被双引号包围。双引号中的名称可以是任何有效的字符串。因此，你可以有一个像这样的名称，它将是完全有效的 JSON：

```
"My animal": "cat"
```

你甚至可以在名称中使用撇号：

```
"Lindsay's animal": "cat"
```

既然你知道这是有效的 JSON，我要告诉你为什么不应该这样做。JSON 中使用的名称-值对是许多系统都友好的数据结构。如果名称中包含空格或特殊字符（a–z, 0–9 除外），就无法考虑 *可移植性*。在第 1 章中，我们将这个关键术语定义为“以与两个系统都兼容的方式在平台之间传输信息”。我们可以在 JSON 数据中做降低可移植性的事情；因此，为了实现 *最大可移植性*，我们说避免空格或特殊字符很重要。

JSON 名称-值对中的名称，如果要在系统中作为对象加载到内存中，将成为一个“属性”或“特征”。在某些系统中，属性或特征可以包含下划线（_）或数字，但在大多数情况下，坚持使用字母表中的字符 A–Z 或 a–z 被认为是良好的做法。因此，如果我想在名称中包含多个单词，我会这样格式化：

```
"lindsaysAnimal": "cat"
```

或者

```
"myAnimal": "cat"
```

例子中的 "cat" 值带有双引号。与名称-值对中的名称不同，值并不总是需要双引号。如果我们的值是字符串数据类型，我们必须使用双引号。在 JSON 中，剩余的数据类型是数字、布尔值、数组、对象和 null。这些不需要被双引号包围。它们的格式将在第 3 章介绍。

JSON 代表 JavaScript Object Notation（JavaScript 对象表示法）。所以，我们唯一缺少的是使其成为对象的语法。我们需要用花括号将我们的名称-值对包围起来，使其成为一个对象。所以，一个在前...

```
{ "animal" : "cat" }
```

...一个在后。当你格式化你的 JSON 时，想象一个授勋仪式，主持人用剑轻触新骑士的肩膀。你就是主持人，你必须用花括号在你的 JSON 两侧“册封”它为一个对象。“我册封你，JSON 爵士。”如果没有轻触两肩，仪式就不完整。

在 JSON 中，多个名称-值对用逗号分隔。因此，为了扩展动物/猫的例子，让我们添加一个颜色：

```
{ "animal" : "cat", "color" : "orange" }
```

看待 JSON 语法的另一种方式是通过读取它的机器的视角。与人类不同，机器是非常严格地遵循规则和指令的生物。当你在字符串值（未被引号包围）之外使用以下任何字符时，你就是在提供关于如何读取数据的指令：

- {（左花括号）表示 "开始对象"
- }（右花括号）表示 "结束对象"
- [（左方括号）表示 "开始数组"
- ]（右方括号）表示 "结束数组"
- :（冒号）表示 "分隔名称-值对中的名称和值"
- ,（逗号）表示 "分隔对象中的名称-值对" 或 "分隔数组中的值"；也可以理解为 "后面还有一个"

如果你忘记用右花括号说“结束对象”，那么你的对象将不会被识别为对象。如果你在名称-值对列表的末尾放置一个逗号，你就给出了“后面还有一个”的指令，但实际上没有提供。因此，语法正确非常重要。

## 一个故事：JSON 的双引号

有一天，我正从一个学生的肩膀后面看他的电脑屏幕。这家伙给我看了一些他正要验证的 JSON。

*示例 2-2. 无法验证的 "JSON"*

```
{
   title : "This is my title.",
   body : "This is the body."
}
```

验证时，他收到了一个解析错误并感到沮丧。他说：“看，它没有任何问题！”

我向他指出，他漏掉了 "title" 和 "body" 周围的引号。他说：“但我见过 JSON 有这两种格式，名称周围有引号和没有引号。”“啊，”我说。“当你看到名称周围没有引号的 JSON 时，那不是 JSON。那是一个 JavaScript 对象。”

这种混淆是可以理解的。JSON 基于 JavaScript 对象字面量，所以它们看起来非常相似。JavaScript 对象字面量不需要在名称-值对的名称周围使用引号。而在 JSON 中，这是绝对必需的。

另一个可能引起混淆的点是使用单引号而不是双引号。在 JavaScript 中，对象语法可能使用单引号而不是双引号。

*示例 2-3. 这不是有效的 JSON*

```
{
   'title': 'This is my title.',
   'body': 'This is the body.'
}
```



> 在 JSON 中，只能使用双引号，而且名称-值对的名称**必须**用双引号括起来。

示例 2-4. 合法的 JSON

```
{
    "title": "This is my title.",
    "body": "This is the body."
}
```

## 语法验证

与机器不同，作为使用键盘的人类，犯一个错误不过是按错一个键而已。说真的，令人惊讶的是我们竟然没有犯更多的错误。验证 JSON 是处理 JSON 的重要环节。

你的集成开发环境（IDE）可能内置了 JSON 验证功能。如果你的 IDE 支持插件和扩展，即使没有集成验证工具，你也可能在插件市场中找到它。如果你不使用 IDE，或者完全不知道我在说什么，那也没关系。

网上有许多用于格式化和验证 JSON 的工具。只需在搜索引擎中快速搜索"JSON validation"，就能得到多个结果。以下是几个值得一提的工具：

- JSON Formatter & Validator：一个功能丰富的格式化工具，拥有漂亮的 UI，可以高亮显示错误。处理后的 JSON 会显示在一个窗口中，该窗口既可作为树状/节点可视化工具，也可用于复制/粘贴格式化后的代码。
- JSON Editor Online：一个集验证、格式化和可视化于一体的 JSON 工具。错误指示器会显示在出错的行上。验证通过后，会显示有用的解析错误信息。可视化工具以树状/节点格式展示你的 JSON。
- JSONLint：一个简洁实用的 JSON 验证工具。只需复制、粘贴，然后点击"validate"即可。它还会友好地帮你格式化 JSON。

这些工具用于*语法验证*。稍后在第 4 章中，我们将讨论另一种称为一致性验证的验证方式。语法验证关注的是 JSON 本身的形式，而一致性验证关注的是特定的数据结构。以示例 2-5 为例，语法验证会检查我们的 JSON 是否正确（用花括号包围，名称-值对之间用逗号分隔）。一致性验证则会检查我们的数据是否包含 name、breed 和 age。此外，一致性验证还会检查 age 的值是否为数字，name 的值是否为字符串。

示例 2-5. 验证示例

```
{
    "name": "Fluffy",
    "breed": "Siamese",
    "age": 2
}
```

你可能会发现，在未来使用 JSON 的过程中，你只是在代码中创建它，并在一个只有开发者工具才能查看的无形世界中传递它。然而，作为一种数据交换格式，JSON 可以作为独立文档存在于文件系统中。JSON 的文件扩展名很容易记住：`.json`。

## 关键术语和概念

本章涵盖以下关键术语：

- *字面量*：按照预期解释方式精确书写的值。
- *变量*：可以更改的值，由标识符表示，例如 x。
- *最大可移植性（在数据交换中）*：超越数据格式的基础可移植性，确保数据本身在不同系统或平台上兼容。
- *名称-值对*：一个具有名称和对应值的属性或特征（也称为键值对）。
- *语法验证*：关注 JSON 形式的验证。
- *一致性验证*：关注特定数据结构的验证。

我们还讨论了以下关键概念：

- JSON 基于 JavaScript 对象字面量属性的语法表示。这*不*包括 JavaScript 对象字面量的函数。
- 在 JSON 的名称-值对中，名称始终用双引号括起来。
- 在 JSON 的名称-值对中，值可以是字符串、数字、布尔值、null、对象或数组。
- JSON 中的名称-值对列表用花括号括起来。
- 在 JSON 中，多个名称-值对之间用逗号分隔。
- JSON 文件使用 *.json* 扩展名。
- JSON 的媒体类型是`application/json`。

# 第 3 章 JSON 数据类型

如果你已经学习过一两种编程语言，你可能对数据类型有所了解。如果没有，那也没关系。让我们快速了解一下。

## 数据类型快速入门

想象一下，如果你把一把锤子递给一个完全不懂工具的小男孩，却不告诉他锤子的用途，会发生什么。财产和人身伤害恐怕在所难免。如果这个孩子行为端正且协调性好，我们可以给他一套使用锤子的说明。这样他就不会到处破坏东西，而是只用锤子来钉钉子和拔钉子（记住，他是个乖孩子）。此外，当你说"请把锤子递给我好吗？"时，他不会把螺丝刀递给你。预先知道某样东西是什么以及如何使用它，在计算领域和现实世界中同样重要。

在计算中，我们最常需要了解正在处理的数据类型，因为不同类型的数据可以进行不同的操作。我可以将一个数字乘以另一个数字，但不能将一个单词乘以另一个数字。如果我有一个单词列表，可以按字母顺序排序。我无法将数字 5 按字母排序。因此，在编程中，当一个方法（或函数）说"请把数字递给我好吗？"时，如果我们知道什么是数字，就不会犯把"ketchup"递给它的错误。

在计算机科学中，有一组数据类型被称为基本数据类型。"基本"这个词会让人联想到石器时代的原始人围坐在火旁哼哼唧唧地削尖木棍。并非这些数据类型像原始人一样粗糙；而是它们是最先出现的、最基本的一些数据类型。正如现代人和原始人之间的关系，现有的一些更现代、更先进的数据类型也起源于这些基本数据类型：

- 数字（例如 5 或 5.09）
  - 整数
  - 浮点数
  - 定点数
- 字符和字符串（例如 "a" 或 "A" 或 "apple"）
- 布尔值（即 true 或 false）

在不同的编程语言中，那些"不可更改"的数据类型通常被称为该语言的基本数据类型或内置类型。这意味着类型的定义及其允许的操作是不可改变的。编程语言不会允许你重新定义两个数字相加的含义。这些基本数据类型因语言而异，通常还会包括前述列表之外的类型，如字节（byte）或引用（或指针、句柄）。

除了基本数据类型之外，还有其他在大多数编程语言中使用的数据类型。这些通常被称为复合数据类型，因为它们是基本数据类型的融合或组合。复合数据类​​型就像一座沙堡，有其自身的结构。如果我们拆开沙堡，可以看到它的结构是由沙子、树枝和水构建而成的。如果我们拆开复合数据类型的数据结构，就会发现它是由基本数据类型构建而成的。

编程语言中常用的一种复合数据类型是枚举数据类型。前面我提到了按字母顺序排列单词列表。单词列表在不同的编程语言中可以用不同的数据类型表示（例如列表或数组）。如果我们拆开这个数据结构，会发现它是由字符或字符串这两种基本数据类型组成的。枚举数据类型是一种可以逐一列举的数据结构。我可以逐个提及结构中的每一项，也可以计算其中有多少项。参见示例 3-1。

示例 3-1. "让我列举你个性中的优秀品质"在编程中可以表示为数组字面量

```
[
    "witty",
    "charming",
    "brave",
    "bold"
]
```

你无需理解本示例中的数组字面量数据结构，就能看出我们可以逐一列举这些“优良特性”，并确认共有四项。

另一种复合数据类型是对象数据类型。在[第2章](#)中，我们探讨了对象数据类型，因为JavaScript对象表示法基于JavaScript的对象字面量表示法。

*示例3-2。在上一章中，我使用JSON描述了我所穿的鞋子*

```
{
    "brand": "Crocs",
    "color": "pink",
    "size": 9,
    "hasLaces": false
}
```

这个对象字面量让我们看到，此处的对象数据类型由名值对构成。如果我们拆解这个数据结构，会发现它由基本数据类型构成：字符串、数字和布尔值。名值对中的名称（brand、color、size、hasLaces）都是字符串数据类型。值"Crocs"和"pink"也都是字符串数据类型。值"9"是数字数据类型。值"false"是布尔数据类型。

## JSON数据类型

尽管不同编程语言在复合类型方面可能有所不同，甚至在基本类型方面也略有差异，但它们大多共享本章前面提到的那些基本类型：

- 数字（例如，5 或 5.09）
  - 整数
  - 浮点数
  - 定点数
- 字符和字符串（例如，"a" 或 "A" 或 "apple"）
- 布尔值（即 true 或 false）

对象数据类型是一些较流行编程语言（如Java和C#）共有的数据结构，但并非所有语言都有。由于JSON基于对象字面量表示法和对象数据类型，你可能会认为这对数据交换格式来说是个问题。毕竟，数据格式的目标是在两个不同系统之间进行通信，共同点应在此格式中表达。请记住，作为复合数据类型的对象数据结构可以被拆解为基本类型。即使对于没有对象数据类型的编程语言，一旦对象数据结构被拆解为这些原生类型，它也是非常友好的。

JSON数据类型有：

- 对象
- 字符串
- 数字
- 布尔值
- 空值
- 数组

## JSON对象数据类型

JSON对象数据类型很简单。从根本上说，JSON就是一个对象。它是一个由花括号包围的名值对列表。当你在JSON中创建一个也是对象的名值对时，你的JSON将开始呈现嵌套结构。示例3-3通过一个用嵌套对象描述的人来说明这一点。

示例3-3。嵌套对象

```
{
    "person": {
        "name": "Lindsay Bassett",
        "heightInInches": 66,
        "head": {
            "hair": {
                "color": "light blond",
                "length": "short",
                "style": "A-line"
            },
            "eyes": "green"
        }
    }
}
```

这里的顶级名值对是person，其值是一个对象。这个对象有三个名值对：name、heightInInches和head。"name"名值对有一个字符串值"Lindsay Bassett"。"heightInInches"名值对有一个数字值。"head"名值对有一个对象值。"hair"名值对也有一个对象值，包含三个字符串数据类型的名值对：color、length和style。"head"对象还有一个"eyes"名值对，其值为"green"。

## JSON字符串数据类型

我们在本书前面通过动物/猫的例子简要探讨了JSON字符串数据类型：

```
{ "animal" : "cat" }
```

值"cat"具有字符串数据类型。在现实世界中，除非这些数据是用于宠物店，否则数据中的字符串值不会如此简单。即使是宠物店，其数据也可能不仅仅是像"cat"这样的单个词。也许商店想传达其最新促销活动的详情：

> 今天在Bob's Best Pets，购买小狗即可获赠一袋8盎司的Bill's Kibble免费试用装。结账时只需说“Bob's the best！”即可。

JSON字符串可以由任何Unicode字符组成，而该促销文本中的所有字符都是有效的。字符串值必须始终用*双引号*包围。

在第2章的“故事：JSON的双引号”（第9页）中，我提到字符串值周围的单引号是无效的（示例3-4）。

示例3-4。*这不是有效的JSON*

```
{
    'title': 'This is my title.',
    'body': 'This is the body.'
}
```

这可能会令人困惑，特别是如果你过去见过使用单引号的JavaScript对象字面量。在JavaScript中，我们可以互换使用单引号或双引号。然而，重要的是要记住，JSON不是JavaScript对象字面量；它只是*基于*JavaScript对象字面量。在JSON中，字符串值周围只允许使用双引号。

上一章还提到了解析器如何读取JSON。在解析器看来，当一个值以双引号（"）开头时，它期望一段以另一个双引号结尾的文本字符串。如果这段文本字符串中包含双引号，就会出现问题。

例如，假设我们正在运行一个宠物店促销活动，客户需要在结账时说“Bob's the best！”以获得一袋免费狗粮。如果我们使用示例3-5中的代码，就会遇到问题，因为我们不能简单地用双引号包围促销数据。

*示例3-5。此代码将无法工作*

```
{
    "promo": "Say "Bob's the best!" at checkout for free 8oz bag of kibble."
}
```

值内部有引号，解析器会将促销文本中“Bob”前面的第一个引号字符读作字符串的结束。然后，当解析器发现剩余的文本悬挂在那儿，不属于任何名值对时，就会产生错误。为了解决这个问题，我们必须通过在字符串值内的引号前加上反斜杠字符（\）来转义它，如[示例3-6](#)所示。

*示例3-6。使用反斜杠字符转义字符串内的引号可以解决问题*

```
{
    "promo": "Say \"Bob's the best!\" at checkout for free 8oz bag of kibble."
}
```

这个反斜杠字符会告诉解析器该引号不是字符串的结束。一旦解析器实际将字符串加载到内存中，任何位于引号字符前的反斜杠字符都将被移除，文本将如预期般呈现。

在JSON字符串中，需要转义的不仅仅是引号。由于反斜杠字符用于转义其他字符，我们也必须转义反斜杠本身。例如，[示例3-7](#)中显示的JSON旨在传达我的程序文件目录位置，将会产生错误。要解决此问题，我们必须通过添加另一个反斜杠字符来转义反斜杠字符，如[示例3-8](#)所示。

*示例3-7。此代码中使用的反斜杠将引发错误*

```
{
    "location": "C:\Program Files"
}
```

*示例3-8。反斜杠字符必须用另一个反斜杠字符转义*

```
{
    "location": "C:\\Program Files"
}
```

除了双引号和反斜杠字符外，你还必须转义以下字符：

- \/（正斜杠）
- \b（退格）
- \f（换页符）
- \t（制表符）
- \n（换行符）
- \r（回车符）
- \u后跟十六进制字符（例如，笑脸表情符号 \u263A）

示例3-9中显示的JSON将产生解析器错误，因为制表符和换行符必须被转义。示例3-10展示了如何解决此问题。

示例3-9。此JSON中使用的制表符和换行符将导致错误

```
{
    "story": "\t Once upon a time, in a far away land \n there lived a princess."
}
```

示例3-10。转义了制表符和换行符的JSON

```
{
    "story": "\\t Once upon a time, in a far away land \\n there lived a princess."
}
```

## 关键术语和概念

本章涵盖了以下关键术语：

- *JSON 字符串数据类型*
  > 字符串值，如用双引号括起来的 "my string"

- *JSON 布尔数据类型*
  > 值为 true 或 false

- *JSON 数值数据类型*
  > 数值，如 42，可以是正或负整数、小数或指数

- *JSON null 数据类型*
  > null 值表示空值

- *JSON 数组数据类型*
  > 数组是一个值的集合或列表，值的类型可以是字符串、数值、布尔值、对象或数组；数组中的值用方括号（`[]`）括起来，并以逗号分隔

- *JSON 对象数据类型*
  > 对象数据类型是一组由逗号分隔、用花括号（`{}`）括起来的名称-值对

我们还讨论了以下关键概念：

- JSON 中布尔数据类型的值 true 或 false 始终为小写字符（即 true，而非 True 或 TRUE）。
- JSON 中 null 数据类型的值始终为小写字符（即 null，而非 NULL 或 Null）。
- 对象和数组之间的一个关键区别是，对象是一组名称-值对的列表或集合，而数组是一组值的列表或集合。
- 数组与对象之间的另一个关键区别是，数组中的值*应该*具有相同的数据类型。

## JSON Schema

在第 3 章中，我们介绍了 JSON 数据类型。讨论了数据类型的重要性和实用性。提前知道某物是什么以及它的用途是什么（记住那个拿着锤子的小孩）会带来巨大的不同。

在大多数数据交换格式的场景中，数据是为了通过网络或互联网发送给另一方而创建的。该方通常对其预期的文档有特定格式要求，包括结构和数据类型。他们通常会提供文档来解释格式并提供示例。

即使提供了最详尽、最精美的文档，在数据中创建错误也并非难事。需要明确的是，这里我们谈论的不是语法错误。这些是误解导致的错误，比如"我发送了一个苹果，而你期待的是一个橘子"。在本书中，我将这种验证称为*一致性验证*，以便将其与语法验证区分开来。

在这种场景中，流程通常如下列步骤进行：

1. 你完成了数据的创建，并感到自信满满。
2. 你将数据通过互联网发送给另一方。今天你的互联网连接很慢，而且发送的数据文件很大，所以花了好几分钟。
3. 你收到错误响应，因为你的数据格式不符合他们的预期。信心受挫。如果幸运的话，错误响应会告诉你一些有用的信息，比如你哪里做错了。
4. 你仔细研读他们的文档，找到你认为出错的地方，修复它，然后回到第 1 步。

自 JSON 出现之前，这种场景就已经存在于数据交换中了。幸运的是，科技行业的人们都是问题解决者，由此产生了 Schema 的概念。

## 附带验证魔法的契约

在现实世界中，我们经常在双方之间使用契约，当结果很重要时尤其如此。当我签署一份合同，承诺为某人完成一个项目时，细节都在那份合同中列明。我同意将在 8 月 31 日之前交付宇宙飞船，最终产品将是一艘功能齐全的宇宙飞船，配备生命支持系统、激光炮和三台引擎。

现在想象一下，我们生活在一个有巫师和魔法的世界。当我为项目工作的公司把合同交给我时，他们添加了一点魔法。在任何时候，我都可以用魔杖轻点合同，它就会告诉我是否已经履行了我的义务。我永远不必走进会议室宣称"我完成了！"然后遭遇尴尬的回应："你承诺要装在宇宙飞船上的第三台引擎呢？它在哪里？"在任何时候，我都可以验证我*真的*完成了项目，然后自信地走进会议室。

数据交换 Schema 非常像那个想象中的巫师和魔法世界。在发送数据之前，我们可以随时根据 Schema 验证其一致性，并查明我们的数据是否可被接受。当我们使用 Schema 交换数据时，流程与没有 Schema 的场景大不相同：

1. 你根据 Schema 验证数据的一致性，并修复发现的任何错误。你通常会获得关于错误的有用信息。
2. 你完成了数据的创建，并感到自信满满。
3. 你将数据通过互联网发送出去，然后收到成功响应。任务完成。

此外，JSON Schema 还可以由接收数据的交易另一方使用。JSON Schema 可以作为接受数据的*第一道防线*，验证数据是否符合规范。JSON Schema 可以在数据处理之前回答所有这些问题：

- *值的数据类型是否正确？*
  我们可以指定值必须是数值、字符串等。
- *是否包含了必需的数据？*
  我们可以指定哪些数据是必需的，哪些不是。
- *值的格式是否符合我的要求？*
  我们可以指定范围、最小值和最大值。

## JSON Schema 简介

虽然 JSON 已经相当成熟，JSON Schema 仍在开发中。截至 2015 年 4 月，JSON Schema 处于第四版草案阶段。这并不意味着你不应该使用 JSON Schema——这只是意味着它仍在不断演进，以更好地服务于世界。

JSON Schema 使用 JSON 编写，因此读写它只需几个步骤。在 JSON 的第一个名称-值对中，我们必须将其声明为 Schema 文档（示例 4-1）。

> 示例 4-1. 此声明的名称将始终为 "$schema"，值将始终为草案版本的链接

```
{
    "$schema": "http://json-schema.org/draft-04/schema#"
}
```

JSON Schema 文档中的第二个名称-值对将是标题（见示例 4-2）。

> 示例 4-2. 表示猫的文档格式

```
{
    "$schema": "http://json-schema.org/draft-04/schema#",
    "title": "Cat"
}
```

在 JSON Schema 文档的第三个名称-值对中，我们将定义希望包含在 JSON 中的属性。属性值本质上是我们想要的 JSON 的名称-值对的骨架。不是具体的值，而是一个定义数据类型的对象，并且可以选填描述（示例 4-3）。

> 示例 4-3. 为猫定义属性

```
{
    "$schema": "http://json-schema.org/draft-04/schema#",
    "title": "Cat",
    "properties": {
        "name": {
            "type": "string"
        },
        "age": {
            "type": "number",
            "description": "Your cat's age in years."
        },
        "declawed": {
            "type": "boolean"
        }
    }
}
```

这样我们就能验证我们的JSON是否符合JSON Schema（示例4-4）。

*示例4-4. 此JSON符合我们为"Cat"定义的JSON Schema*

```
{
  "name": "Fluffy",
  "age": 2,
  "declawed": false
}
```

先前我提到，JSON Schema可以回答以下问题：

*这些值的数据类型正确吗？*
我们可以指定一个值必须是数字、字符串等。

*这是否包含了所有必需的数据？*
我们可以指定哪些数据是必需的，哪些不是。

*这些值是否符合我要求的格式？*
我们可以指定范围、最小值和最大值。

通过这个非常简单的猫咪例子，第一个问题得到了解答。我们能够验证猫咪"Fluffy"的JSON数据中，name、age和declawed的值具有正确的数据类型。现在来回答第二个问题：这是否包含了所有必需的数据？

当我们请求数据时，通常有些属性（或字段）是我们必须提供值的，而其他的则是可选的。例如，当我在购物网站上创建一个新账户时，我需要填写一个收货地址表单。该地址表单要求我提供姓名、街道、城市、州和邮政编码。我还可以选择提供公司名称、公寓号码以及街道地址的第二行。如果我遗漏了任何一个必需的字段，我就无法继续完成账户创建。

为了在JSON Schema中实现这种必需逻辑，我们在 `$schema`、`title` 和 `properties` 之后添加了第四个键值对。这个键值对的名称是 "required"，其值是数组数据类型。该数组包含我们要求的字段。

在示例4-5中，我们首先添加了另一个字段 "description"。接着，我们添加了第四个键值对 "required"，其值是一个包含必需字段名称的数组。Name、age和declawed是必需的，所以我们将它们添加到这个列表中。我们省略了description，因为它不是必需的。

示例4-5. 填写必需字段

```
{
  "$schema": "http://json-schema.org/draft-04/schema#",
  "title": "Cat",
  "properties": {
    "name": {
      "type": "string"
    },
    "age": {
      "type": "number",
      "description": "Your cat's age in years."
    },
    "declawed": {
      "type": "boolean"
    },
    "description": {
      "type": "string"
    }
  },
  "required": [
    "name",
    "age",
    "declawed"
  ]
}
```

通过在JSON Schema中添加 "required"，示例4-6中的JSON就是有效的。此JSON符合我们为"Cat"定义的JSON Schema，其中包含了必需的字段：name、age和declawed。我们也包含了可选的键值对 "description"。

示例4-6. 有效的JSON

```
{
  "name": "Fluffy",
  "age": 2,
  "declawed": false,
  "description" : "Fluffy loves to sleep all day."
}
```

我们也可以省略description字段，因为它没有包含在必需字段的列表中。示例4-7中的JSON符合我们为"Cat"定义的JSON Schema，其中包含了必需的字段：name、age和declawed。

示例4-7. 不包含description字段的有效JSON

```
{
  "name": "Fluffy",
  "age": 2,
  "declawed": false
}
```

需要特别注意的是，如果你没有在JSON Schema中包含 "required" 键值对及其所需的名称数组，那么就没有任何字段是必需的。一个内部没有任何键值对的JSON对象也会被认为是有效的。没有 "required" 数组，示例4-8中的JSON对于"Cat"的JSON Schema来说是有效的。

示例4-8. 有效的JSON

```
{}
```

我们可以用JSON Schema回答的第三个也是最后一个问题：这些值是否符合我要求的格式？我们已经回答了关于值的数据类型的问题，但我们通常需要为类型指定特定的格式。例如，我需要一个用户名，但用户名不应超过20个字符。此外，我可能要求你提供一个介于10到100之间的数字。我们可以在JSON Schema中表达这些具体要求。

在猫咪JSON中，我们有这样的要求：name是字符串，age是数字。然而，我们不希望有人提供非常长的猫名、非常短的猫名，或者负数的猫龄。在我们的JSON Schema中，我们可以为字符串定义最小长度和最大长度，为数字定义最小值。

在示例4-9中，添加了验证以确保猫的名字至少3个字符，最多20个字符。此外，我们确保提交的猫咪年龄不是负数。

示例4-9. 验证猫咪JSON

```
{
    "$schema": "http://json-schema.org/draft-04/schema#",
    "title": "Cat",
    "properties": {
        "name": {
            "type": "string",
            "minLength": 3,
            "maxLength": 20
        },
        "age": {
            "type": "number",
            "description": "Your cat's age in years.",
            "minimum": 0
        },
        "declawed": {
            "type": "boolean"
        },
        "description": {
            "type": "string"
        }
    },
    "required": [
        "name",
        "age",
        "declawed"
    ]
}
```

示例4-10中的JSON对于猫咪JSON Schema是无效的，因为name的值超过了maxLength，而age的值小于minimum。

*示例4-10. 无效的JSON*

```
{
  "name": "Fluffy the greatest cat in the whole wide world",
  "age": -2,
  "declawed": false,
  "description" : "Fluffy loves to sleep all day."
}
```

示例4-11中的JSON对于猫咪JSON Schema是有效的，并且符合对值的要求。

*示例4-11. 此JSON是有效的*

```
{
  "name": "Fluffy",
  "age": 2,
  "declawed": false,
  "description" : "Fluffy loves to sleep all day."
}
```

如果我们回到Schema与合同的类比，你会看到我们合同的细节可以非常具体。本章提供的示例是入门级的，仅仅是冰山一角。JSON Schema甚至支持正则表达式（字符模式，如电子邮件地址）和枚举（可能值的列表）。如果你想成为JSON Schema大师，请访问 http://json-schema.org，在那里你可以找到规范的链接：

-   字段：data.name，错误：长度超过允许值，值："Fluffy the greatest cat in the whole wide world"
-   字段：data.age，错误：小于最小值，值：-2

如果我访问JSON Schema Validator网站，我也会看到同样的两个文本区域。再次，如果我将示例4-9中的Schema和示例4-10中的JSON粘贴进去，我会看到错误。此外，JSON的行号会显示一个红色的叉，向我们展示错误在JSON中的位置。

-   消息：字符串 'Fluffy the greatest cat in the whole wide world' 超过最大长度 20，Schema路径：#/properties/name/maxLength

JSON Schema Validator不仅指出了错误发生的行号，还给出了导致验证失败的Schema要求的路径。这两个验证器对错误的描述可能略有不同，但它们都找到了相同的错误。

## JSON 安全问题

JSON 本身威胁不大。毕竟，它只是一种数据交换格式。其本身只是一份文档或数据流。真正的安全问题源于 JSON 的使用方式。本章将探讨 Web 上 JSON 最常见的两种安全问题：跨站请求伪造和跨站脚本攻击。

在深入讨论安全问题并进入本书剩余章节之前，我们需要理解客户端与服务器端的关系。对于尚未理解此概念的读者，我们先快速了解一下这些关系。

- JSON Schema 可以回答以下三个问题以进行合规性验证：
  - *值的数据类型正确吗？*
    我们可以指定一个值必须是数字、字符串等。
  - *是否包含必需的数据？*
    我们可以指定哪些数据是必需的，哪些不是。
  - *值是否符合我要求的格式？*
    我们可以指定范围、最小值和最大值。

## 快速了解客户端与服务器端关系

抵达皮埃尔高级餐厅用晚餐时，我在一张可爱的桌子旁坐下，餐巾被折成了天鹅形状。一位穿着休闲裤和漂亮衬衫的高个子男子走近桌子，说道：“我叫托马斯，今晚由我为您服务。”认出我后，他压低声音说：“顺便说一句，您是我最喜欢的顾客之一。”他挑了挑眉毛说：“这是我们的特色菜单。”

浏览完特色菜单后，我告诉托马斯我想要的晚餐，过了一会儿，他把餐点端上了桌。我享用了一顿美好的晚餐，后来为那些摆盘艺术的小份食物支付了200美元。这又是在皮埃尔高级餐厅的一个美好夜晚，托马斯是服务员，而我是顾客。

您的互联网浏览器与网站之间的关系，就像我与皮埃尔高级餐厅的关系一样。这种关系是一个繁忙的*请求*和*响应*世界。我请求一盘食物，厨房通过制作我特别请求的食物并将其送出作为响应。

当您访问最喜欢的网站查看可爱的小猫图片时，您电脑上的互联网浏览器就是客户端，而托管可爱小猫图片的计算机就是服务器。您的互联网浏览器发出请求，该请求在互联网上流转，直到可爱小猫图片网站背后的计算机接收到它。可爱小猫网站随后以响应的形式提供页面，该响应通过互联网发回，您的浏览器将其渲染在屏幕上。

在这种关系中，我们划定一条界限：可爱小猫图片网站以响应形式发送的所有内容，由浏览器处理的部分称为客户端代码。在餐厅示例中，响应将是那盘食物，而我坐的桌子就是互联网浏览器。桌子接收食物，现在我能看到它并享用它。

然后我们说，在该响应页面发送之前发生的所有事情，本质上是其创建过程，就是服务器端代码。在餐厅示例中，服务器端代码将是厨房里发生的一切。我从不进入厨房，也看不到他们在里面如何制作我的餐盘。餐厅示例与现实世界之间一个微妙的区别是，服务器并不是那个在厨房和桌子之间来回跑的人。厨房是服务器，而那个人是互联网。

公众看不到可爱小猫图片网站在其隐喻的厨房里在做什么。该网站可能使用 PHP、ASP .NET 或任何其他编程语言。无论它在厨房里使用什么，只要网站提供包含客户端代码的响应，对我的浏览器来说都无关紧要。

我从网站获得的响应是 HTML、CSS 和 JavaScript 的组合。就像我可以在餐厅检查桌子上的一切一样，我可以在浏览器中按 F12，使用开发人员工具查看页面的所有 HTML、CSS 和 JavaScript。我甚至可以看到那个烦人的闪烁弹出窗口（里面有跳舞的小猫）的 JavaScript 代码。

客户端是指用户互联网浏览器中发生的一切，服务器端是指网站托管的服务器上发生的一切。当提到客户端代码时，通常指 JavaScript、HTML 或 CSS。当提到服务器端代码时，通常指服务器端语言，如 ASP.NET、Ruby on Rails 或 Java。

现在让我们看看安全这个重要课题。

## 跨站请求伪造 (CSRF)

跨站请求伪造，或称 CSRF（发音为 sea-surf），是一种利用网站对用户互联网浏览器的信任进行的攻击。CSRF 漏洞由来已久，远在 JSON 出现之前就已存在。

一个涉及 JSON 的 CSRF 攻击示例如下。您登录了一个银行网站。该网站有一个包含您一些敏感信息的 JSON URL（示例 5-1）。

> 示例 5-1。您的 JSON 格式的敏感信息：

```json
[
  {
    "user": "bobbarker"
  },
  {
    "phone": "555-555-5555"
  }
]
```

您可能会想，“嘿，这个 JSON 缺少了花括号！” 这是有效的 JSON。但危险的有效 JSON，因为它也是一个有效的 JavaScript 脚本。这被称为*顶层 JSON 数组*。

该银行网站示例使用会话 Cookie 进行身份验证，以确保这些信息仅提供给您——已登录的注册用户。

这个示例中的坏蛋找到了银行网站上敏感 JSON 数据的 URL，并将其放入他自己网站上的一个 script 标签中。如果您不确定 script 标签是什么，可以在大多数现代网页的幕后找到它们。这称为代码后置，它是一个 HTML 文档。如果您访问最喜欢的网站，右键单击并选择“查看源代码”，您应该会找到一个或多个看起来像示例 5-2 中所示的标签。

> 示例 5-2。script 标签示例（此标签中的“src”属性指定了脚本的位置）

```html
<script src="https://code.jquery.com/jquery-2.1.4.min.js"></script>
```

互联网浏览器有关于不同域名网站（*http://domainone.com* 和 *http://domaintwo.com* 是不同的域名）之间共享的规则。坏蛋使用 script 标签，因为它豁免于这些共享规则（示例 5-3）。通常有必要且正常地使用托管在另一个网站上的脚本，因此 script 标签获得例外。JSON 使用的是顶级数组，使其成为有效的 JavaScript，因此他得逞了。

> 示例 5-3。坏蛋网站上的 script 标签可能是什么样子的示例

```html
<script src="https://www.yourspecialbank.com/user.json"></script>
```

此攻击能够成功的一个关键点是您与银行网站的关系。没有这种关系，script 标签中的链接就不会返回敏感数据。该链接不仅仅是托管您的敏感数据。它是一个动态链接，为已登录的成员返回敏感数据。当您登录银行时，您已经建立了一种信任关系，银行相信您就是您所声称的那个人。

这种攻击依赖于这种信任。为了利用这种信任，坏蛋需要您在他拥有该窃取 script 标签的网站上，并且同时您已登录到您的银行。为了实现这一点，坏蛋可能会向人们发送一百万封电子邮件，内容是“您的银行网站上有一条重要信息给您。”这些电子邮件通常会格式化成与人们熟悉的银行（或他们试图利用的网站）的电子邮件完全一样。如果他们不检查邮件头查看发件人是谁，或者不将鼠标悬停在链接上确认是否指向他们信任网站的真实域名，那么他们很可能会点击它。

例如，假设您生病了，头脑不清醒，所以点击了该链接。此外，您上次离开银行网站时没有注销，因此您的会话仍然存在。您目前处于与银行的信任关系状态。一旦加载到坏蛋网站的页面，您可能会意识到自己到了一个奇怪的地方然后离开。但为时已晚。坏蛋的网站已经能够检索到敏感的 JSON 数据，将其发送回自己的服务器并保存起来。糟糕。

银行及其 Web 开发人员本可以做些什么不同的事情来防止 CSRF 攻击？

首先，银行本可以将数组转换为 JSON 对象中的一个值。这将使其成为无效的 JavaScript。参见示例 5-4。

> 示例 5-4。通过将数组包装在对象中，它不再是可以在 script 标签中加载的有效 JavaScript

```json
{
    "info": [
        {
            "user": "bobbarker"
        },
        {
            "phone": "555-555-5555"
        }
    ]
}
```

另外，如果银行只允许 POST 请求而不是 GET 请求来检索敏感的 JSON，那么坏蛋就无法使用他 URL 中的链接。GET 和 POST 是两种用于与服务器通信的 HTTP 方法。GET 是请求数据，可以返回响应。POST 是提交数据，也可以...



## 注入攻击

注入攻击形式多样。归根结底，它们都依赖于寻找安全漏洞。刚才讲到的 CSRF 攻击是利用信任的攻击，而*注入攻击*则是利用将恶意代码注入看似无害网站的能力。

### 跨站脚本攻击 (XSS)

跨站脚本攻击 (XSS) 是一种注入攻击。JSON 相关的安全漏洞常出现在 JavaScript 获取 JSON 字符串并将其转换为 JavaScript 对象的过程中。

请记住，JSON 本身只是文本。在编程中，若要利用该对象的文本表示做有用的事，就需要将其作为对象加载到内存中，然后才能进行操作、检查和用于编程逻辑。

在 JavaScript 中，一种方法是使用名为 eval() 的函数。eval() 函数接收一个字符串，编译它，然后执行它。

示例 5-5 中，JavaScript 代码使用 eval() 函数将 animal-cat 对象加载到内存中，随后代码即可访问该对象的属性。第三行的 alert 将弹出浏览器警告框，显示 "cat"。

### 示例 5-5. 访问对象属性

```
var jsonString = '{"animal":"cat"}';
var myObject = eval("(" + jsonString + ")");
alert(myObject.animal);
```

示例 5-5 相对无害，因为 JSON 直接包含在代码中。通常 JSON 来自其他服务器，而该服务器往往是第三方服务器，我们无法控制。例如，若我向 Facebook 的服务器请求 JSON，我无法控制它返回的内容。如果服务器被攻陷或 JSON 被拦截，我可能接收恶意代码。

eval() 函数的问题在于它不加区分地接收字符串、编译并执行。如果我的 JSON 来自第三方服务器并被替换为恶意脚本，那么我完全无害的网站将在访问者的浏览器中编译并执行这段恶意代码。

示例 5-6 的 JavaScript 代码中，我已将 JSON 字符串替换为一段 JavaScript。当代码运行时，eval() 函数将执行并显示警告框，内容为 "this is bad"。

### 示例 5-6. eval() 函数的警告

```
var jsonString = "alert('this is bad')";
var myObject = eval("(" + jsonString + ")");
alert(myObject.animal);
```

随着 JSON 多年发展，这一漏洞已被识别。JSON.parse() 函数通过选择性解析来解决此漏洞。该函数仅解析 JSON，不执行脚本。示例 5-7 用 JSON.parse() 替换了 eval()。

### 示例 5-7. 用 JSON.parse() 替换 eval()

```
var jsonString = '{"animal":"cat"}';
var myObject = JSON.parse(jsonString);
alert(myObject.animal);
```

在 Web 开发中，另一个常与安全性同等重要的考量是跨浏览器支持。随着 Web 发展，网站托管者必须决定支持哪些浏览器及版本。本质上，他们需要决定放弃谁。总会有人不更新浏览器，或使用未能跟上演进标准的冷门浏览器。

更安全的 JSON.parse() 函数目前在所有主流浏览器及最新版本中都受支持。然而，一些早期浏览器版本（少量用户仍在使用）不支持此函数。如果使用了 JSON.parse()，这部分用户将无法使用依赖 JSON 的网站功能。通常通过优雅降级来处理，例如捕获错误并显示"请更新浏览器到最新版本"的消息，而非让页面充满错误。

### 安全漏洞：架构决策

本章开头我提到"JSON 本身不是威胁"。这仍然成立，但某些情况下威胁可直接包含在 JSON 数据中，同时保持有效的 JSON 格式。

让我们看一些完全无害的 JSON（示例 5-8）。

*示例 5-8. 完全无害的 JSON*

```
{
    "message": "hello world!"
}
```

现在假设我运营一个网站，将消息存储在数据库中，然后显示在网页上供用户阅读。我从未听说过此漏洞，因此我的页面允许用户向其他用户发送包含任何内容的消息。在我的消息页面中，我从服务器请求 JSON 字符串，客户端使用 eval() JavaScript 函数将 JSON 字符串响应转换为 JavaScript 对象，并在客户端代码中使用该对象将消息值直接显示在 HTML 中。

现在看看示例 5-9 中一些不那么无害的 JSON。

*示例 5-9. 不那么无害的 JSON*

```
{
    "message": "<div onmouseover=\"alert('gotcha!')\">hover here.</div>"
}
```

示例中的不那么无害的 JSON 包含了 JavaScript。虽然这段 JavaScript 位于 JSON 名称-值对的范围内，但它只是一段文本字符串。这是完全有效的 JSON，在许多地方使用都不会构成威胁。

然而，当示例中的 JavaScript 在消息网站的 HTML 中输出时，它就成了威胁。这里展示的"不那么无害的 JSON"会导致每次用户将鼠标悬停在屏幕上的消息上时，弹出警告框显示 "gotcha"。问题在于，比弹出警告框更严重的事情也可能发生。攻击者可能包含一段脚本，访问页面上所有你的私有消息，并将其发送到他自己的服务器上阅读。

我本可以采取什么措施来防止这种情况？首先，我可以禁止消息中包含 HTML。这涉及客户端和服务器端的验证。此外，我可以确保消息中包含的任何 HTML 字符都被转义，这样 HTML 字符如 <div> 将在页面上显示为 &lt;div&gt;（&lt;div&gt; 不会作为有效的 HTML 发挥作用）。所有这些措施都应针对我架构中使用的客户端和服务器端代码。

大多数注入攻击涉及的架构在构建时没有考虑到一个关键问题：攻击者如何利用它？允许 HTML 存在于 JSON 中并直接将值显示在页面上的决定，看似无害。在避免注入攻击时，关键是考虑可能的利用方式，并采取额外（有时是繁琐的）步骤来预防它们。

## 关键术语和概念

本章涵盖了以下关键术语：

- **服务器端（在 Web 开发中）**：在请求页面或资源的服务器后台进行的操作。服务器提供响应，由 Internet 浏览器处理和/或加载。

- **客户端（在 Web 开发中）**：从请求的页面被加载起，在 Internet 浏览器中进行的操作。这通常是 HTML、CSS 和 JavaScript。

- **跨站请求伪造 (CSRF)**：利用网站对用户浏览器信任的漏洞利用攻击。

- **顶级 JSON 数组**：存在于名称-值对之外且位于文档顶级的 JSON 数组。

- **注入攻击**：通过向 Web 应用程序注入数据以协助执行或解释恶意数据的攻击。

- **JSON 跨站脚本攻击 (XSS)**：一种注入攻击，通过拦截或替换第三方提供给网站的 JSON 为恶意脚本，从而利用无害的网站。

我们还讨论了以下关键概念：

- JSON 本身并不构成威胁。它只是文本。
- 关于 JSON 安全性问题，有三点需要记住：
  - 不要使用顶级数组。顶级数组是有效的 JavaScript，可以通过 `<script>` 标签链接并使用。
  - 对于不面向公众的 JSON，应使用 HTTP POST 而非 GET。HTTP GET 请求可以在 URL 中链接并放入 script 标签。
  - 使用 `JSON.parse()` 而非 `eval()`。`eval()` 函数会编译并执行传入的字符串，这会使代码暴露在攻击风险之下。`JSON.parse()` 仅解析 JSON。
- 安全漏洞往往源于架构决策，而这些决策没有提出最基本的问题："坏人如何利用这一点？"

## JavaScript XMLHttpRequest 与 Web API

JavaScript XMLHttpRequest 和 Web API 这个名称或许很难快速连说三遍，但实际上并不像听起来那么复杂。它就是一个简单的客户端与服务器关系。JavaScript XMLHttpRequest 是发出请求的客户端，Web API 则是发送响应的服务器。

在上一章讨论的客户端-服务器餐厅示例中，我将服务器比作厨房，客户端比作顾客。本章将聚焦于一种特定的"厨房"及其运作方式。

不言而喻，并非所有餐厅都以相同方式运营。有些餐厅可以驾车到窗口点餐；有些餐厅对公众开放，有些则可能只是大型企业园区内的食堂。

我们大多数人参与的一种客户端-服务器关系就是上网冲浪。我们常常以为自己是在互联网中旅行或探索。实际上，我们通常只是坐着盯着屏幕。互联网浏览器本身也不会去任何地方。它只是原地不动，就像餐厅里的一张桌子，发出请求并接收响应。一旦服务器给出响应，它就与我们无关了，转而去处理其他实体的请求。

互联网浏览器发出的请求是为了获取资源。当我们"上网冲浪"时，我们要么点击带有 URL 的链接，要么直接在浏览器中输入 URL。URL 代表统一资源定位符（Universal Resource Locator）。我们在浏览互联网时使用的 URL 用于定位 HTML 资源，这让我们能够看到网站，包括那些展示可爱猫咪图片的网站。在这种情况下，我们请求的资源内容类型为 `text/html`。

另一种不直接涉及人类的客户端-服务器关系是 Web API。Web API 和网站一样通过 HTTP 提供内容，但它并非为人类阅读而设计。你可以将其视为面向代码的餐厅，因为向这些服务器发出请求的主体大多是代码。

编程代码通常不会像人类那样去查看可爱的猫咪图片。它的"胃口"通常由请求数据组成。本章讨论的是一种请求 JSON（内容类型为 `application/json` 的资源）的客户端类型，以及为这些顾客提供服务的"餐厅"类型：Web API。

让我们先来看看 Web API，以及 JSON 在 Web API 中扮演的角色。

### JavaScript XMLHttpRequest

尽管 JavaScript XMLHttpRequest 听起来似乎与 XML 有关，但我们用它来发起 HTTP 请求。在它命名时夹带 XML 的年代，XML 正是这类请求的当红数据交换格式。然而，XMLHttpRequest*并不*局限于 XML。尽管名字如此，我们仍用它来获取 JSON。

前面，我多次以"获取资源的代码"开头。JavaScript XMLHttpRequest 就是一种获取资源的代码。这种表述在谈论 HTTP 请求时很常见，尽管实际上代码并不会像狗追球一样在网络空间中穿梭。代码就待在自己的位置上，礼貌地请求资源被交付。

如果我们回到餐厅示例，可以想象 JavaScript 代码坐在餐厅的桌子旁。JavaScript 代码不会去厨房请求 JSON，也不会在餐厅里大喊大叫。餐厅有其规矩。这种规矩要求你召唤服务员，服务员记下你的订单并将其送到厨房。

同样存在允许代码向可能数百或数千英里外的 Web 服务器发送请求的协议。让我们能够访问喜爱网站的数据通信基础是一个名为*超文本传输协议（HyperText Transfer Protocol，HTTP）*的协议。当我们在浏览器中输入 `http://www.cutelittlekittens.com` 时，我们就在使用超文本传输协议来请求资源。对于那个可爱的猫咪网站来说，该资源是嵌入了可爱猫咪图片的 HTML 页面。需要请求 JSON 资源的代码使用同样的协议（HTTP）。

在 JavaScript 中，使用该协议来发起请求的代码就是 XMLHttpRequest。JavaScript 是一种面向对象的语言，因此 XMLHttpRequest 自然也是一个对象。一旦使用 `new XMLHttpRequest()` 语法创建（示例 6-3），并将其赋值给一个变量，它就拥有了可以调用的函数来从某个位置请求资源。

> 示例 6-3. JavaScript XMLHttpRequest 对象

```javascript
var myXmlHttpRequest = new XMLHttpRequest();
```

XMLHttpRequest 是一个对象，示例 6-3 展示了创建新的 XMLHttpRequest 对象的过程。即使你不了解 JavaScript，如果你已经读到这里，你对 JSON 的了解也会帮助你想象 JavaScript 对象的样子。毕竟，JSON 正是基于 JavaScript 对象的字面量表示法。

我们说一个 JavaScript 对象拥有属性。这些"属性"本质上就是名值对。XMLHttpRequest 的属性分别为：onreadystatechange、readyState、response、responseText、responseType、responseXML、status、statusText、timeout、ontimeout、upload 和 withCredentials。注意这些属性的命名大小写并不统一。有些使用驼峰命名法，有些则全部小写。如果你将来打算编写自己的 XMLHttpRequest 代码，这可能会让你抓狂，因为你不仅需要记住属性的名称，还要注意不同的大小写。

编程中典型对象与 JSON 对象之间的一个关键区别在于，JSON 不包含可执行指令。JSON 仅由属性组成，因为它是用于数据交换的。编程中的典型对象还会包含函数（或方法）。例如，我可以用 JSON 以名值对的形式来描述我的鞋子，比如：颜色-粉色，品牌-crocs。我无法在 JSON 中做到的是通过调用函数（或方法）让这双鞋动起来，比如 shoe.walk()。

我们最关心的 XMLHttpRequest 可用函数有：

-   open(*method, url, async（可选）, user（可选）, password（可选）*)
-   send()

我们最关心的 XMLHttpRequest 可用属性有：

***onreadystatechange***

其值为一个我们可以在代码中定义的函数。

***readyState***

返回一个 0–4 之间的值，代表状态码。

***status***

返回 HTTP 状态码（例如 200 表示成功）。

***responseText***

当响应成功时，此属性包含以文本形式表示的响应正文（如果我们请求的是 JSON，则此处为 JSON）。

对于不熟悉 JavaScript 的读者来说，下面这个概念可能会让你感到困惑：一个属性的值可以是一个函数。这在 JavaScript 中是可行的，因为函数本身就是对象。对象是一种数据类型，因此可以赋值给变量（属性）、修改和传递。在编程世界中，这被称为一等函数。onreadystatechange 属性的值就是一个函数。

[示例 6-4](#) 创建了一个新的 XMLHttpRequest 对象，并从 Open Weather Map API 获取 JSON 数据。

## 示例 6-4. 一个新的 XMLHttpRequest 对象

```
var myXMLHttpRequest = new XMLHttpRequest();
var url = "http://api.openweathermap.org/data/2.5/weather?lat=35&lon=139";

myXMLHttpRequest.onreadystatechange = function() {
    if (myXMLHttpRequest.readyState === 4 && myXMLHttpRequest.status === 200) {
        var myObject = JSON.parse(myXMLHttpRequest.responseText);
        var myJSON = JSON.stringify(myObject);
    }
}
myXMLHttpRequest.open("GET", url, true);
myXMLHttpRequest.send();
```

在该示例中，代码的第二行创建了一个包含 JSON 资源 URL 的变量。然后我创建了一个函数并将其赋值给 myXMLHttpRequest 的 onreadystatechange 属性。每当 readyState 属性发生变化时，这个函数都会被执行。在函数内部，我检查 readyState 是否为 4（"完成"的代码）以及 HTTP 状态码是否为 200（表示成功的代码）。如果这两个条件都满足，我就将 JSON 解析为 JSON 对象。

当 JSON 从对象转换为文本，再从文本转换回对象时，你会经常听到两个术语：*序列化*和*反序列化*。序列化是将对象转换为文本的行为。反序列化是将文本转换回对象的行为。

在示例 6-5 中，JavaScript 使用 JSON.parse 进行反序列化。在 responseText 中，JSON 仅仅是作为数据交换格式的文本。一旦经过 JSON.parse 解析，它就不再是 JSON，而是一个 JavaScript 对象。

## 示例 6-5. 反序列化

```
var myJSON = JSON.parse(myXMLHttpRequest.responseText);
```

使用 JSON.parse 进行反序列化是必要的，因为 JSON 此时还不是对象。请记住，JSON 代表 JavaScript Object *Notation*（JavaScript 对象表示法）。当它处于 JSON 形式时，它是以文本形式对对象的字面表示。要使 JSON 成为真正的对象，必须对其进行反序列化。在 JavaScript 中，我们也可以使用 JSON.stringify() 对 JSON 进行序列化。

在示例 6-6 中，myObject 变量获得了反序列化后的 JSON。此时它是一个对象。myJSON 变量获得了序列化后的对象。此时它是 JSON。

## 示例 6-6. 对象先反序列化再序列化

```
// JSON 响应反序列化
var myObject = JSON.parse(myXMLHttpRequest.responseText);
// 对象序列化
var myJSON = JSON.stringify(myObject);
```

最后，我示例中的最后两行代码设置了请求，然后通过 HTTP 协议发送出去（示例 6-7）。

*示例 6-7. JSON 请求的设置和发送*

```
myXMLHttpRequest.open("GET", url, true);
myXMLHttpRequest.send();
```

你可能会觉得奇怪，处理 JSON 响应的代码居然出现在请求发送之前。我甚至在介绍请求的设置和发送之前就讨论了它。onreadystatechange 属性的函数值是一个事件处理器。底层的 JavaScript 引擎（不是我的代码）拥有相应的逻辑，每次 ready 状态发生变化时都会访问该属性的值（我的函数）。ready 状态从 0 到 4 分别为：

- *0 代表* **UNSENT（未发送）**
    执行 open() 函数之前的状态
- *1 代表* **OPENED（已打开）**
    执行 open() 函数之后但在执行 send() 函数之前的状态
- *2 代表* **HEADERS_RECEIVED（已接收响应头）**
    执行 send() 函数之后，响应头和状态码可用的状态
- *3 代表* **LOADING（加载中）**
    响应头已接收，但响应正文仍在获取中
- *4 代表* **DONE（完成）**
    完成；已收到包含响应头和响应正文的完整消息

> 处理 ready 状态的状态码可能看起来令人困惑。在第 7 章中，我们将看到如何使用 jQuery 简化 XMLHttpRequest。通过 jQuery，我们可以使用简单的 getJSON() 函数获取 JSON，并以更易读的方式处理状态：done()、fail()、always()。

![](img/b559c72bd38b5be05c7e1fe3e7ae3b60_69_0.png)

在我的示例中，我使用了一个属于 Open Weather Map API 的 URL。这是一个通过 API 提供天气数据的网络服务。该 API 为各种天气数据提供了 XML 和 JSON 资源的 URL。我的示例展示了如何在客户端使用 JavaScript 从该 API 请求和接收 JSON。然而，出于安全考虑，互联网浏览器对资源共享有相关规则。同源策略规定，一个网站只能与同一域名下的站点进行此类后台请求。这是为了保护用户，因为除非他们了解互联网浏览器的开发者工具，否则他们无法*看到*这些请求的发生。

我示例中分享的代码可以在 URL 为 *http://www.mycoolsite.com* 的网站上的脚本中执行。这是原始域，因为它是原始请求的 URL。API 的 URL 为：

```
http://api.openweathermap.org/data/2.5/weather?lat=35&lon=139
```

域 *http://api.openweathermap.org* 与原始域 *http://www.mycoolsite.com* 不匹配。这明显违反了同源策略。这种后台请求和响应之所以能够实现，是因为 Open Weather Map API 的开发者费尽周折地绕过了一些限制。让我们来看看这些曲折的路径和漏洞，了解公共 API 的幕后请求是如何实现的。

## 跨域资源共享（CORS）

有些 Web 开发者可能写了很多年的 JavaScript AJAX 代码，从公共 Web API 发起请求，却从未遇到过同源策略的问题。这是因为大多数公共 API 都已经在自己的服务器上实现了 CORS。服务器在响应头中提供一些以"Access-Control-Allow"为前缀的额外属性（示例 6-8）。

*示例 6-8. Open Weather Map API 对资源 http://api.openweathermap.org/data/2.5/weather?lat=35&lon=139 响应中的 Access Control Allow 头*

```
Access-Control-Allow-Credentials:true
Access-Control-Allow-Methods:GET, POST
Access-Control-Allow-Origin:*
```

这些头定义了是否允许凭证、允许使用哪些 HTTP 方法（GET、POST、PUT、DELETE、HEAD、OPTIONS、TRACE、CONNECT），以及最重要的是，允许哪些源域。在该示例中，提供了星号（*）。这是一个通配符，表示允许任何源域。



CORS 使得像 Open Weather Map API 这样的网站能够以特定方式共享其数据，允许用户在客户端通过 AJAX 交互来使用这些数据。此外，CORS 还可以用来阻止网站对 API 进行恶意操作，例如 CSRF。如果你还记得第 5 章中的示例，一个坏人能够通过在 script 标签中链接 JSON 来利用银行网站的信任。银行可以采取的一种安全措施是实现 CORS，并在其响应中包含示例 6-9 所示的响应头。

> 示例 6-9. 将 CORS 用作安全措施

```
Access-Control-Allow-Methods:POST
Access-Control-Allow-Origin:http://www.somebank.com
```

在这个示例中，POST 是唯一允许的方法。如果有人试图通过 URL 在 script 标签中请求此资源（使用 GET 方法），浏览器将不允许这样做。此外，通过指定银行网站的来源 URL，Internet 浏览器将拒绝除 *http://www.somebank.com* 之外的任何网站访问。

实现 CORS 并不总是可行的，而且 JSON 并不总是由成熟的 Web API 托管。假设你有两个不同域名的网站（*http://domainone.com* 和 *http://domaintwo.com*），你想要从 *http://domainone.com* 共享一个 JSON 文件到 *http://domaintwo.com*。这就是 JSONP 的用武之地。

## JSON-P

JSON-P 代表 **JSON with padding**（带填充的 JSON）。我在第 5 章中提到过，`<script>` 标签不受同源策略的限制。JSON-P 利用这一豁免来从不同源的服务器请求 JSON。

JSON-P 不如 CORS 理想，因为它被归类为一种变通方法（CORS 是首选方法，因为它是一种标准）。然而，当形势所迫时，有时这样的变通方法是必要的。你需要在 *http://domainone.com* 和 *http://domaintwo.com* 之间建立关系，而当 CORS 不可行时，浏览器关于共享的规则可能会让这变得很棘手。

JSON-P 中的"填充"非常简单。它就是添加到 JSON 文档中的 JavaScript。参见示例 6-10。

> 示例 6-10. 带填充的 JSON（JSON-P）

```
getTheAnimal(
    {
        "animal": "cat"
    }
);
```

此 JSON 文档中的 JavaScript "填充"是对一个函数的调用，JSON 作为参数传递给该函数。函数参数提供了一种将数据传入函数的方式。例如，如果我想要一个将两个数字相加的函数，我需要一种方式将这两个数字传入函数。

这个函数在我们的客户端代码中定义，在我们的 JavaScript 中（示例 6-11）。

> 示例 6-11. 在我们的 JavaScript 中声明的函数

```
function getTheAnimal(data) {
    var myAnimal = data.animal; // will be "cat"
}
```

在函数声明之后，还需要一些设置。这是 JSON-P 利用 `<script>` 标签不受同源策略限制的部分。参见示例 6-12。

> 示例 6-12. 在 head 标签之后动态创建并附加到 HTML 文档的 script 标签

```
var script = document.createElement("script");
script.type = "text/javascript";
script.src = "http://notarealdomain.com/animal.json";
document.getElementsByTagName('head')[0].appendChild(script);
```

对于实现 JSON-P 的服务器，通常还允许用户决定函数的名称。这通常通过 URL 中的查询字符串参数传递。参见示例 6-13。

> 示例 6-13. 通过查询字符串向服务器传递的函数名称

```
script.src = "http://notarealdomain.com/animal.json?callback=getThing";
```

服务器会接收我在 callback 中的函数名，并动态生成 JSON 文件中的填充。参见示例 6-14。

> 示例 6-14. JSON 填充中动态命名的函数

```
getThing(
    {
        "animal": "cat"
    }
);
```

JSON-P 仍然需要服务器端的努力，因为 JSON 资源必须包含 JavaScript 填充。CORS 和 JSON-P 都需要服务器端的努力。因此，客户端的跨域 XMLHttpRequest 能否成功，取决于 JSON 资源的服务器。

## 关键术语和概念

本章涵盖了以下关键术语：

- **Web API**：一组通过 HTTP 与服务交互的指令和标准
- **XMLHttpRequest**：一个 JavaScript 对象，主要用于 AJAX 编程，用于从 URL 检索数据而无需重新加载页面
- **超文本传输协议（HTTP）**：万维网数据通信基础协议
- **序列化**：将对象转换为文本的行为
- **反序列化**：将序列化的文本转换回对象的行为
- **同源策略**：Internet 浏览器要求脚本必须来自同一域名以确保安全
- **跨域资源共享（CORS）**：通过在响应头中定义权限，允许从请求域之外的另一个域请求资源（例如 JSON 文档）
- **带填充的 JSON（JSON-P）**：利用 `<script>` 标签不受同源策略限制，从不同源的服务器请求 JSON

我们还讨论了以下关键概念：

- JavaScript XMLHttpRequest 与 Web API 之间的关系是客户端-服务器关系。
- XMLHttpRequest 不仅用于 XML。我们也用它来请求 JSON 资源。
- 网站面向人类，Web API 面向代码。两者都通过 HTTP 提供资源。
- 同源策略可能导致 JavaScript 与 JSON 资源之间的客户端-服务器交互关系出现问题。
- 客户端的跨域 XMLHttpRequest 能否成功，取决于 JSON 资源的服务器。

## JSON 与客户端框架

在 *第 6 章* 中，我们了解了 Web 浏览器与 Web API 之间的客户端-服务器关系。在本章中，我们将镜头聚焦到该关系的客户端，看看一些客户端框架是如何支持或利用 JSON 的。

我们先快速了解一下什么是框架，对于不熟悉这个概念的人来说。在现实世界中，"框架"可以用来描述一个基本的支撑结构，或一个底层结构。在计算领域，框架不是底层结构。它是位于软件或编程语言之上的一层结构，为开发人员提供支持。

计算中的框架是一个支撑结构，但不能把它类比为建筑物的横梁。如果语义化的 JavaScript 语言是一座房子，JavaScript 框架不会是这个建筑物的支撑结构。事实上，你可以在没有 JavaScript 框架的情况下建造一座非常坚固的房子。

如果我们从事用 JavaScript 建造房屋的业务，JavaScript 框架就像订购一套已经包含管道和电线设施的预制房屋。有了我们的预制房屋，我们可以专注于创建任何类型的厨房水槽，而通水只需将水槽连接到管道即可。我们可以专注于安装漂亮的橱柜和美丽的花岗岩台面。本质上，我们的 JavaScript 框架让你能够节省时间并专注于构建功能。

这种节省时间和集中精力的框架在计算机科学中被称为**抽象工具**。对于不熟悉抽象概念的人来说，它可能会让人联想到毕加索的艺术，那些由形状构成的奇怪面孔。抽象不是复杂的艺术，而是一种处理复杂系统的技术。

如果你被要求建造一艘宇宙飞船，而从未有过火箭科学的经验，你会从哪里开始？我们大多数人会说"显然我不是这份工作的最佳人选"，但如果你别无选择呢？你可以直面那个复杂的任务并觉得它不可能完成。你可以恐慌并把自己锁在房间里。或者，你可以使用**抽象**。

通过抽象，你一次专注于整个拼图的一块。我们将建造宇宙飞船的任务分解为所有基本部分，例如在飞船上支持人类生命或将飞船发射到外太空。我们专注于复杂系统的每个部分，直到系统完整。

**抽象工具**是任何促进抽象的工具。JavaScript 框架通过预先构建的库来促进抽象，这些库已经处理了系统中的复杂性。我们不能用 JavaScript 框架建造真正的宇宙飞船，但如果可以的话，那个框架可能包含一艘已经能够发射到太空的飞船。这将使造船者能够专注于他们如何支持飞船内的人类生命。

## jQuery 与 JSON

jQuery 是一个抽象工具，它允许开发人员通过专注于操作 HTML 文档对象模型（DOM）来构建功能。这是一种与 HTML 页面交互的约定。在此模型中，底层 HTML 被视为一个对象和一组可以枚举、访问和操作的节点。

在没有 jQuery 框架的情况下，JavaScript 操作 DOM 也是可能的。然而，开发人员经常需要对 DOM 执行一些操作，这些操作需要多行代码。例如，操作 DOM 的一个常见操作是隐藏 HTML 元素。假设我有一个按钮想要隐藏（示例 7-1）。

*示例 7-1. 在 Web 浏览器中显示文本 "My Button" 的 HTML 按钮*

```
<button id="myButton">My Button</button>
```



如[示例 7-2](#)所示，为了实现用 JavaScript 隐藏按钮的目标，我必须在 HTML 文档对象上调用函数 `getElementById(*id*)`，然后将 `style.display` 属性设置为 "none"。

> *示例 7-2。这行 JavaScript 会隐藏 id 为 "myButton" 的 HTML 按钮；它将不会在浏览器中显示。*

```javascript
document.getElementById("myButton").style.display = "none";
```

jQuery 用不到一半的代码字符量实现了同样的目标（[示例 7-3](#)）。

> *示例 7-3。这行 jQuery 会隐藏 id 为 "myButton" 的 HTML 按钮；它将不会在浏览器中显示。*

```javascript
$("#myButton").hide();
```

只需输入不到一半的字符就能实现相同的目标，这节省了开发时间。除了节省时间，jQuery 还处理了浏览器兼容性问题。例如，在[第 5 章](#)中，我提到 `JSON.parse()` 是比 `eval()` 更安全的 JSON 解析替代方案。在较旧版本的 Internet Explorer、Firefox 和 Chrome 中，`JSON.parse()` 不受支持。这意味着你使用 `JSON.parse()` 编写的任何功能，对于少数未更新浏览器的用户来说将无法使用。

jQuery 为你处理了许多常见的版本兼容性问题，包括前面提到的 `JSON.parse()` 问题。jQuery 提供了一个用于解析 JSON 的函数：`jQuery.parseJSON`。在[示例 7-4](#)中，JSON 使用 JavaScript 的 `JSON.parse()` 进行解析。在[示例 7-5](#)中，JSON 使用 jQuery 内置函数进行解析。

> *示例 7-4。使用 JavaScript 的 `JSON.parse()` 解析 JSON。*

```javascript
var myAnimal = JSON.parse('{ "animal" : "cat" }');
```

> *示例 7-5。使用 jQuery 的 `jQuery.parseJSON` 解析 JSON。*

```javascript
var myAnimal = jQuery.parseJSON('{ "animal" : "cat" }');
```

在这些示例中，你可以看到 jQuery 示例在字符输入量上似乎并没有节省多少。然而，jQuery 的 `parseJSON()` 函数所做的远不止一行代码那么简单。如果你查看 jQuery 库源码中该函数的实现，它会尝试使用原生的 `JSON.parse()` 函数。如果浏览器中不可用（旧版本），它会回退到使用 `new Function()`，这等同于使用 `eval()`。此外，还有一些逻辑用于检查无效字符——这些字符可能出现在注入攻击的脚本中，此时会抛出一个错误。

除了 `jQuery.parseJSON`，还有一个用于发起 JSON HTTP 请求的函数。如果我们回顾一下[第 6 章](#)中的示例，可以看到用 JavaScript 通过 HTTP 请求资源可能需要大量的代码（[示例 7-6](#)）。

> *示例 7-6。此示例代码创建了一个新的 XMLHttpRequest 对象，并从 Open Weather Map API 获取 JSON。*

```javascript
var myXMLHttpRequest = new XMLHttpRequest();
var url = "http://api.openweathermap.org/data/2.5/weather?lat=35&lon=139";

myXMLHttpRequest.onreadystatechange = function() {
    if (myXMLHttpRequest.readyState === 4 && myXMLHttpRequest.status === 200) {
        var myObject = JSON.parse(myXMLHttpRequest.responseText);
        var myJSON = JSON.stringify(myObject);
    }
}
myXMLHttpRequest.open("GET", url, true);
myXMLHttpRequest.send();
```

在 jQuery 中，我们只需编写几行代码就可以请求 JSON 资源（[示例 7-7](#)）。

> *示例 7-7。此 jQuery 代码将创建一个新的 XMLHttpRequest，并检索与前面示例相同的 JSON 资源；这包括将 JSON 反序列化为 JavaScript 对象。*

```javascript
var url = "http://api.openweathermap.org/data/2.5/weather?lat=35&lon=139";
$.getJSON(url, function(data) {
    // do something with weather data
});
```

jQuery JavaScript 框架以一种减少开发时间的方式支持 JSON 的请求和解析。这包括以支持旧版本浏览器的方式解析 JSON。我们可以说 jQuery *支持*与 JSON 交互。

## AngularJS

jQuery 框架是一个专注于文档对象模型（DOM）操作的抽象工具。[AngularJS 框架](#)是一个专注于单页应用的抽象工具。*单页 Web 应用*是脱离传统多页 Web 应用体验、将所有内容整合到一个页面中的网页。

传统的多页 Web 应用体验与客户端和服务器之间的人机交互紧密相关。用户输入或点击一个 URL，通过 HTTP 请求资源。在这种传统 Web 应用中，客户端、服务器和用户之间的交互就像一场"舞蹈"，每一步都会"跳转"到一个新的网页。

在互联网发展成为能够处理当今海量多媒体内容的庞然大物之前，大多数面向大众的应用都是桌面应用。如果你想使用数字百科全书，你需要将它安装在电脑上。你与之交互的应用或多或少是无缝的。当你在百科全书中搜索内容时，没有地址会变化的 URL 栏。

单页 Web 应用致力于在你的互联网浏览器中回归那种无缝的应用体验。这在很大程度上是通过 JavaScript 和我们的好朋友 `XMLHttpRequest` 实现的。用户不再通过 URL 和链接在资源之间跳转，而是在后台的代码处理资源请求的同时，用户始终停留在一个页面上。

AngularJS 框架是一个抽象工具，帮助开发者免去从零开始构建单页应用的工作。单页 Web 应用是一个复杂的系统，AngularJS 绝不会替开发者完全构建它。相反，它提供了一个基于模型-视图-控制器（MVC）架构概念的框架。

AngularJS 按如下方式实现 MVC 概念：

*   **模型**
    JavaScript 对象就是数据模型。
*   **视图**
    HTML（使用语法与模型进行数据绑定）。
*   **控制器**
    使用 AngularJS 语法定义和处理与模型及视图交互的 JavaScript 文件。

AngularJS 的学习曲线可能比较陡峭，尤其是对于那些多年来一直使用 JavaScript 和 HTML 文档对象模型（DOM）操作的人来说。它要求转变对 DOM 交互方式的思维方式。Angular 旨在将 DOM 操作与应用逻辑解耦。

这种 DOM 操作的解耦可以通过比较在不使用和使用 AngularJS 框架的情况下如何实现相同目标来表达。例如，我需要将页面上的消息从通用的 "Hello, stranger"（[示例 7-8](#example-7-8)）更改为用户登录时的个性化问候（[示例 7-9](#example-7-9)）。在 JavaScript 中，我们通过操作文档对象模型来实现这一点。

> *示例 7-8。用户未登录时的 HTML 消息。*

```html
<h1 id="message">Hello, stranger!</h1>
```

> *示例 7-9。用户已登录时更改消息的 JavaScript 代码。*

```javascript
if (signedIn) {
    var message = "Hello, " + userName + "!";
    document.getElementById("message").innerHTML = message;
}
```

在 AngularJS 中，由于 HTML 是我们的视图，我们对其进行设置以准备数据模型的变更（[示例 7-10](#example-7-10)）。

> *示例 7-10。使用 AngularJS 属性和语法进行数据绑定的 HTML 视图。*

```html
<body ng-app="myApp">
    <div id="wrapper" ng-controller="myAppController">
        <h1 id="message">Hello {{ userData.userName }}!</h1>
    </div>
</body>
```

HTML 标签（`<body>` 和 `<div>`）上的 "ng-app" 和 "ng-controller" 属性是用于设置视图以支持数据绑定的语法。数据绑定正如其名：我们通过一系列占位符将数据"绑定"到页面上。AngularJS 语法使用"花括号"作为需要绑定数据的占位符。这些花括号由两个左花括号 "{{" 和两个右花括号 "}}" 包围着占位符的语法（在[示例 7-10](#example-7-10) 中为 "userData.userName"）。

在[示例 7-11](#example-7-11) 中，JavaScript 控制器将一个 "userData" 对象添加到全局作用域中；这允许视图（HTML）使用该对象进行数据绑定。

> *示例 7-11。添加到全局作用域的 userData 对象。*

```javascript
angular.module('myApp', [])
  .controller('myAppController', function($scope) {
    $scope.userData = { userName : "Stranger" };
    if(signedIn)
    {
        $scope.userData = { userName : "Bob" };
    }
  });
```



在 AngularJS JavaScript 控制器文件中，不是直接操作 DOM，而是操作数据模型。被操作的数据模型是 "userData" 对象。无论是普通的 JavaScript/HTML 示例还是 Angular 示例，都实现了相同的功能。对于我的简单示例来说，Angular 的方式可能显得更费力，尤其是对于一个抽象工具而言。然而，当你深入研究复杂的应用程序时，比如一个允许用户对其个人信息执行创建、读取、更新和删除（CRUD）操作的页面，Angular 的方式就简化了开发。

示例 7-11 展示了一个用于数据模型的 JavaScript 对象 "userData"。AngularJS 通过将 JavaScript 对象用作 MVC 架构中的模型来利用它们。正如我们所知，JSON 是 JavaScript 对象字面量的表示法。那么 JSON 在 AngularJS 中扮演什么角色呢？

要问的问题是"我们的数据模型来自哪里？"在示例代码中，我的数据模型是硬编码到控制器中的。如果我们回到数字百科全书的例子，我们知道数据必须存储在某个地方。当数据被存储时，通常存储在某种数据库中。

如何将数据从数据库获取到单页 Web 应用程序的数据模型中，取决于开发者。在 AngularJS 数据模型中，将数据从数据库传输到数据模型最常见的载体是 JSON。这通常是通过 HTTP 请求的 JSON 资源，一种客户端-服务器关系。AngularJS 利用这种关系，通过一个核心 AngularJS 服务 `$http` 轻松检索数据模型。

在示例 7-12 中，AngularJS `$http` 用于从 Open Weather Map API 获取天气数据；JSON 被添加为名为 "weatherData" 的对象到全局作用域。响应结果如示例 7-13 所示。

## 第 8 章

## JSON 与 NoSQL

在第 7 章中，我们将镜头聚焦到 Web 客户端-服务器关系中的客户端。在本章中，我们将把镜头聚焦到服务器端的一种数据库，这种数据库不仅使用 JSON 文档来存储数据，而且通过 Web API 与外部世界交互。

我们生活在"信息时代"，大量的数据和知识触手可及。我们可以在 Wikipedia 等网站上查询特定主题的信息，如"裸鼹鼠"。"裸鼹鼠"的信息必须存储在某个地方，而这个地方归根结底就是数据库。

如果你过去曾使用过数据库并熟悉 SQL，那么你很可能在使用*关系型数据库*。关系型数据库由表、列和行构成。每个表代表某种事物，例如账户。代表账户的表可能与代表账户地址的表存在关系。每个表中的键，例如包含账户标识符的列，构成了两个表之间的关系。

为了创建、操作和查询这些关系型数据库，我们使用*结构化查询语言*（SQL）。使用 SQL，我可以从数据库的一个或多个表中查询列和行（示例 8-1）。

> 示例 8-1. 一个简单的 SQL 查询，将从 Account 表中返回 AccountID、FirstName 和 LastName 的列和行
>
> ```
> SELECT accountId, firstName, lastName
> FROM Account
> ```

借助关系型数据库中表之间的关系，我还可以从多个表中查询列和行（示例 8-2）。

*示例 8-2。连接两个表的查询；这将返回所有账户及其关联地址的名字、姓氏、街道地址和邮政编码列及行*

```sql
SELECT Account.firstName, Account.lastName, Address.street, Address.zip
FROM Account
JOIN Address
ON Account.accountId = Address.accountId
```

赋予数据库的“NoSQL”标题告诉我们它不是关系型数据库。我们不能使用结构化查询语言（SQL）来要求数据库返回连接在一起的表的列和行。这个标题没有告诉我们的是*它到底是什么*。它只是说“我发现了一种存储数据的替代方法，它不是关系型的。”自然，存在不止一种“替代方法”。

当今世界上的NoSQL数据库在本质上差异巨大，就像老虎和大象一样。这些类型的数据库性质各异，因为数据具有不同的大小、形状和用途。这些NoSQL数据库的创造者认识到了这一点，因此为数据的存储和检索创建了脱离传统关系型模式的“家园”。

NoSQL数据库的一个例子是*键值存储*。键值存储将简单数据建模为键值对。如果我们拿一本英语词典并为它创建一个数据库，它会很适合键值存储。每个单词可以是键，每个释义可以是值。对于简单数据结构，这种类型的数据库是替代关系型数据库开销的绝佳选择。

本章我们将探讨的NoSQL数据库类型是*文档存储*。这种关系型数据库的替代方案围绕文档的概念来组织数据，而不是将数据片段表示为表并建立关系。目前世界上正在使用20多种不同的文档存储数据库，有些使用XML文档，有些使用JSON文档。

在本章中，我们将了解一种使用JSON文档存储数据的文档存储数据库。让我们来看看CouchDB。

## CouchDB数据库

由于[CouchDB](http://couchdb.apache.org/)是一个NoSQL数据库，它使用JSON文档以非关系型的方式存储数据。

假设我需要存储客户的账户数据。在关系型数据库中，账户信息可能会快速跨越多个表。如果我需要一个账户拥有多个地址，那么就需要一个单独的地址表来支持这种一对多的关系。

在关系型数据库中，像一个账户拥有多个地址这样的一对多关系，必须通过连接来查询，以便将数据重新组合在一起。此外，如果我查询数据库以获取单个账户及其所有连接的地址记录，结果将包含多行。每一行都会有相同的账户字段重复出现，但每一行对应不同的地址。因此，数据的结构存在于数据库内部，但在查询时被扁平化为列和行。

使用CouchDB，数据内部的关系不需要为存储而分离数据，也不需要在后续读取时重新组装。关系在数据中表达，结构在数据进出数据库时得以保持。

在示例 8-3 中，账户地址的一对多关系表示为对象数组。

*示例 8-3。表示账户的JSON文档*

```json

            "street": "456 fakey ln",
            "city": "Some Place",
            "state": "CA",
            "zip": 96026
        }

使用CouchDB文档存储，当我向数据库请求一个账户时，我得到的是一个结构化的文档。无需组装。这既方便又更快。

然而，文档存储并非数据存储的万能解决方案。如果需要多个关联，这种模式很快就会变得麻烦。如果我想在地址的城市、州和邮政编码之间建立关系怎么办？一旦需要这些关系，关系型模型会更适合数据，因为在单个文档中表达复杂关系会很困难。

CouchDB的另一个优点是促进了数据的演进。有些数据会随着时间而演变。例如，在1990年，我可能可以用这些字段来表示账户记录中的电话号码：

- 家庭电话
- 工作电话
- 传真

现在我们不再处于1990年，我们需要一个手机字段。数据需要演进。

在关系型数据库中，我们需要修改地址表的模式以支持这个手机字段。我们可能还会决定删除账户表上的字段，并将电话号码移动到它们自己的表中。

使用CouchDB，我们的数据允许演进而无需修改模式。我可以在JSON中轻松地将电话号码表示为对象数组（示例 8-4），并允许一个账户拥有与其实际电话记录一样多的条目。

这些示例展示了如何查看和创建存储在 CouchDB 数据库中的 JSON 文档。如果只能做这些，我们很快就会遇到问题。也许我需要一个仅包含名人的姓氏列表。在 CouchDB 中，我们可以使用 "视图" 来实现这一点。参见示例 8-17。

视图是我们重新组织和查询 CouchDB 数据库数据的方式。视图存储在一个称为设计文档的 JSON 文档中。设计文档指定了语言，并且可能包含多个视图。

示例 8-17. 用于 accounts 数据库的 CouchDB 设计文档，其中包含一个用于名人的视图

    "_rev": "8-4124de7756277c6a937004a763d6247d",
    "language": "javascript",
    "views": {
        "famous": {
            "map": "function(doc){if(doc.lastName!==null&&doc.famous){emit(doc.lastName,null)}}"
        }
    }
}
```

每个视图都是一个对象，可能包含一个 map 函数和一个 reduce 函数。在示例 8-17 中，只有一个 map 函数。map 函数以每个文档作为参数，然后调用 emit 函数。这本质上是对数据进行转换（???）。

示例 8-18. 仔细查看 "famous" 视图的 "map" 函数

```

    if (doc.lastName !== null && doc.famous) {
        emit(doc.lastName, null)
    }
}
```

在示例 8-18 中，该函数检查数据库中的每个 JSON 文档（doc 参数），以确保我们拥有姓氏，并且 "famous" 键值对的值为 true。emit() 的参数是 key 和 value，它们将在转换后的文档结果中作为键值对显示。

然后我可以通过 URL http://localhost:5984/accounts/_design/lists/_view/famous 将该视图作为资源请求。其结构为 /<db-name>/_design/<design_document_name>/_view/<view_name>/。

## 关键术语和概念

本章涵盖了以下关键术语：

*关系型数据库*
一种数据库类型，其结构旨在识别存储数据中的关系。

*非关系型数据库（NoSQL）*
一种数据库类型，其结构*不*基于存储数据中的关系。

*CouchDB*
一种文档存储类型的非关系型数据库，以 JSON 文档的形式存储数据。

我们还讨论了这些关键概念：

- 在关系型数据库中，通常有表、列和行，以及这些表、列和行之间的关系。存在主键和外键。
- 存在多种类型的非关系型数据库，它们摒弃了关系模型。

我们还讨论了 CouchDB。以下是一些需要记住的关键点：

- 它是一种文档存储类型的非关系型数据库。
- 它存储和管理 JSON 文档。
- 它在存储和检索时维护数据的结构。
- 它使用 HTTP API 以 JSON 文档资源的形式访问数据。
- 它使用 JavaScript 作为查询语言，并使用 Map 和 Reduce 函数来创建视图，这些视图可以通过 HTTP API 访问。

## 反序列化 JSON

在 PHP 中序列化 JSON 时，我们使用了内置的 `json_encode` 函数。反序列化 JSON 时，我们使用 `json_decode` 函数。遗憾的是，它没有内置支持将 JSON 反序列化为指定的 PHP 对象（如 Account 类）。因此，我们必须进行一些处理，将数据重新塑形为 PHP 对象。

让我们为账户对象添加一个新函数，从 JSON 字符串加载其属性（示例 9-13）。

*示例 9-13. `loadFromJSON` 函数接受一个 JSON 字符串作为参数，调用内置的 `json_decode` 函数反序列化为通用 PHP 对象，并在 foreach 循环中按名称将名称-值对映射到 Account 的属性上*

```
class Account {
    public $firstName;
    public $lastName;
    public $phone;
    public $gender;
    public $addresses;
    public $famous;

    public function loadFromJSON($json)
    {
        $object = json_decode($json);
        foreach ($object AS $name => $value)
        {
            $this->{$name} = $value;
        }
    }
}
```

接下来，我们可以创建一个新的 Address 对象，并调用新的 `loadFromJSON` 函数。

*示例 9-14. 调用我们新的 `loadFromJSON` 函数将账户 JSON 反序列化回 Address 对象。最后一行将显示 "Bob Barker"。*

```
$json = json_encode($account);

$deserializedAccount = new Account();
$deserializedAccount->loadFromJSON($json);

echo $deserializedAccount->firstName . " " . $deserializedAccount->lastName;
```

在 PHP 和 ASP.NET 的示例中，我们可以看到，尽管 JSON 基于 JavaScript 语言的对象字面量表示法，但这种表示法能很好地转换为其他编程语言的对象。由于服务端编程语言种类繁多，其中许多都支持对象和 JSON 数据类型。这是非常理想的，因为它允许数据的结构或"形状"在以 JSON 形式进出系统时得以保持。

此外，服务端对 JSON 的支持非常广泛。大多数 Web 服务端语言（或框架）要么提供内置的 JSON 序列化/反序列化支持，要么有可用的库或模块。这种服务端对 JSON 的支持促使其成为一种成功的数据交换格式。

让我们来看几个服务端 JSON HTTP 请求的简短示例。在每个示例中，你都会看到一个对 JSON 资源的 HTTP 请求，

对资源的解析成对象，以及从JSON文档中渲染值。

所有这些示例中的JSON文档都将来自Open Weather Map API。所有值的渲染都将基于JSON资源的一个子集，该资源位于 http://api.openweathermap.org/data/2.5/weather?q=London,uk。

示例 9-17. Open Weather Map API天气数据JSON资源中的坐标对象。这代表了英国伦敦的经纬度。

```
{
    "coord": {
        "lon": -0.13,
        "lat": 51.51
    }
}

## Ruby on Rails

Ruby on Rails 是一个服务器端Web应用框架。它使用Ruby编程语言编写，并基于模型-视图-控制器（MVC）架构。

在Ruby中，gem是一个用于安装程序或库的包。要在Ruby on Rails中序列化和反序列化JSON，需要JSON这个Ruby gem。一旦安装了JSON gem，解析JSON就很简单，只需使用 `JSON.parse()`。

示例 9-18. 在本例中，我们向Open Weather Map API发出HTTP请求，并将JSON反序列化为Ruby对象。最后，在代码的最后一行，我们渲染出数据中坐标（coord）对象的经度（lon）。

```
require 'net/http'
require 'json'

url = URI.parse('http://api.openweathermap.org/data/2.5/weather?q=London,uk')
request = Net::HTTP::Get.new(url.to_s)
response = Net::HTTP.start(url.host, url.port) {|http|
  http.request(request)
}

weatherData = JSON.parse(response.body)

render text: weatherData["coord"]["lon"]
```

## Node.js

Node.js 是在服务器端运行的JavaScript（无需互联网浏览器），这得益于Google的开源V8 JavaScript引擎。使用Node.js，你可以用JavaScript构建服务器端应用程序。

在本书的前面部分，我们介绍了在客户端使用JavaScript处理JSON，并看到JSON通过简单的 `JSON.parse()` 反序列化为JavaScript对象。Node.js中也一样，因为它*就是*JavaScript。

然而，在Node.js中我们不使用 `XMLHttpRequest` 对象，因为它是特定于网络浏览器的JavaScript对象。在Node.js中，我们可以使用一个命名更恰当的函数 `get()` 来请求我们的JSON（以及其他类型的资源）。

> *示例 9-19. 在本例中，我们向Open Weather Map API发出HTTP请求，并将JSON反序列化为JavaScript对象。然后，我们使用 `console.log()` 打印出数据中坐标（coord）对象的经度（lon）。*

```
var http = require('http');
http.get({
    host: 'api.openweathermap.org',
    path: '/data/2.5/weather?q=London,uk'
}, function(response) {
    var body = '';
    response.on('data', function(data) {
        body += data;
    });
    response.on('end', function() {
        var weatherData = JSON.parse(body);
        console.log(weatherData.coord.lon);
    });
});
```

## Java

Java 是一种面向对象的编程语言。Java可以作为Java小程序在网页浏览器中运行，或者在安装了Java运行环境（JRE）的机器上独立运行。

有许多支持Java中JSON的库。在本节中，我将使用以下库从URL获取JSON资源，并将其反序列化为Java中的对象：

- Apache Commons IO: https://commons.apache.org/proper/commons-io/
- JSON in Java: http://www.json.org/java/

> *示例 9-20. 在本例中，我们从Open Weather Map API获取JSON资源作为字符串。之后，我们通过实例化一个 `JSONObject` 来反序列化JSON字符串。然后，我们使用 `System.out.println()` 打印出数据中坐标（coord）对象的经度（lon）。*

```
import java.io.IOException;
import java.net.URL;

import org.apache.commons.io.IOUtils;
import org.json.JSONException;
import org.json.JSONObject;

public class HelloWorldApp {

    public static void main(String[] args) throws IOException, JSONException {
        String url = "http://api.openweathermap.org/data/2.5/weather?q=London,uk";
        String json = IOUtils.toString(new URL(url));
        JSONObject weatherData = new JSONObject(json);
        JSONObject coordinates = weatherData.getJSONObject("coord");
        System.out.println(coordinates.get("lon"));
    }

}
```

从大约6000英尺的高空，我们可以看到JSON在世界各地穿梭，在系统之间进出数据。JSON在作为数据交换格式方面非常出色，我们在这本书中已经看到了这一点。然而，如果你用望远镜仔细观察，你会发现JSON在某些地方实际上是静止不动的。

尽管JSON在某些地方静止不动，但本书基本上忽略了这个主题。重点一直是双方之间的数据交换。本质上，是移动数据。

JSON既可以是数据的容器，也可以是数据的载体，它不局限于单一用途。我们在NoSQL中JSON所扮演的角色已经看到了这一点的例证。越来越多地，JSON作为一种非常有用的工具，正在进入各种项目和事业中。为了进一步说明，让我们最后看看JSON在当今世界中扮演的一个角色：作为一个配置文件，静止不动地存放在一个地方。

## JSON作为配置文件

在第9章中，我们探讨了两种支持解析JSON的服务器端Web技术。正如该章所讨论的，JSON得到了大多数服务器端Web语言（或框架）的广泛支持。由于其广泛的服务器端支持、易于解析以及人类可读性，使用JSON来存储配置数据已变得非常流行。

配置文件或设置文件通常在软件中使用，以便在不重新编译的情况下更改设置。配置文件有几种格式，包括INI和XML。

让我们看看如何将相同的设置信息分别存储在INI、XML和JSON格式中（分别见示例10-1、10-2和10-3）。

### 示例 10-1. INI格式的游戏设置文件示例（settings.ini）

```

        <mouseSensitivity>0.54</mouseSensitivity>
    </general>

        <complexTextures>true</complexTextures>

所有这三种格式都是人类可读的。如果我想更改我的声音设置，我可以在每个文件中快速找到它并更改数字。这就是它们成为优秀配置文件的原因。

每种格式都有其优缺点。INI文件更容易被人类阅读，因为它没有XML的小于号和大于号，也没有JSON的花括号和双引号。INI对于更复杂的数据，如嵌套信息或复杂列表，就不太适用了。XML可以容纳更复杂的数据，但它没有像JSON那样的数据类型。

除了每种数据格式的优缺点之外，所使用的语言/框架的解析便利性也是一个重要的考虑因素。如果你的应用程序已经大量使用了JSON解析器，那么JSON可能是你的配置文件的最佳选择。

## 全局视角

作为存放在服务器上的配置文件，或作为通过 URL 请求的资源，JSON 正在履行其作为数据交换格式的职责。我们已经在本书的章节中探讨了这些职责（或角色）。现在让我们从全局视角回顾一下当今世界中 JSON 的使用情况。

在服务器端，对象可以序列化为 JSON 文本格式，并反序列化回对象。JSON 也可以从服务器端代码中请求。我们在第 9 章讨论的 ASP.NET 和 PHP 示例中看到了这一点的实际应用。

此外，JSON 是一种文本格式，也可用作文档存储类型数据库的文档。我们在第 8 章的 CouchDB 中看到了这一点。该数据库也是通过 HTTP Web API 进行接口的。

HTTP Web API 为 HTML 和 JSON 文档等资源提供了请求和响应系统。这些文档通过带有 URL 的 HTTP 请求。我们在第 6 章的 Open Weather Map API 提供 JSON 格式天气数据资源时也看到了这一点。

JavaScript 的 XMLHttpRequest 可以从 URL 请求 JSON 资源。要在 JavaScript 代码中使用 JSON，我们必须将 JSON 反序列化为 JavaScript 对象。这可以使用内置的 JavaScript "JSON.parse" 函数轻松完成。

从 JavaScript 对象，到 JSON 格式，再到服务器上的对象，我们可以看到数据完成了一个完整的循环。每天，数据在全球各地的系统中进进出出，而这些数据都处于一种交换格式中。

如果我们再次从 6,000 英尺（约 1829 米）的高空俯瞰，就会发现 JSON 并非唯一的数据交换格式。一些数据以逗号分隔值（CSV）格式或 Excel 格式进行传递。两者都是表格形式。其他数据则以 XML 格式传递，它支持数据的嵌套。

数据有多种格式和多种形态。处理这些格式数据的系统也是多样的。在选择数据交换格式时，必须考虑数据的形态以及交换数据的系统。尽管本书喜爱 JSON 并视其为数据的绝佳格式，但 JSON 并非总是唯一的答案。

例如，假设两个系统需要通信库存数据，而这两个系统都将这些信息存储为表格格式。那么，将这些表格数据转换为对象格式、序列化为 JSON、再转换回对象格式、然后又转换回表格数据，这有意义吗？不，在这种情况下，我们只是徒增步骤，仅仅是为了使用 JSON。对于这类数据，更合适的格式是表格形式的，比如 CSV 或制表符分隔格式。

JSON 是一种流行的数据交换格式，因为许多系统都将数据建模为对象。数据通常存储在关系型数据库中。尽管关系型数据库的表是表格形式的，但数据中的关系被分解为可视为对象的实体。每个实体（例如一个地址）都有“字段”，这些字段本质上是键值对。

在像互联网浏览器这样的系统中，JavaScript 支持面向对象编程，因此 JSON 非常适合用于数据交换。JSON 在 JavaScript 中非常适合与 Web API 通信并创建 AJAX 交互。

在像服务器端 Web 框架这样的面向对象的系统中，JSON 也适合用于数据交换。JSON 在数据进出系统时，以其对象字面量的形式保持结构不变，这使其大放异彩。

就像第 101 页“JSON 作为配置文件”中的示例一样，选择格式时必须权衡利弊。一切都归结为合适的工具用于合适的工作。
