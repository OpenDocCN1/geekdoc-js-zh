# 人类 JavaScript




## 前言

我学会用 JavaScript 做的第一件事是切换图片。

那是 1998 年，那是我所能接触到的“最先进”的网络应用编程技术。那是一个网络尚未充斥 `MM_swapImage` 的时代，不过我记得 Dreamweaver 已经出现了。当时我懂 HTML，而捣鼓一些 JavaScript 是我第一次涉足真正的编程。当时，`<img>` 的 `src` 属性可以通过编程方式修改，这对我而言是一个深刻的领悟，尽管现在看来那似乎是很久以前的事了。

我的网络技术探索之路与其他人同步，可能因为我要等待东西运到德国而有一两年的延迟（那时的互联网非常慢）。Netscape 和 IE 4 发布了，带来了新的动态操作和动画化 HTML 内容的方法。DHTML 诞生了，我试图理解这一切，直到我能够用层（layers!）和 div 在*两个*浏览器中替换内容。

玩这个很酷，但在那时，构建能一致运行的东西并不怎么有趣，所以我转投了“黑暗面”，参与了后端网络开发。我可以让别人去担心那些古怪的浏览器差异。在后端，我找到了自己对数据库的热情。

但后来，2005 年到来了，一切都变了。谷歌推出了地图，世界变得不同了。直到今天，我仍清晰地记得在浏览器窗口中拖动地图的情景——想到这个我依然会起鸡皮疙瘩。谷歌地图是网络世界的“披头士登陆美国”时刻。

大约在同一时期，37signals 推出了面向自由职业者和小型企业的基于网络的应用程序，不仅向世界展示了网络能做什么，还引发了我们所谓的原生桌面应用与网络应用支持者之间长达一年的讨论。我们现在正在经历原生移动应用和网络应用之间的同样的事情。

37signals 甚至写了一本书，讲述如何围绕软件即服务模式构建自举业务，这催生了一代网络应用企业家，他们以自己的方式构建了触及世界的产品。

深受启发，我和一位大学朋友着手开展我们自己的软件即服务。我们投入了大量时间，但最终，它没有成功。存在许多问题，而我对于前端网络技术理解不足肯定也没帮上忙。我们设法构建了一个功能原型，但代码一团糟，bug 不可能修复，新功能无法实现，重构工作多次失败，直到我们放弃。我们关掉了项目，我回到了后端和数据库领域。

快进到我创立 Hoodie 的时候，发现自己置身于优秀的前端开发者之中。现在，我能为这个项目做的最好的事情就是构建所有的后端，这样他们在集中精力搞定前端时，就无需担心任何事情。

然而，我仍然渴望更深入地理解前端世界。我可以涉猎，但我想要自信地掌握它。

计算机科学从根本上说是关于构建事物。与建筑或结构工程不同，我们工作的内容、方式和原因，其变化尺度是年，有时甚至是周。我们去年学到的东西，用一句老话说，今天就过时了。

这种性质的另一面是，构建一个经典体系非常困难。当然，我们有算法和数据结构作为现代教学的基础，而且它们确实是日常工作的组成部分，但编程和构建产品*远不止*于此。

我们有责任弄清楚如何将缺失的部分纳入课程体系，以培养未来的网络开发者。

当 Henrik 告诉我他正在写《人性化的 JavaScript》时，我恳求被加入评审名单。不是因为我认为我能指出他所有错误的地方，而是因为我仍然对前端网络开发者这个领域充满好奇。我也喜欢这个角度，想着“我是个人类，这本书就是为我写的！”开个玩笑，技术书籍往往非常枯燥。而这本承诺采用不同的方法，一种我能产生共鸣的方法。

我一口气读完了初稿，做了很多笔记，读完之后，对我来说一直无法触及的整个前端世界，变得清晰了。我看到了客户端上比我所经历过的更复杂的 MVC 框架的必要性。我开始理解为什么以特定方式组织代码，能使其在多人协作时更具健壮性。这本书成功地在陌生的前端领域阐明了众所周知的概念。《人性化的 JavaScript》让我能够接触到前端开发。

再次深受启发，我接着做了一个小的副项目。它虽然没什么大不了的，但它让我对构建更多网络应用感到兴奋。

《人性化的 JavaScript》是 &yet（Henrik 工作的公司）团队的智慧结晶，是他们投入到优秀客户项目和自身产品中的所有心血和汗水。没有比他们更好的一群人了。他们既关心正确的技术，也关心如何教授它。他们自觉承担起填补网络开发经典体系缺失的空白。

&yet 是我们这一代的 37signals，我迫不及待地想看看他们激励的人会创造出什么。我迫不及待地想看看你会创造出什么。

— Jan Lehnardt
柏林，2013年9月27日

Jan 是来自德国柏林的开源软件开发者。他是 [Apache CouchDB](http://couchdb.apache.org/)（可复制的数据库）的副主席。他是 [JSConf EU](http://2013.jsconf.eu/) 的联合策展人，[The Node Firm](http://thenodefirm.com/) 的合伙人，他著名的一个 JavaScript 项目是 [mustache.js](https://github.com/janl/mustache.js)。他目前从事 [hood.ie](http://hood.ie/) 的工作，这是一个开源的无后端解决方案，旨在为前端开发做 Rails 为后端所做的事情：消除所有繁琐的痛苦，并将其隐藏在一个直观的 JavaScript API 后面。

## # 人性化 JavaScript

代码既是关于人的，也是关于计算机的。当然，它由计算机运行，但它是由人编写、维护，并最终为人而创造的。人不是计算机。我们不是机器人。我们不可预测、不完美、且非理性。即使使用相同的工具和指令，相同的人每次也不会产生相同的输出。我们通常不喜欢独处，也不擅长孤立地工作。事实上，为了做到最好，我们*需要*与他人合作。这些特质没有一样是坏事，恰恰相反，它们定义了我们是谁，它们使我们成为——嗯……人类。然而，作为开发者，我们很容易过于专注于优化技术，以至于忘记了为人优化。

你可以从其他地方阅读关于 JavaScript 这门语言的内容。它的优点、缺点和丑陋之处都有详尽的记载。这本书是关于一套特定的工具、模式和方法，我们认为它们是*为人类优化*的。这些方法使我们的团队能够快速构建和交付为人类服务的高质量 JavaScript 应用程序。

**&yet**，我很荣幸能成为其中一员的团队，是一家小型（约40人）的自举咨询和产品公司，主要专注于实时单页 Web 应用程序。我们曾有机会为各种目的和受众构建非常广泛的单页应用程序。我们为移动设备、桌面应用、浏览器扩展、PhoneGap、电视等等构建过各种东西。从这些经验中，模式开始浮现。这些模式使我们能够高效地作为一个团队交付真实世界的应用程序（带着真实世界的截止日期）。

在这个过程中，我们尽力从中提取可复用的工具。因此，在某种程度上，我们意外地写了这本书。我的意思是，本书的大部分内容汇编自过去的博客文章、对团队成员和客户的解释，以及项目 README 文件。本书主要是提炼，而非创作。我们分享我们的经验、秘密和工具，希望能为你和你的团队在构建出色的应用和体验方面打下坚实的基础。

## # 本书将帮助你构建原生 HTML5 应用

让我们稍微谈谈这个“应用”的话题，以便在术语上达成共识。如果你拥有任何形式的智能手机，在过去五年左右，你一定被“应用”这个词轰炸过。

与其花三章的篇幅来阐述这个词的含义，我将根据本书的目的，按照我的理解来解释其区别。

当大多数人说他们在构建一个“Web 应用”时，他们谈论的是编写描述一个将在服务器上运行并将渲染后的 HTML 发送到浏览器的应用程序的源代码。这个定义似乎有点狭隘和局限。另外，当我想到我最喜欢的 Web 应用时，它们并不完全符合那个框框。最好的 Web 应用通常具有多个界面和客户端，有些是原生的，有些是 Web 的。大多数都能与其他服务良好协作或完全集成。总的来说，Web 应用擅长解决某个特定问题或提供某种特定好处，并使用 Web 将这一切联系在一起。

Web 与原生的争论已经有些过时了。在我看来，整个争论在某种程度上是被误导的。不一定要非此即彼，我可以接受两者兼备。大多数原生应用结合 Web 会更好，这已经不是秘密。否则，像 iPhoto 这样的经典原生 Apple 应用为什么要开始与 Flickr 和 Facebook 集成呢？然而，你不可能为每个平台都编写一个原生应用。

将你的“Web 应用”视为一个 API 和一系列客户端，这似乎更加合适。这很有道理。你的 API 定义了你的服务，将你与其他用户连接起来，并整合了整个体验。然后，你可以专注于构建为各种环境和用途提供最佳体验的客户端。

让我们谈谈浏览器。它们简直*太*令人惊叹了。嗯，至少现代浏览器是这样。它们可以说是极其强大、*基本*标准化的操作系统，在几乎每个平台上都免费可用。它们每天都在变得越来越令人惊叹。可惜的是，对向后兼容性的沉迷，严重限制了人们对这个操作系统能力的认知。通常，Web 界面最终在体验上成了最低公分母。但情况不必如此！让我们为 Web 的未来而构建，而不是为它的过去。

我们正在讨论的这本书中要构建的应用类型，可以真正称为“原生 HTML5 应用”，因为它们充分利用了 HTML5，而不必屈从于与老旧糟糕的浏览器兼容。

进一步澄清：

-   1. 它们与 API 是分离的。
-   2. 如果有人关闭了 JavaScript，它们*根本*无法工作。
-   3. 具有现代 JavaScript 引擎的现代浏览器是最低系统要求。
-   4. 我们将应用程序代码本身发送到浏览器，而不是应用程序代码运行的结果。
-   5. 应用完全在客户端渲染。我们只发送运行应用所需的最少量的 HTML。通常只是一个文档类型、一个脚本标签和一个样式表。
-   6. 加载后，客户端获取自己的数据，以数据形式（通常是 JSON），而不是渲染后的 HTML。
-   7. 应用加载一次，在使用过程中永远不需要完整的页面重新加载。
-   8. 像点击链接渲染新“页面”这样的操作利用了异步 JavaScript。
-   9. 应用拥有并维护着独立于服务器的、被缓存和维护的“状态”。

从现在开始，当我在这些页面中说“应用”、“原生 HTML5 应用”、“浏览器应用”或“客户端应用”时，指的就是这个。

这里还有一些值得思考的问题：一旦你承认浏览器拥有状态，你就真的应该思考如何保持该状态的最新，并使其成为一个“实时”应用。

### 实时应用就是人性化应用

很多人对“实时”这个词很纠结。我在这里使用它时，指的不是延迟或传递速度，而是指有多个数据源（通常是人）在做事！人们一直在改变数据，而我们的应用并非被动地等待用户刷新。相反，应用会主动保持自身更新。实际上，根据计算机科学的定义，没有哪个 Web 应用是“硬实时”的。在我们的案例中，它只是一个用来帮助描述那些能自我更新的应用的术语。

实时不是关于炒作和技术——它是关于消除技术对协作的阻碍，以及克服跟踪大量状态的困惑。

Web 的未来是实时的。对此我毫不怀疑。

我之所以能如此肯定地说出来，是因为它已经发生在我们眼前。

Facebook、Gmail、Google Talk 和 GitHub 等等（仅举几例）都已经实现了某种形式的自动页面更新。当他们有新东西要告诉你时，他们不会等你去询问。他们会把它推送给你，从服务器到客户端。

在某些情况下，这就像页面自动轮询查看是否有新内容一样简单。在其他情况下，它更高级，用于构建和更新页面的所有数据都是通过开放的 WebSocket 连接传输的。就我们的目的而言，传输机制在很大程度上无关紧要；重点是，数据会主动来到你面前。

这从根本上打破了 Web 的无状态性。过去，我访问一个 URL 并得到一个网页。作为用户，我理解页面上的信息在请求时（大概）是准确的。如果我想检查新东西，我会再次请求，然后收到另一个时间点的快照。

一旦我们努力使页面上的信息与服务器同步，我们就已经承认网页具有“状态”。在某些方面，页面一直*有*状态，但用户清楚地知道那是快照状态，而非实时同步的状态。因此，那个静态页面更像是一张印刷页面，而不是一个活的文档。



数字媒体相对于印刷品的一个根本优势在于它不再是静态的。它是动态的、流动的，并且可以随着信息的更新而更新。

因此，一旦我们作为开发者决定对页面进行部分更新，我们唯一能做的就是了解我们当前拥有的信息，并将其与服务器上的信息进行比较。状态复制已经发生，我们现在以某种形式在客户端维护着“状态”。

随着用户对这个概念越来越熟悉，我认为我们会达到这样一个阶段：总是最新的、自动更新的信息是*期望之中的*，而非意外惊喜。Facebook的聊天、实时评论和推送通知已经在培养整整一代用户期待实时更新的习惯。我相信，对于希望保持行业领先地位的Web开发者来说，知道如何构建实时应用是一项至关重要的技能。

每次你复制状态，你都会增加复杂性。你不再仅仅担心正确地渲染某些数据，现在你还要关心数据的过期、缓存和冲突。

如果我们稍作退后，开始意识到我们实际上构建的是一个分布式系统，因此我们将面临构建分布式系统时带来的所有相同挑战。

我知道你可能在想什么。某个框架会出现并为我解决这个问题。你可能是对的，处理状态复制问题有许多不同的方法。有一些新兴的框架，如Meteor和Derby，旨在简化构建此类应用的过程。

其中一些框架的挑战在于，它们过分强调在客户端和服务器端之间共享代码和逻辑。在我看来，客户端和服务器端确实应该扮演根本不同的角色。服务器端用于数据，客户端用于展示。这有助于实现更清晰的关注点分离。与此形成对比的是我的朋友Owen Barnes在SocketStream上的工作。有趣的是，在过去几年里，我们最终得出了非常相似的结论。正如他在2012年RealtimeConf的演讲中提到的，可能不会出现实时的“Rails”。问题实在太多样化了。他后来将关注点转移到了其他地方，但结论似乎是构建松散耦合的模块化方法和模式，以便根据需要进行替换。事实证明，这正是我们最终用[Ampersand.js](https://github.com/AmpersandJS)构建出来的东西。

分布式系统、延迟补偿和状态复制都是非常复杂的问题。解决复杂问题的方法*不是*直接解决复杂问题。相反，你需要将它们分解成更小、更简单、可解决的问题。这些解决方案的集合可以代表完整的解决方案。

那么，为什么要把服务器端的复杂性带到客户端，反之亦然？此外，当你试图在浏览器中共享太多服务器代码时，很容易陷入将应用程序与特定客户端紧密耦合的陷阱。这使得构建其他客户端（例如，为你的应用构建一个iOS应用）变得更加困难。虽然这些框架对于标准的桌面Web应用很有用，但当我们想超越这些时，它们就有点力不从心了。随着越来越多关于“物联网”的讨论，我们有充分的理由相信，希望与你的应用通信的设备类型的广度将继续增加。

### 误解、担忧和工程化

我们需要停止贬低“前端”代码的概念。情况正在好转，但许多自诩为“真正的”开发者仍然认为浏览器代码是小儿科。在他们看来，客户端很简单，是那些偏设计、非开发者的人做的事。这太荒谬了。

我们讨论的不是在服务器上渲染一些HTML然后撒上几行jQuery。我们讨论的是在这里*工程化*一个UI。

不幸的是，由于这些先入为主的观念，许多被要求构建这类应用的人并没有深厚的工程背景，他们处理任务的方式就像处理其他任何客户端代码一样：写一些jQuery。

但是，jQuery不是应用框架。它是一个用于处理DOM的抽象层和工具包。我完全不是在贬低jQuery，事实上，我认为它是一个很棒的DOM操作工具包。我在许多HTML5应用中使用它，并且非常满意。我的重点仅仅是jQuery是一个DOM工具包，而不是应用框架。

但是，不可避免地，“前端”人员会被要求构建一个沉浸式、复杂的客户端应用，很快他们就会得到一个3500行的JavaScript文件，名为“app.js”，它做了*所有*的事情。而且，现在没有其他人知道它是如何工作的，或者它的结构是怎样的。没有赢家。

为了避免这种情况，我们必须将其作为构建高性能、结构良好的UI的工程任务来对待。

### 选择你的工具

现在有越来越多的工具可用于构建客户端应用。AngularJS、Ember、Backbone、Sencha、Knockout等都有各自的优缺点。

负责开发团队的人似乎在这个决定上很痛苦。他们将这些选项视为具有巨大、长期影响的长期决策，他们不想选错。最棒的是……它们都是JavaScript。所以这并不是*那么*严重的决定，切换到其他东西也不会让你的整个业务付之一炬。最重要的是，你的团队熟悉使用JavaScript构建结构良好的应用。这项投资将是值得的，并且可以转化到新的工具上（如果它们出现的话）。

决策既耗时又昂贵。在&yet，我们使用各种不同的工具和方法构建和重建了应用程序。接下来的页面包含我们得出的结论。它们可能并不适合所有人，但我们对结果相当满意，它们使我们能够作为团队高效地协作开发客户端应用。这些方法是根据以下标准选择的：

1.  工具是“纯粹的JavaScript”。不是那种用特定领域语言（DSL）描述应用的工具（不用Sencha）。这是为了避免在贡献之前需要太多关于框架本身的知识。专注于JavaScript也能在一定程度上防止在框架特定知识上投入过多。
2.  工具是通过编写JavaScript文件中的代码来构建应用，而不是试图在HTML中声明太多的应用逻辑（不用AngularJS，抱歉）。不得不在模板中编写应用逻辑感觉违反了关注点分离。它有一些短期收益，可以使简单的事情变得非常容易。然而，当你想要更多控制时，在框架的约束下可能很难做到。
3.  没有庞大的、万能的部件框架（不用Sproutcore）。这些框架通常对你想要如何构建HTML做很多假设，并且经常违反关注点分离。
4.  模型状态与视图状态完全解耦（不用Knockout.js）。同样，这是为了分离关注点。
5.  你不应该是一个JavaScript高手才能编辑模板。模板放在单独的文件中，逻辑很少，允许设计师在不知道一切如何运作的情况下编辑模板。
6.  DOM只是状态的一个视图，并对模型层中的变化做出反应。
7.  简单、解耦的文件结构，包含大量解决单一问题的组件。
8.  尽可能少的魔法（不用Ember）。类似于第1点，这主要是为了避免需要太多框架特定的知识。这引出了下一点。
9.  已经知道JavaScript的人应该能够在没有大量关于特定工具或框架知识的情况下开发应用。
10. 前一点的逆命题也应该成立，即学习应用如何工作的人，应该在此过程中顺便学习JavaScript如何工作。
11. 它应该在使用版本控制的团队环境中运行良好（没有巨大的文件）。
12. 每个功能都应该有一个明显的“归宿”。结构，结构，结构。这使得可以轻松地跳入旧代码修复错误，或在项目之间切换。
13. 项目应该有一套可以通过自动化流程强制执行的代码风格标准。这鼓励整个代码库的可读性和一致性。它将围绕一个可执行的标准来集中代码风格的争论。我们发现这可以最小化很多关于代码风格的反复争论，因为它变成了简单的自动通过或失败。
14. 它应该足够灵活，能够真正构建任何你想要的东西，而无需将一堆未使用的代码发送到浏览器。

# 选择客户端还是服务器端？要么全力以赴，要么干脆放弃。

作为一名编写大量 JavaScript 的人，你可能认为我会主张一切都应该做成单页应用。简而言之：并非如此。

要尽可能地将事情简化。编程是复杂的、昂贵的、耗时的。实用主义是完成任何事情的唯一途径。

对于许多类型的应用程序来说，构建单页应用更难，而且不会带来额外的价值。我确实相信会有那么一天情况不再如此。但目前还不是。

因此，反过来，想想你希望你的应用如何被使用。它是那种用户加载一次，然后就让它整天停留在桌面上的东西吗？还是那种快速查阅一下然后就关闭的东西？

作为工程师，我们总是在过度设计。想想看，有多少博客在每一次请求时都要查询数据库，而实际上它们完全可以是从 Markdown 之类的东西生成的静态 HTML（例如：Jekyll）。

构建客户端应用通常比构建服务器端渲染的应用更复杂。请仔细决定。问问自己，这对你的用户有额外的好处吗？你构建的是一个会被频繁打开和关闭的东西，还是在构建一种体验？应用程序中的数据变化频率如何？你是否在意应用打开时数据发生变化？

# 所以我没说服你放弃？好吧，那就全力以赴！

你听说过“关注点分离”。我们被教导要构建功能单一、自包含的工具和组件。这使代码更具可重用性和可维护性，也能让开发者更理智。

然而，人们在构建 Web 应用时最常做的一件事，就是在服务器上渲染一堆 HTML，然后把它发送到客户端，并用一堆 JavaScript 开始摆弄它！就这样，我们将服务器和客户端代码耦合在了一起，因为现在双方都必须关心渲染和呈现。

请选择其中一种，说真的。如果你正在构建一个“应用”，其中很大一部分数据将在客户端渲染，那就直接把*所有*渲染工作都放在客户端完成。别再犹豫了。把一堆部分渲染好的 HTML 发送到客户端，然后再开始折腾它，这太难看了。

我最喜欢向开发者展示的 And Bang 代码库中的一样东西，就是我们发送给浏览器的 HTML。它就在这里……截至撰写本文时的完整版本：

```
<!DOCTYPE html>
<!-- served with <3, &yet -->
<script>window.times = {start: new Date};</script>
<link href="/&!.css" rel="stylesheet">
<script src="/&!.js"></script>
```

是的。（而且，是的，HTML 规范允许省略 `<html>`、`<head>` 和 `<body>` 标签。）

我疯了吗？可能吧。

*但是*，如果我们已经决定要让服务器能够专注于数据处理，那么我们不妨将尽可能多的渲染和呈现工作转移给客户端。

好吧，我承认，这种极致的简约部分是出于美学考虑。但这也清楚地表明，渲染应用程序并管理其中的所有内容（包括页面标题和所有文档元素的生命周期等）是客户端的职责。

一些开发者提倡在服务器上进行部分渲染，以加快加载速度等。对我来说，一旦我们认识到我们正在构建一个“厚”客户端，我们不如就把它全部放在那里渲染。否则，如果我们的页面状态的一部分是在服务器上渲染的，我们就必须以某种方式将 HTML 重新转换为状态信息。同样，我更喜欢明确的关注点分离。

我现在就能听到尖叫声了，“加载时间和性能怎么办？！？！？！”我宁愿优化应用程序加载*后*的运行方式，而不是从下载初始应用所需的时间中削减几毫秒。另外，让我们记住，那个闪闪发光的、支持 Retina 显示的 logo 或者你使用的背景纹理图片，可能和你整个应用占用的带宽一样多。无论如何，如果你的应用包含在一个文件中（后面会详细讨论），那么对其进行压缩、版本控制并告诉浏览器永久缓存它是相当简单的，这样你的应用每个版本只需要下载一次。

此外，如果你对此持实用主义态度，那么你会意识到在某个时候你可能需要渲染某种注册或登录表单。如果你足够机灵，你可以利用用户第一次访问该页面不可避免要花费的时间来下载应用，这样当用户登录时，他们就已经在一个预缓存的版本上访问了，即使是在第一次加载时！

我将在第 4 章讨论代码组织时介绍更多相关工具和方法。

# 工具与技巧

跟上我了吗？好的，但你具体该怎么做呢？
嗯，让我给你一个简单的例子：

```
// 假设这是来自某处的字符串数组
var myArray = ['hello', 'something', 'awesome'];
if (~myArray.indexOf('hello')) {
    // 什么情况下会调用这里？
}
```

你能用通俗的英语解释一下那个波浪号（~）的作用吗？如果你能，那很好，但你认为你的整个团队都能吗？

现在，与这个比较一下：

```
// 同一个数组：
var myArray = ['hello', 'something', 'awesome'];
if (myArray.indexOf('hello') !== -1) {
    // 当然更清晰一些，对吧？
}
```

或者甚至这个，使用 Underscore 库：

```
// 同一个数组：
var myArray = ['hello', 'something', 'awesome'];
if (_(myArray).contains('hello')) {
    // 同样非常清楚！
}
```

坦率地说，我认为第一个例子在视觉上看起来更好。事实上，我有时在开发一个不打算作为团队项目的库时会使用第一个。然而，如果我正在开发一个其他人将与我一起工作的应用，我会用第二种方式编写它，因为它更明确，并且对可能不熟悉第一个例子中语法的其他开发人员要求更低。

## 代码检查

与可读性一样，代码规范和格式应在整个项目中保持一致。在实践中，如果有多人参与一个项目，这可能很难做到。

分号、制表符和空格是开发者们争论不休的事情。我遇到过的每个开发者都对代码风格有意见（通常是强烈坚持的）。

如果你正在构建大型 JS 应用，而没有对代码进行某种形式的静态分析，那你就是在自找麻烦。它有助于捕获愚蠢的错误并强制保持代码风格的一致性。理想情况下，不应该有人能分辨出你的应用的哪个部分是谁写的。如果你在一个团队中，项目内的所有内容都应该是统一的。你该怎么做呢？我们使用一个由我们团队的 [Nathan LaFreniere](https://github.com/nicholasf) 编写的巧妙工具，简单地命名为 [precommit-hook](https://github.com/nicholasf/precommit-hook)。所以我们只需要在我们的依赖项列表中（在一个 Node 项目中）添加 “precommit-hook”。

它的作用是在项目中安装一个 git pre-commit 钩子，该钩子使用 JSHint 在每次提交前检查你的项目是否符合代码风格一致性。曾经有一个由 Douglas Crockford 编写的工具叫 JSLint。如今，同一项目有一个不那么严格、更可配置的版本叫做 [JSHint](http://www.jshint.com/)。

npm 版本的 JSHint 的一个巧妙之处在于，如果你从命令行运行它，它会寻找一个配置文件（.jshintrc）和一个忽略文件（.jshintignore），如果它们不存在，precommit hook 会为你创建这两个文件。你可以使用这些文件来配置 JSHint 以遵循你为项目定义的代码风格规则。这意味着你现在可以在项目根目录运行 `jshint .`，并对整个项目进行 lint 检查，以确保它遵循你在 `.jshintrc` 文件中定义的代码风格。太棒了，



### 是不是吧？！

我们的 `.jshintrc` 文件通常看起来像这样：

```json
{
  "asi": false,
  "expr": true,
  "loopfunc": true,
  "curly": false,
  "evil": true,
  "white": true,
  "undef": true,
  "indent": 4
}
```

这种方法的妙处在于，它能强制执行一致性，项目规则被包含其中，并且实际上会被提交到项目仓库本身（以 `.jshintrc` 文件的形式）。所以，如果你决定在下一个项目中采用不同的规则集，没问题。这不是一个全局设置；它由运行项目的人定义和调整。你也可以选择在 `package.json` 中通过添加一个 `jshintConfig` 属性来指定你的 jshint 配置，其包含与上述相同类型的配置。

关于样式和样式指南的更深入讨论，我强烈推荐阅读 Airbnb 的 [JavaScript 风格指南](https://github.com/airbnb/javascript)。它将让你很好地了解各种常见的风格差异以及他们做出某些选择背后的原因。如果你想 fork 它并调整为“你们团队的风格指南”，它也是一个绝佳的起点。

### 告别客户端意大利面条式代码。整理你的代码。

在构建复杂的客户端应用程序时，你将面临的最大挑战是防止你的代码库变成一堆混乱不堪的垃圾。

如果这是一个你计划长期维护和修改的长期项目，那就更难了。功能会来来去去。你会尝试一些东西，结果发现那不是正确的选择，然后在代码各处留下旧代码的痕迹。

我绝对*厌恶*混乱的代码。它难以阅读、难以维护、难以协作，而且看起来就是丑陋不堪。除了这些实际原因，我认为我的代码是我的手工艺品。因此，我希望我在编写代码时投入的用心能被阅读代码的人明显地感受到。

复杂性会悄悄向你逼近。如果你不在软件中积极争取简单性，复杂性就会获胜。

这里有一些技巧、拐杖、应对机制和半专业的提示，帮助你保持理智。

### 早重构，勤重构

熵在代码库中是不可避免的。如果我们不持续地修改、简化和统一现有代码以及正在编写的新代码，我们很容易最终得到一个非常庞大、混乱的应用程序。

一些开发者似乎不愿意修改他们已经写过的代码。但是，我相信删除和更新代码是构建应用程序的一个常规且重要的部分。当你刚开始构建应用程序时，你不知道你将如何构建其中的所有东西，所以没有理由把你沿途构建的任何代码视为绝对正确。

代码只是文本，不是法令。它可以很容易地被更改，并且应该在你构建过程中被精简。

不要害怕重构。要害怕构建一个无法维护的垃圾。我发现从长远来看，那成本要高得多。此外，如果你的应用程序被分割成干净、简单的模块，意外破坏其他东西的风险会显著降低。

### 分离视图和状态

这是我构建了许多单页应用程序后学到的最重要一课。你的视图（DOM）应该只是对应用程序的模型状态做出反应。为此，你可以使用任何数量的工具和框架。我经常向接触这些概念的新手开发者推荐阅读 [Backbone 文档](https://backbonejs.org/)。它为这个问题提供了一种清晰的“纯 JavaScript”™ 方法，并作为构建客户端应用程序问题的一个绝佳入门。

本质上，你将在浏览器内存中填充一组模型和模型的集合。这些将存储你的应用程序的所有状态。这些模型应该完全不关心它们如何被使用；它们只是存储状态并广播其变化。然后你会有视图监听模型的变化并更新 DOM。在构建大型应用程序时，分离视图和应用程序状态这一核心原则至关重要。

这种方法常被忽视的一个方面是，如果你决定应用程序应该有一个不同的 UI（这种情况*从来*不会发生，对吧？），或者如果你在同一个 API 上构建另一个应用程序，它提供了灵活性。所有的模型基本上无需修改就可以完全重用。

### CommonJS 模块

我不会陷入关于模块风格和脚本加载器的争论。但我可以告诉你：我没有见过比 CommonJS 模块更干净、更简单的将代码分割成独立模块的机制了。

让我们暂停一下，讨论一下模块为我们做了什么。JavaScript 有全局变量。我的意思是，如果你在变量声明前不加上 `var`，你就创建了一个全局变量，它可以从你应用程序中的*任何*其他代码访问。虽然这*可以*被用于好的目的，但它也给了你很多自缚手脚的绳索。如果没有方法来管理这个，随着你的应用程序增长，知道你在什么时间有什么全局变量将变得几乎不可能，并且可能成为 bug 的一个主要来源。

我们也希望将我们的应用程序构建为独立的微小代码块（又名模块）。那么，我们如何确保每个模块都能访问它需要的东西呢？通过不引用全局变量，并让每个模块显式地 `require` 它需要的其他代码。这就是为什么我们需要一个模块系统。很少有什么比切换到一个好的模块系统对你的代码结构产生更大的积极影响了。

CommonJS 是 Node 中使用的相同风格/概念。遵循这种风格，你可以额外受益于能够在服务器上重用为客户端编写的模块，反之亦然（尽管，重叠通常没那么大）。

如果你不熟悉 CommonJS 模块风格，你的文件最终看起来会像这样：

```javascript
// 你使用特殊的 `require` 函数来导入东西，并且你可以
// 将结果赋值给一个变量
var AmpersandModel = require('ampersand-model');
var _ = require('underscore');

// 你通过像这样声明你的主要导出来向其他模块公开功能。
module.exports = AmpersandModel.extend({
    type: 'navItem',
    props: {
        active: ['boolean', true, false],
        url: ['string', true, ''],
        position: ['number', true, 200]
    },
    init: function () {
        // 做些事情
    }
});
```

就是这样！超级简单。你不会创建任何全局变量。每个使用你模块的文件都可以给它起一个在该模块中最合适的名字。

你只需导出一个构造函数（如上），或一个单独的函数，甚至一组函数。不过，通常我建议你每个模块只导出一个东西。

当然，浏览器本身不支持这些类型的模块（没有 `window.require`）。但是，幸运的是，这可以被修复。我们使用一个名为 [browserify](https://browserify.org/) 的巧妙小工具，它可以让你 `require` 你需要的任何模块。这还包括能够在 `package.json` 文件中声明依赖项，并且只需从 npm 安装可 `require` 的模块到你的项目中。通过这种方法，不需要像 Bower 这样的客户端特定的包管理。你只需在你的包文件中声明你的依赖项并安装它们。

Browserify 将创建一个 `require` 系统，并从你指定为入口点的模块开始，将每个 `require` 的代码片段包含到一个可以发送到浏览器的应用程序包中。

Browserify 是为 Node 编写的，但即使你使用其他东西来构建你的 Web 应用程序，你也可以使用 Node 和 browserify 来构建你的客户端包。最终，你只是创建了一个 JS 文件。所以一旦它生成，该文件就可以像任何其他静态文件一样，由你想要的任何文件服务器提供。

### 穿上你的月球靴

如果你习惯于构建这样的应用程序：应用目录中的每个脚本都在某个 HTML 文件中有一个对应的硬编码的 `<script>` 标签，那么当你切换到使用像 browserify 这样的脚本模块系统时，可能会感到有些困惑。

正如我在第 2 章中提到的，我们真的希望我们的生产环境能够提供一个单一的、经过压缩的、具有唯一文件名的 `.js` 文件，这样我们就可以告诉浏览器永远缓存它。然而，在开发环境中，这远非理想，因为我们不想调试压缩过的

在浏览器中调试代码或每次更改都必须重新构建。因此，为了让开发周期保持愉快，我们的目标是：

1.  无需重启服务器或手动重新编译，即可轻松编辑/刷新客户端JavaScript文件。
2.  能够轻松将浏览器中的代码映射到应用文件夹中未编译版本的正确文件和行号。
3.  在开发环境中提供未压缩的代码。
4.  在生产环境中，提供一个压缩过的、具有唯一名称、可永久缓存的文件，其中包含整个应用。
5.  能够通过一个简单的配置标志在两种状态之间切换。
6.  能够为所有兼容模块使用browserify，但仍然能够将其他库捆绑到我们的应用文件中。
7.  能够以同样的方式提供/压缩/缓存CSS。

由于定义这种类型的浏览器应用“包”是一个常见问题，并且我们希望所有应用都能受益，因此我构建了一个辅助工具来使其更容易使用。

它被称为“moonboots”。要使用它，你可以这样定义你的浏览器应用（假设使用Node和Express）：

```javascript
var Moonboots = require('moonboots');

var clientapp = new Moonboots({
  // The directory where all the client code is stored
  main: __dirname + '/clientapp/main.js',

  // Whether or not to build and serve cached/minified version of
  // the application file.
  // While you're in development mode you don't need to restart the
  // server or do anything other than edit clientside code in your project.
  developmentMode: true,

  // These are the regular JavaScript files (not written in CommonJS style)
  // that we want to include in our application. These all live in client/libraries
  // and will be concatenated in the order listed.
  libraries: [
    __dirname + '/libs/jquery-1.9.1.js',
    __dirname + '/libs/jquery.plugin.js'
  ],

  // These are our stylesheets. They will be concatenated and run through
  // cssmin to minify them.
  stylesheets: [
    __dirname + '/public/css/styles.css'
  ],

  // We pass in the Express app here so that it can handle serving files during development
  server: app
});
```

此时，我们可以告诉Express我们希望它提供我们应用程序的路由。如果你不习惯做客户端路由的单页应用程序，这可能有点难以理解。

由于我们发送的是JavaScript应用程序，而不是渲染好的HTML给浏览器，因此需要客户端读取URL、获取相应数据并渲染该URL所代表的页面。因此，我们需要配置我们的服务器，使其在属于我们客户端应用程序的任何URL上始终返回相同的HTML。我们将在第9章更详细地介绍客户端路由的概念。

你可以通过使用通配符处理程序，或者通过传递正则表达式而不是字符串作为路由定义，在Express中实现这一点。如果你查看[示例应用程序](sample application)，你会看到`server.js`中的相关行如下所示：

```javascript
app.get('*', csrf, clientapp.html());
```

其中`clientapp`是我们上面定义的应用程序。在其上调用`html()`将返回一个请求处理程序，该处理程序在所有相关路由上提供应用程序的基础HTML。通过让辅助工具提供请求处理程序，你仍然可以添加任何你想要的中间件（如示例中的CSRF）。

当你打开一个使用HTML5 push state的应用程序并在其中导航到不同的URL时，通配符URL的必要性变得更加明显。假设我们点击一个按钮，将我们带到应用程序内的/sample。导航到该页面时，浏览器不会发出任何服务器请求，但你会看到URL发生变化。但是，现在你正在查看/sample页面，如果你刷新浏览器，浏览器将向/sample发出请求。因此，如果你的服务器应用程序没有设置为在该URL上提供相同的响应，它将无法工作。

### 关于投入生产环境的说明

Node恰好非常擅长提供静态文件。因此，仅使用Node/moonboots提供生产文件可能对大多数流量适中的应用程序就足够了。在生产模式下，moonboots将使用激进的缓存头从内存中构建并提供应用程序文件。

然而，许多人喜欢使用单独的进程（如nginx或CDN等）来提供静态文件。在这种情况下，你可以在开发过程中使用moonboots，然后生成压缩文件，将其写入磁盘，或在部署过程中将其放到S3之类的存储上。

调用`moonboots.sourceCode(function (source) { ... })`会将基于当前配置生成的源代码作为参数传递给你的回调函数，你可以使用它将其写入磁盘或在grunt任务中将其放到CDN上。这些细节可能超出了本书的范围。但是，关键是，如果这更符合你的应用需求，你当然可以使用这些工具来实现。

### 客户端文件夹的结构

我们的客户端文件夹通常包含以下文件夹：

-   **models (文件夹)：** 包含所有模型和集合的定义。作为一个健全的检查，这些文件中不应有任何与DOM元素或DOM操作相关的内容。
-   **pages (文件夹)：** 页面文件夹是我们存储代表在特定URL渲染的页面的视图的地方。通常这些仍然是“视图”，但由于它们在应用程序中扮演着特殊的角色，将它们放在自己的文件夹中是有用的。
-   **views (文件夹)：** 视图文件夹包含我们所有的Backbone视图（非页面视图），例如主应用程序视图和用于渲染特定类型模型的视图等。
-   **helpers (文件夹)：** 这里是我们放置任何特定于应用程序但在其他模块中有用的客户端模块的地方。例如，我们可能使用它来放置一个辅助模块，用于从应用程序的多个地方向服务器报告指标。
-   **forms (文件夹)：** 存放我们可能有的任何表单视图的地方。我们经常希望为创建和编辑一种类型的数据重用同一个表单。
-   **app.js (文件)：** 这是我们应用程序的主入口点。它创建一个`app`全局变量并实例化主模型和视图。
-   **router.js (文件)：** 这是我们的客户端（Backbone）路由器。它在顶部包含一个URL路由列表和相应的处理程序，其工作是从URL中使用正确的数据实例化正确的视图，并发出可以被我们的主视图渲染到页面容器中的已实例化的页面视图。
-   **libraries (文件夹)：** 这里包含我们使用的所有*不是*像CommonJS模块那样组织的库。因此，像jQuery和jQuery插件这样的东西会放在这里。
-   **templates.js (文件)：** 这是从templates文件夹创建的模块（见下文）。它是一个单一的文件，每个客户端模板对应一个函数。这个文件是自动生成的，所以不要试图直接编辑它。将其放在这里也让我们可以在视图中轻松地要求和使用我们的模板函数。每个模板都有一个对应的模板函数。每个函数接受你的上下文对象并只返回一个HTML字符串。
-   **templates (文件夹)：** 这里是我们存放所有用于客户端应用程序的Jade文件的地方。任何时候你想在应用程序中创建HTML，都可以使用Jade模板并将其放在这里。你可以根据应用程序的需要以任何合理的方式组织这个文件夹。重要的是要理解文件夹会成为template.js模块结构的一部分。例如，在这个模板中，你会看到templates文件夹中有一个pages文件夹，里面有一个名为home.jade的文件。要使用从该文件创建的函数，你可以这样访问：

```javascript
var templates = require('./templates');

// Note that 'pages' becomes part of the structure of your
// imported templates object
var html = templates.pages.home();
```

有关模板的更深入讨论，请参见第8章。

### 创建应用全局变量

那么什么构成一个模块？理想情况下，我建议每个模块都放在

每个文件只导出单一功能。单一导出有助于你明确模块的用途，并使其专注于该任务。目标是让大量模块各司其职，从而让应用组合成连贯的整体。

构建应用时，我会有意创建一个主控制器对象。为方便起见，它通过 `app` 属性挂载到 `window` 对象上。对于专门为该应用编写的模块（位于 `client` 文件夹中的代码），我允许自己使用这个全局变量来执行应用级操作，如导航等。

主应用对象本身无需特殊化。通常我会创建一个对象字面量，包含一个主初始化函数（第10章将详细讲解）。其基本结构如下：

```
module.exports = {
    // 主初始化函数
    blastoff: function () {
        // 将应用对象挂载到 window 上
        window.app = this;
        // 在此渲染主视图、获取数据、
        // 启动历史记录追踪等
        // 详见第10章
        ...
    },

    // Backbone.history 的别名，便于在应用任何位置
    // 执行 app.navigate('/someother/page')
    navigate: function (url) {
        app.history.navigate(url, true);
    }
};

// 运行整个应用，一切从这里开始：
module.exports.blastoff();
```

注意最后一行实际调用了 `blastoff()` 函数。这就是启动整个应用的方式，也是应用的主要入口点。

### 使用事件：模块间通信

如何保持模块间的清晰分离？有时模块间存在依赖，但我们仍希望保持松耦合？一个很好的技巧是触发大量事件，供其他代码作为钩子使用。Node 的许多核心组件都是 `EventEmitter` 类的扩展。这意味着你可以注册处理函数，在对象发生事件时被调用，类似于在浏览器中为页面元素注册点击事件处理函数。

我发现开发者常认为 JavaScript 中的事件是某种神奇或特殊的东西，但其实不然。实际上，从头构建事件发射器是很好的学习练习。它们非常简单，核心思想是：“当这件事发生时，请调用这个函数。”通常你会看到这样的代码：

浏览器环境：

```
document.getElementById('something').addEventListener('click', function () { ... }, false);
```

jQuery 中：

```
$('#something').click(function (event) { ... });
// 或
$('#something').on('click', function (event) { ... });
```

EventEmitter 中：

```
myEventEmitter.on('someEvent', function () { ... });
```

它们的工作原理相同：存储你传递的函数的引用（通常通过将其添加到内部函数数组实现）。当事件发生时，用事件信息调用相关数组中的所有函数。仅此而已，毫无神奇之处。

当你构建可复用组件时，这种模式非常有用。导出继承自某种事件发射器的对象和类，意味着使用你模块的代码可以指定关心的事件，而无需模块自身知晓。

在模块中你认为外部代码可能关心的触发点，只需调用 `this.emit('someEventName', {some: 'data'})`，如果存在该事件的处理函数，它们就会被调用。

事件发射器有多种实现，功能各异。主要涉及事件监听器的注册与注销方式。例如，你可能希望注册一个处理函数仅在事件首次发生时被调用，因此许多事件处理函数在 `on()` 方法外还提供了 `once()` 方法。此外，某些事件处理函数允许你监听特定对象或特定命名空间的所有事件。这些功能可用于记录所有事件（便于调试）或代理事件。

浏览器没有提供可直接使用的 `EventEmitter` 基类，因此客户端代码需要引入一个实现。我们使用的是经过轻微修改的 `wildemitter`（来自 LearnBoost 团队的优秀轻量级实现：@tjholowaychuk、@rauchg 等）。如果你感兴趣，可以在我的 GitHub 上找到它。

除了标准的 `on()`、`off()` 和 `once()` 方法外，它主要增加了两个特性：

1. 通配符事件处理函数：监听对象的所有事件。例如：`emitter.on('*', function (eventName, event) { ... })` 或 `emitter.on('namespace*', function (eventName, event) { ... })`。
2. 分组事件处理函数：注册时可指定处理函数所属分组，然后一次性注销整个分组的处理函数：

```
var WildEmitter = require('wildemitter');

var emitter = new WildEmitter();

// 注册一个处理函数
emitter.on('something', 'group1', function () { ... });
// 在同一分组注册另一个处理函数
emitter.on('someOtherEvent', 'group1', function () { ... });

// 同时释放两个处理函数
emitter.releaseGroup('group1');
```

抛开具体实现细节，所有事件发射器都支持基本的处理函数添加与移除概念。

例如，以下是 `andbang.js` 库的简化版本，该库是用于与 And Bang API 交互的 SDK：

```
// 引入我们的发射器
var Emitter = require('wildemitter');

// 主构造函数
var AndBang = function (config) {
    // 扩展发射器功能
    Emitter.call(this);
};

// 继承发射器但保留构造函数
AndBang.prototype = Object.create(Emitter.prototype, {
    constructor: {
        value: AndBang
    }
});

// 其他方法
AndBang.prototype.setName = function (newName) {
    this.name = newName;
    // 可以触发任意事件
    // 这些只是其他代码可以选择监听的钩子
    this.emit('nameChanged', newName);
};

// 导出到全局
module.exports = AndBang;
```

其他代码要使用此模块时，可以监听事件：

```
var AndBang = require('andbang');
var api = new AndBang();

// 当事件被触发时，此处理函数将被调用
api.on('nameChanged',  function (newName) { /* 执行有趣操作 */ });
```

这种模式使得暴露功能变得简单，无需了解其具体使用方式的细节。

### 数据模型

#### 简单示例

假设你有一个项目列表。当用户点击项目时，你想在视觉上标记为已选中。习惯构建简单应用的人可能会这样做：

```
// 在父列表上注册点击处理函数
$('ul.theList').delegate('click', 'li', function () {
  // 切换点击项目的类名
  $(this).toggleClass('selected');
})
```

现在点击项目会切换类名。jQuery 的 `toggleClass()` 方法会检查是否已包含该类，必要时进行添加或移除。完成！

但通常选择某个项目是有原因的，对吧？所以我们的应用需要对已选项目*进行操作*。

假设用户选择了多个项目，现在想通过点击删除按钮来删除它们。没问题，添加一个按钮处理函数，查找带有 `selected` 类的元素并删除它们。

```
$('button.delete').click(function () {
  // 获取已选 DOM 项目并遍历
  $('ul.theList li.selected').each(function () {
    // 但我们还需要获取每个项目的 ID
    // 以便向服务器传递正确信息
    // 假设使用 HTML5 data 属性
    // jQuery 的 data() 方法可以读取这些属性
    var id = $(this).data('serverId');
    var listId = $(this).data('listId');
    $.ajax({
      type: 'delete',
      url: '/lists/' + listId + '/widgets/' + id,
      success: function () {
        // 执行操作
      },
      error: function () {
        // 以某种方式通知用户
      }
    })
  });
});
```

这还不算太糟，对吧？

但如果需求增加呢？

1. 页面上有多个列表，而不仅是单个。某些操作可以批量执行，但仅适用于部分列表中的部分项目。
2. 某些项目无法删除（因权限不足），但仍可选择并添加注释。
3. 删除只是每个项目可执行的六种操作之一。
4. 必须支持完整的键盘控制，以及鼠标点击处理。
5. 现在需要支持选择顶部项目后按住 Shift 点击底部项目以选择范围。

### 模型登场

如果你从未在客户端代码中使用过模型，它可能并不像听起来那么吓人。其核心思想很简单：我们在浏览器中创建一些独立于DOM的数据结构，用于存放从服务器获取的数据以及任何客户端特有的数据或状态。

上文描述的“选中”状态就是一个典型的客户端特有状态的例子——当我们向API更新一条记录时，并不会把 `{selected: true}` 作为其属性之一发送。服务器对此毫不在意，它仅用于追踪用户界面状态。

那么，模型究竟是什么？它能为我们带来什么？

模型应提供的基本功能是**可观察性**。我的意思是？就像你可以在浏览器中注册一个事件监听器来响应表单输入值的变化：

```
document.getElementById('myInput').addEventListener('change', function () {
  // 处理值的变化
});
```

模型应该让我们能够监听其属性的变化：

```
model.on('change:selected', function (newValue) {
  // 处理新值
});
```

此外，模型应包含便于我们操作数据的功能。这意味着将数据的某些处理形式作为模型的方法暴露出来。假设模型的某个属性代表日期，模型上可能会有一个方法，能基于该日期对象生成格式美观的日期字符串。可以说这是展示层的问题，但模型最终成为暴露日期属性字符串版本的逻辑位置，以实现最大化的重用和一致性。

同时，模型也是对自身执行操作的方法的良好载体，例如在模型更新时通知服务器。

在And Bang项目中，我们大量处理任务。你可以将任务分配给他人、“发送”任务、“稍后处理”任务、“丢弃”任务等等。

因此，每个操作都由任务模型上的一个方法表示，该方法向服务器发送正确的数据，并更新本地模型上的相应属性。

例如，以下是And Bang中任务的`trash`方法：

```
... },
trash: function () {
  if (this.deleteable) {
    this.removing = true;
    this.api('deleteTask');
  }
  return this.deleteable;
},
...
```

它首先检查我们是否有权限丢弃此项目。如果你想知道，这实际上并不用于执行该权限，那是API的工作。

事实上，这里值得稍作展开以强调API的目的。维护自身数据完整性*永远*是API的工作。你不应该*能够*在客户端代码中做任何将API数据置于奇怪或损坏状态的操作。例如，绝不应让你的客户端代码知道如果删除一个列表，也必须去删除列表中的所有项目。那是API的工作。

继续……调用`trash`方法会设置本地状态属性`removing`，然后调用API方法向服务器发送删除任务的命令（本例中通过WebSocket，但传输方式无关紧要）。

但酷的是，仅此而已。当我们想要删除一个控件时，只需找到该控件的模型并调用`.trash()`即可。

在这段代码中，你看不到任何关于从DOM中移除项目的内容。

当我们从API收到任务已被移除的确认时，它会从集合中被移除，这会在集合上触发一个`remove`事件，而视图（代表DOM，将在下一章描述）会监听`remove`事件并将该列表项从DOM中移除。听起来可能有点复杂，但那只是因为你需要描述所有这些关系。一旦理解了，它就变得非常简洁。

假设我们有一个代表该模型的视图，该视图会有一个像这样的点击处理程序：

```
var Backbone = require('backbone');
module.exports = Backbone.View.extend({
  // 我们的事件哈希表（将在下一章解释）
  events: {
    'click .delete': 'handleDeleteClick'
  },
  // 我们的处理程序只是调用"trash"，仅此而已
  handleDeleteClick: function() {
    this.model.trash();
  },
  ...
})
```

或者，你也可以直接在浏览器的JS控制台中输入：

```
> app.currentTeam.tasks.get('someId').trash();
```

你会看到所有事情仍然像你点击删除时一样发生。任务将在服务器上被删除，并从DOM中移除。

### 将模型用于一切

随着应用程序变得越来越复杂，未能将所有状态存储在应用程序中的一个（且唯一一个）位置，将成为那些让你放弃开发、转行园艺的bug的根源。

那么，我说的*在应用程序中存储所有状态*是什么意思？这很简单。如果你发现自己在检查某个元素是否有某个类名，并据此决定行动方向，那你就做错了。

有两条简单的规则：

+   1. 所有输入，无论是来自用户还是API，*永远*只应该调用方法或更新模型的属性。
+   2. 始终将模型作为应用程序中的“真实来源”。永远不要在模型之外的任何地方“查找”状态信息。

### 将此方法应用于我们的控件示例

在考虑行为之前，我们先考虑数据。列表中的这些项目代表某些东西。在思考它们如何呈现之前，我们先为*那个东西*建模。我们只需创建一个代表列表项目的模型集合。

**models/widgetCollection.js**

```
var Backbone = require('backbone');
var WidgetModel = require('./models/widget')

// 本模块的主输出（仅为集合）
module.exports = Backbone.Collection.extend({
  // 指定此集合的模型类型
  model: WidgetModel,
  // 代表此资源的RESTful API URL
  url: '/widgets'
});
```

只需想象一下，团队能够并行工作，编写的代码不需要因为有人想改变应用程序布局而被丢弃，这会产生怎样的影响。

### 模型替代方案

为了提供可观测性，模型通常会提供某种事件注册系统，以及一种设置和获取某些“受保护”属性的方法。

很长一段时间里，我凡事都使用 Backbone 模型。它们的代码相当简单且易读（是的！）；它们也很灵活、易于使用。此外，我总体上非常推崇 Backbone 的原则和架构。

然而，你会注意到所有示例都使用 `AmpersandModel` 而不是 `Backbone.Model`。

尽管我们 &yet 团队对 Backbone 充满热爱，但有几个因素最终促使我们创建了 [Ampersand.js](http://Ampersand.js)。

Backbone 的简洁性令人赞叹，并且解决了客户端应用程序开发中的许多常见问题。但我们怀念 node 领域中微小模块那种专注的简洁性。

我们想要一种风格和理念相似，但能完全拥抱微小模块、npm 和 browserify 的方案。关于这些工具的更多信息，请查看 [Ampersand.js 网站](http://Ampersand.js site)。

我们希望模型具备的具体特性是：

+   1. 可读性

如果模型是我们应用程序的核心（理应如此），那么某人应该能够打开模型的代码并*阅读*出它存储了哪些属性以及这些属性的类型。这对于让人们快速上手并为项目做出贡献是*至关重要*的。

#### 2. 派生属性

很多时候，你从服务器获取的数据格式并非你想要呈现的格式。一个经典的例子是名字和姓氏。很可能它们从 API 以独立字段的形式传来，但实际上，在应用程序中展示用户名的大多数地方，格式都是：`firstName + ' ' + lastName`。在 Backbone 中，你可能会创建一个名为 `fullName()` 的方法，调用时返回这个值。当你想将这个值绑定到 DOM 中的某个位置时，烦人的事情就来了。你必须监听 `firstName` 或 `lastName` 的变化，然后再次调用该方法并将结果放入 DOM。有两件事我不喜欢这样做：

+   1. 从*感觉上*说，`fullName` 或者甚至 `name` 应该能够像访问 `firstName` 或 `lastName` 一样被访问。为什么我不能直接用 `user.name` 呢？

    2. 我希望能在一个地方监听变化。所以，与其用 `model.on('change:firstName change:lastName', doSomething)`，似乎我应该能够只监听 `change:name` 的变化，并且模型足够智能，知道无论是名字还是姓氏变化，都调用那个处理器。

#### 3. 直接访问属性

在大型应用程序中，你与模型打交道的次数**非常多**。在我看来，到处都需要调用 `get` 和 `set` 并不太理想。ECMAScript 5（也就是现代浏览器中可用的 JS 规范版本）允许使用 `getters` 和 `setters`，这意味着你实际上可以处理简单的赋值。用一个例子来说明会更清楚：

```
// 没有 getter/setter 的情况（Backbone 模型）
model.set('firstName', 'Henrik');

// 有 getter/setter 的情况（AmpersandModel）
model.firstName = 'Henrik';
```

我是什么意思？即使没有 getter/setter，你也可以直接在对象上设置任何你想要的属性，对吧？！

是的！但这样设置是无法被观测到的。

Getter 和 setter 允许我们即使在属性被直接设置时也能触发那些 `change` 事件：

```
model.on('change:firstName', function () {
  console.log('firstName changed!');
});

// 即使直接设置属性，上面注册的回调
// 仍然会被调用。
model.firstName = 'Henrik';
```

Getter 和 setter 给了我们巨大的灵活性，这可能是坏事。例如，我们可以在访问属性时让 getter 运行任何我们想要的代码并返回任何值。

```
trickyModel.firstName = 'Henrik';

console.log(trickyModel.firstName);
// 尽管上面看起来只是进行了赋值，
// 我们可以让它输出*任何*我们想要的东西。
```

关于如何使用 getter/setter 的简要说明

请务必阅读下面的警告，但对于不熟悉的人来说，稍微解释一下 getter 和 setter 的写法可能会有用。有两种语法选项。

第一种是直接使用 `get` 和 `set` 操作符来定义这些方法：

```
var myObject: {
  _properties: {},
  get name () {
    return this._properties.name;
  },
  set name (value) {
    this._properties.name = value;
  }
}
```

第二种是使用 `Object.defineProperty()`：

```
var myObject = {
  _properties: {}
};

Object.defineProperty(myObject, "name", {
  get: function () {
    return this._properties.name;
  },
  set: function (value) {
    this._properties.name = value;
  }
});

// 还有 defineProperties（复数形式）
Object.defineProperties(myObject, {
  lastName: {
    get: function () { ... },
    set: function () { ... }
  },
  fullName: {
    get: function () { ... },
    set: function () { ... }
  }
})
```

> 警告！

可以想象，这种强大的能力给了你*很多*可以让你自缚手脚的绳索，因此，应该*非常*谨慎地使用这个功能。

有些人认为，我理解他们的观点，使用这个特性过于魔幻。如果你有这种感觉。幸运的是，在我们快乐的模块化世界里，你可以直接使用普通的 Backbone 模型。

然而，我碰巧认为在模型的上下文中，getter/setter 实际上可以使我们的代码更健壮、更易读。但是，我*只*将它们用于模型属性，并且只以可预测的方式使用。

#### 4. 类型强制

JavaScript 语言是动态类型的，这很棒。但我们已经说过，我们将模型作为应用程序的*核心*。知道某个属性是某个特定类型对于消除愚蠢的错误和保护我们自己非常有用。

让我们用一个简单的用户模型来比较两者。在 Backbone 中，没有定义属性的标准方式。相反，你只需设置一个值，就好像它存在一样，然后它就存在了。

```
// Backbone 模型，不需要定义。
// 甚至没有标准方式来定义它应该存储的属性。
var model = new Backbone.Model();

model.set({
  firstName: 'Henrik',
  lastName: 'Joreteg'
});

// 现在我可以获取它们
model.get('firstName'); // 输出 'Henrik'
```

简单、优雅、灵活。但是，假设我在大型应用程序另一部分的某个视图代码中设置了这些值，我怎么知道我有哪些可用的属性，或者它们叫什么？

如果我是通过调用 API 获取数据，并使用返回的数据来设置模型的属性，那么我有两种选择来弄清楚我存储了什么数据以及我的视图有哪些可用数据。要么检查请求以知道我应该有哪些属性，要么在运行时在控制台中检查它，看看我的模型包含哪些属性以及它们的名称。

这看起来对开发者不太友好。

想想我错过了多少信息：

+   1. 我有哪些属性？
    2. 这些属性包含什么类型的值？
    3. 我能相信这个属性总是包含一个值吗？
    4. 这是客户端状态属性还是我们从服务器获得的数据？
    5. 当我需要将模型更新到服务器时，哪些属性应该被发送？
    6. 一个属性是否由其他属性计算得出？如果是，我如何保持它是最新的？
    7. 也许最重要的是，我到哪里去找上述问题的答案？

当然，下面的例子很蠢，但如果我写了一些愚蠢的代码（我们有时都会这样，对吧，人类？！）怎么办？

```
// 没有任何阻止你将 firstName 属性
// 设置为日期对象。
model.set('firstName', new Date());
```

当然，你可能能在一定程度上把所有信息都记在脑子里，但当第二个开发者来看这段代码时怎么办？或者当你在六个月（甚至两周）后回来看这段代码时会怎样？你到哪里去看应用程序的结构？你不得不深入挖掘视图来寻找答案。

我更希望模型是存储状态的显式文档。

看看在 AmpersandModel 中这会是怎样的：



### 模型备选方案

文件: models/user.js

```javascript
var AmpersandModel = require('ampersand-model');

module.exports = AmpersandModel.extend({
  type: 'user',
  // 我们从服务器获取的属性
  props: {
    // 这里是定义属性的简写语法：
    // 第一个是类型，第二个是是否必需，最后一个是默认值。
    firstName: ['string', true, ''],
    lastName: ['string', true, ''],
    // 你也可以更明确地
    // 传递一个对象
    middleName: {
      type: 'string',
      required: true,
      default: ''
    },
    // 或者更简单，最低要求是
    // 需要一个类型，例如：
    isAwesome: 'boolean'
  },
  // 会话属性的定义和工作方式与普通属性完全相同。
  // 区别在于，它们在保存（save()）等操作时
  // 不会被发送到服务器。
  session: {
    selected: ['boolean', true, false]
  },
  // 派生属性是由其他信息构建的getter。
  // （你无法设置派生属性，这是有意为之的）
  derived: {
    // 派生属性的名称。
    // 在这种情况下，引用"model.fullName"
    // 将返回调用下面函数的结果
    fullName: {
      // 我们指定此派生属性依赖于哪些属性
      // （这意味着如果这些属性改变，
      // 派生属性也会改变）
      deps: ['firstName', 'lastName'],
      fn: function () {
        return (this.firstName + ' ' + this.lastName).trim();
      },
      // 结果默认会被智能缓存，这意味着
      // 除非依赖项的值自上次以来发生了变化，否则不会重新运行该函数；
      // 除非新的派生值确实不同，否则不会在派生值上触发`change`事件。
      // 通过仅在派生值更改时触发change事件，与普通Backbone相比
      // 可以显著提高性能。
      // 我们当然也可以将此设置为false，这样结果将永远不会被缓存。
      cache: true
    }
  }
});
```

文件: hypothetical_app.js

```javascript
// 从上面引入我们的用户定义
var User = require('./models/user');

// 创建一个该用户模型的实例
```

通过强制执行这种级别的属性定义，我们始终确保我们的模型——作为应用程序的“骨干”（双关语）——是易于理解的代码，有助于记录应用程序的构建方式。

#### 5. 更好地处理列表/日期

使用getter/setter处理模型的另一个论点是，它使得观察对象属性的变化成为可能。至少在使用数组和日期作为属性时是这样。

由于数组和日期在JS中是对象，它们是通过引用传递的。

那么，如果我们想将ID列表作为用户的属性来存储，会发生什么？

在Backbone中，我们如何获得change事件？

```javascript
var model = new Backbone.Model();

model.set('ids', ['23', '25', '47']);
```

```javascript
// 如果我们想获取它们并进行修改
var myIds = model.get('ids');

// 如果我们现在修改它...
myIds.reverse();

// ...并把它设置回去
model.set('ids', myIds);

// 我们永远不会从Backbone得到change事件
```

如果你理解JavaScript，你会意识到这不是Backbone的缺陷，只是因为JavaScript按引用传递对象。

因此，当Backbone收到“set”事件时，它只是比较 `this.get('ids') === newIds`，这将始终为true，因为你在比较同一个对象，而不是它的副本。

对于日期也是如此。如果你获取一个日期对象，在其上调用一个方法，比如`setHours()`，然后再设置回去，你永远不会得到change事件。所以你不知道你需要更新视图。

我们可以在那些*我们*明确希望这种行为的情况下，通过getter/setter来解决这个问题：强制模型在我们访问属性时总是给我们一个新对象。

```javascript
var AmpersandModel = require('ampersand-model');

// 设置一个简单的模型定义
var DemoModel = AmpersandModel.extend({
  props: {
    ids: ['array', true, []]
  }
});

// 然后我们使用它
var model = new DemoModel();

// 获取我们的数组
var arr = model.ids;

// 修改它
arr.push('something');

// 这现在触发了change事件
model.ids = arr;
```

### 模型总结

模型应包含以下内容：

1.  我们从API获取的属性
2.  我们需要用于跟踪客户端状态的属性（selected等）
3.  验证自身数据完整性的机制
4.  我们可以调用来更新或删除服务器上相应模型的方法
5.  用于以某种方式描述或处理属性的便捷访问器（又名派生属性），以便重用
6.  子集合（如果适用）

模型应*永远不*包含：

1.  任何操作DOM的内容
2.  任何DOM事件处理程序

你可以在 [Ampersand.js 文档](https://docs.ampersandjs.com/) 中阅读更多关于ampersand-model的内容。

## 视图

为了遵循一个非常老套的说法，视图是实践发生的地方。它是你的模型层与DOM相遇的地方。

在深入细节之前，让我们先谈谈为什么我认为视图是一个很好的模式。它们提供给我们的主要是一个干净的方式来封装和存储应用程序如何与DOM交互的所有逻辑。事实上，它比这更具体；我们将它们用于封装DOM中*特定元素*的所有逻辑。每个视图负责单个元素的内容、事件处理和更新，视图中的事件处理程序将用户操作转换为对模型的更改。

正如我在前几章已经暗示的那样，分离应用模型和视图为我们提供了*极大的*灵活性。我们可以更改整个应用程序的布局和HTML结构，而无需更改应用程序从API获取、存储或更新数据的任何方式。因此，就像CSS帮助我们清晰地将文档的样式与HTML内容分开一样，视图帮助我们将DOM创建、更新和事件从我们应用的模型层中分离出来。

视图的另一个*巨大*好处是它们让我们可以将所有事件处理程序（点击处理程序等）干净地捆绑在一起，并与DOM的相关部分关联。如果你曾经尝试过在没有视图的情况下构建单页应用，你就会知道管理大量的事件处理程序往往是bug、内存泄漏和混乱代码的一个主要来源。

有许多工具、框架和方法来处理这一层——都带有不同程度的“魔法”。

因此，为了延续我们追求可读性和关注点分离的主题，我们需要简单、明确、声明式的东西。

Backbone视图为构建视图层提供了一些非常棒的基础模式：

1.  一个由视图控制的根元素，在视图内可通过 `this.el` 访问。
2.  一个主要的模型和/或集合，分别通过 `this.model` 和 `this.collection` 访问。
3.  一个负责用适当内容填充和维护该基础元素的 `render()` 方法。
4.  一个可选的 `initialize()` 方法，用于任何必要的设置。
5.  注册DOM事件处理程序的简写方式（`this.events` 哈希）。
6.  一种处理视图及其注册的任何监听器的方式。

但是，它们*相当*基础，因此，我们将扩展Backbone视图以实现：

1.  使用我们在第8章中描述的预编译模板函数进行简单模板化。
2.  一种声明模型/模板绑定的简单方式。



### 介绍 AmpersandView

正如我之前提到的，Backbone 视图的作用范围非常有限——这是有意为之。以下解释直接引自 Backbone 文档：

> Backbone 视图几乎更多是一种约定，而非代码——它们不会为你决定 HTML 或 CSS 的任何内容，并且可以与任何 JavaScript 模板库一起使用。其核心思想是将你的界面组织成逻辑视图，由模型支撑，每个视图都可以在模型发生变化时独立更新，而无需重绘页面。

Backbone 的总体方法是提供一些简单的组件和模式，由你根据需要进行应用。这种非指令性的灵活性是 Backbone 如此流行的重要原因之一。

然而，随着你开始构建越来越多的应用程序，你会发现自已在反复解决类似的问题。在纯 Backbone 项目中，我们发现自己总是在创建一个 `BaseView`，其中包含许多我们希望所有视图都具有的通用辅助函数和模式，我们用它来构建应用中的所有视图。有一天，我发现自己在将一个 `BaseView` 从一个项目复制粘贴到另一个项目，于是决定将其发布到 npm 上。

这就是 AmpersandView 的诞生过程。它就像一个 Backbone 视图，但为我们提供了一些额外的便利。

具体来说，它提供了以下功能：

- 1. 声明式数据绑定。
- 2. 一个 `.renderWithTemplate()` 方法，它在每次渲染时会执行我们想要做的几件事。
- 3. 一个 `.listenToAndRun()` 便捷方法，用于将视图方法绑定到模型事件，同时保持视图作为上下文并立即触发它们。
- 4. 一个 `.renderCollection()` 方法，用于在视图中的指定容器元素内为集合中的每个项目渲染一个视图。

我们将逐一探讨这些功能。但首先，让我们弄清楚如何在应用中组织我们的视图。

### 视图层次结构

当你开始使用视图构建应用程序时，你会发现将内容分割为子视图是合理的。这就引出了一个问题：你如何确定将应用布局的哪些部分拆分为子视图？

我通常从一个主视图开始，将其放在 `views/main.js` 中。主视图以 `<body>` 作为其根元素。它只渲染一次，并创建应用的主布局，通常会渲染多个子视图。它也成为注册“全局”事件处理程序（如键盘快捷键或应用范围的点击处理程序）的逻辑位置。

布局会因应用而异，但通常有一些始终存在的元素是布局的一部分（导航等），我通常会有一个主要的内容容器，根据 URL 进行切换。我通常给它一个 `id` 为 `pages`，然后使用一个名为 `ampersand-view-switcher` 的辅助模块，根据 URL 将 `PageView` 渲染到该容器中。

视图切换器只是一种处理视图切换的方式。默认情况下，它只是渲染你提供的视图并将其附加到容器中，并移除那里可能存在的任何现有视图。但我们也可以提供自定义的过渡方式。例如，我们可能希望页面能够设置页面上的 `<title>`。

以下是一个使用 AmpersandView 时主视图可能的样子示例：

```javascript
var AmpersandView = require('ampersand-view');
var ViewSwitcher = require('ampersand-view-switcher');
var templates = require('./templates');

module.exports = AmpersandView.extend({
    // 我们的模板函数，返回一个 HTML 字符串
    // 这也可以只是一个字符串。模板语言无关紧要。
    // 它只需要是一个接受参数并返回字符串的函数。
    template: templates.main,

    render: function () {
        // 继承自 AmpersandView，它渲染主模板
        // 并将其插入根元素。
        this.renderWithTemplate();
        // 为该元素设置我们的页面切换器
        this.pageSwitcher = new ViewSwitcher(this.get('#pages'), {
            // 这里我们提供一些在每次切换应用页面时想要执行的操作。
            show: function (newView, oldView) {
                // 设置我们的文档标题
                document.title = newView.pageTitle || 'my awesome app';
                // 滚动到顶部
                document.body.scrollTop = 0;
                // 也许在我们的应用全局对象上存储当前页面的引用，
                // 以便从浏览器控制台轻松访问。
                app.currentPage = view;
            }
        });
    }
});
```

### 注意事项：理解 `this.$` 和 `this.get`

在上面的示例中，在 `render` 方法里，你会注意到我们传递了：`this.get('#pages')`。在 Backbone 中，你会做 `this.$('#pages')[0]` 作为子视图的 `el` 参数。你可能想知道，为什么不直接传递 `$('#pages')` 甚至直接传递 `document.getElementById('pages')`？

原因是我们不能假设在调用此方法时视图已附加到主 DOM 树。如果你尚未将其附加，其他选择器查询将无法找到正确的元素，因为它们还不在主文档树中。事实上，通常父视图会在其自身的 render 方法中调用子视图的 `render()`，然后将结果附加到 DOM。这完全是有意为之，因为在主 DOM 树外部创建 DOM 元素要快得多，只附加和绘制一次即可。

因此，为了解决这个问题，Backbone 视图为每个视图创建了一个名为 `$` 的方法。此方法在功能上等同于普通的 jQuery 选择器，如 `$('.item')`。*但是*，它只在视图的元素内查找匹配项。这不仅更快（因为需要遍历的 DOM 更少），而且更重要的是，即使视图的元素*尚未附加到 DOM*，它也能在视图的元素内找到与选择器匹配的元素。Ampersand-View 的 `.get()` 方法工作原理类似，它只在*视图的根元素内*搜索以检索匹配项。

如果以上内容有点过于复杂，只需知道，当试图获取视图内的元素时，通常应该使用 `this.$('.yourSelector')` 或 `this.get` **而不是** `$('.yourSelector')`。

为了保持关注点分离，我很少直接从 JavaScript 设置样式属性。我认为那是 CSS 的工作。因此，我的大部分工作是根据底层模型的属性值来切换类名。

这就是 AmpersandView 发挥作用的地方。与我们在上面描述的在 `events` 哈希中声明事件处理程序的方式类似，我们也可以在视图中声明各种类型的数据绑定，如下所示：

```
var templates = require('templates');

  template: templates.widget,
  events: {
    'click .delete': 'handleDeleteClick',
    'keyup input.search': 'handleSearchKeyUp'

  // We simply list our bindings here
  bindings: {
    // This simple text binding means
    // we put the property value of the
    // model in this view into the
    // element that matches the
    // '.profileName' selector as text.
    'model.name': '.profileName',
    // There's a few different binding types
    // 'booleanClass' bindings will add or remove
    // a class with the name provided based on
    // the truthiness of the property.
    'model.selected': {

      selector: '.container',
      name: 'active'
    }
  },
  render: function () {
    // This we inherit from ampersand-view
    this.renderWithTemplate();
  },
  handleDeleteClick: function () {
    this.model.delete();

  handleSearchKeyUp: function () {
    var inputVal = this.$('.search').val();
    this.collection.each(function (model) {
      model.matchesSearch = this.name.indexOf(inputVal) !== -1;
    });
```

### AmpersandView 的便捷方法

#### .renderWithTemplate();

Backbone 文档中提倡的通用模式是使用模板来填充视图根元素的内容。这样，你就永远不必重新注册任何 DOM 事件处理程序，因为它们附加在视图的根元素上。采用这种方法（对于某些用途来说是完美的），你只需在模型中的任何内容发生变化时调用 `.render()` 即可。

如果你有一个渲染单个模型的简单视图，那么绑定视图就会变得非常容易。你只需做类似这样的事情：

```
var Backbone = require('backbone');
var _ = require('underscore');
var templates = require('templates');

module.exports = Backbone.View.extend({
  template: templates.user,
  events: {
    'click .myClass': 'myHandler'
  },
  initialize: function () {
    // Register a single change handler for the model
    this.listenTo(this.model, 'change', _.bind(this.render, this));
  },
  render: function () {
    // We simply fill the contents of the current element with
    // the rendered HTML using the model's current attributes each time.
    $(this.el).html(this.template(this.model.toJSON()));
  },
  myHandler: function () {
    // Do something
  }
});
```

此时，我们对该模型所做的任何更改都将简单地重新渲染整个 HTML。巧妙、简单、易于实现。

然而，这并不总是你想要的，尤其是在实时应用程序中，当一个传入事件到来并在你未准备好时更改了模型。但也许一个更有说服力的例子是你想使用 CSS3 过渡和动画的情况。如果我们想添加一个触发过渡的类，简单地重绘整个容器实际上并不会触发它，因为实际上从未有过过渡。

此外，对我来说，编写仅包含视图元素内容的模板感觉不太对：

```
<h1>My page</h1>
<p>My content</p>
```

编写包含根元素本身在内的*整个*视图模板似乎更符合逻辑：

```
<section class="page">
  <h1>My page</h1>
  <p>My content</p>
</section>
```

因为现在，只需查看那个模板，我就能知道它是什么，而无需知道哪个视图将使用它。

此外，如果我想在根元素上包含一些条件类或其他属性，我可以声明式地在模板中与其他内容一起完成，而不必在视图的 render 方法中执行。

现在，来看 `renderWithTemplate(contextObject)`。这简单地封装了使用 `template` 属性渲染视图所需执行的所有操作，同时替换整个现有根元素并确保事件哈希中的所有事件处理程序都已注册。如果你的 `template` 是一个函数，它将使用你调用 `renderWithTemplate` 时传递的 contextObject 来调用。

最基本的情况是，`template` 可以是一个简单的 HTML 字符串，但它也可以是一个返回 HTML 字符串的函数，或一个返回 DOM 元素的函数。

#### .listenToAndRun();

非常常见的是，当你想监听模型上的某些变化时，你通常希望：

1. 绑定处理程序，以便在调用时，`this` 是视图。
2. 运行绑定的处理程序一次，以便其效果应用于 DOM。（这避免了在模板中重复处理程序中已有的逻辑）。

`.listenToAndRun()` **同时为你做了这两件事。**

所以，你不必这样写：

```
...
initialize: function () {
  this.listenTo(this.model, 'change', _.bind(this.doSomething, this));
  this.doSomething();
}
...
```

你可以直接这样写：

```
...
initialize: function () {
  this.listenToAndRun(this.model, 'change', this.doSomething);
}
...
```

### 关于在模板中定义绑定（类似 AngularJS、Ractive）的说明

市面上有几个库，允许你在模板中指定哪些信息应该放到 DOM 的哪些位置，然后它们会自动为你创建事件绑定。

基本上，你会有一个像这样的模板：

```
<div>
  <p>Hello {{ name }}</p>
</div>
```

然后你将模板与模型结合起来，它们就会自动绑定。这是一个简化的伪代码示例：

```
var template = require('compiled-template-from-somewhere');
var model = require('./models/some-model');

document.body.appendChild(template(model));

// 然后，如果你修改了模型
model.set('name', 'Sue');

// DOM 会自动更新为：
/*
<div>
  <p>Hello Sue</p>
</div>
*/
```

这实际上是一个偏好问题，幸运的是，要切换成你喜欢的任何方法都很容易。

对于简单的、在这里放这段文本的绑定，一切都很直接。

可能变得有点复杂的情况是，当你实际需要的是一些逻辑时。比如说，你想根据模型上的一个布尔属性，从一个类列表中添加或移除一个项；或者说你想添加或移除整个属性，比如 `checked`。为了让模板语言知道这是我们想要的，它必须有一种新的语法来指示绑定应该如何行为。

在我看来，这就是许多这类语言走得太远的地方。它们试图在模板中声明太多逻辑。就个人而言，在标记语言中编写代码感觉不太对。

重要的是要认识到，模板语言方法和声明式绑定 *实际上是在做同样的事情*。它们只是一种构建函数集合的方式，能够将“嘿，模型上的这个值变了”这样的事件，转换成实际的、更新 DOM 的 DOM 方法，例如：`someElement.setAttribute('href', '/my-url')`。

如果你想使用一种也能为你处理绑定的模板语言，我强烈推荐：Phil Roberts 的 domthing。它是 mustache 的一个变体，允许你使用如下所示的模板自动绑定：

```
<div class="entry">
  <h1>{{title}}</h1>
  <div class="body">
    {{body}}
  </div>
</div>
```

但它也会自动为这些属性创建到最终 DOM 的绑定。

### 关于可重用性的说明

就个人而言，我希望确保我可能想在另一个项目中重用的任何东西都不依赖于特定的模板语言。

所以，对于任何不特定于我正在构建的应用程序的东西，我建议只使用 HTML 字符串和声明式绑定，以最大化可重用性。

### 别再把模板引擎发往浏览器了！这是一个事后看来显而易见的、能快 6 到 10 倍的创建模板的方法。

如今，越来越多的 HTML 是在客户端渲染的，而不是由服务器预渲染后发送的。所以，如果你正在构建一个大量使用客户端 JavaScript 的 Web 应用程序，你无疑会想在浏览器中创建一些 HTML。

### 我们过去的做法

首先，回顾一下历史。当我第一次写 ICanHaz 时，我只是想减轻在浏览器中生成大量 HTML 的痛苦。

为什么这很痛苦？主要是因为 JavaScript 并不干净地支持多行字符串，也因为 JS 中没有内置强大的字符串插值系统。

为了解决这个问题，ICanHaz 和许多其他客户端模板系统一样，使用了一个 hack 来更容易地向浏览器发送任意字符串。事实证明，如果你给 `<script>` 标签一个不是 `text/javascript` 的 `type` 属性，浏览器会忽略其中的内容。因此，ICanHaz 会读取页面上标记为 `<script type="text/html">` 的标签内容，这些标签可以包含模板或任何其他多行字符串。然后，ICanHaz 会读取这些模板，并使用 Jan Lehnardt 出色的 mustache.js 将每个模板转换成一个函数，你可以调用该函数并传入你的数据来渲染字符串。例如：

这段 HTML：

```
<script id="user" type="text/html">
  <li>
    <p class="name">Hello my name is: {{ name }}</p>
    <p><a href="http://twitter.com/{{ twitter }}">@{{ twitter }}</a></p>
  </li>
</script>
```

被 ICanHaz 读取并转换成一个函数，你可以像这样用自己的数据调用它：

```
// 你的数据
var data = {
  first_name: "Henrik",
  last_name: "Joreteg"
}

// 我可以 has 一个用户？？
html = ich.user(data)
```

这效果相当好，比手动构建 HTML 字符串干净得多。显然，很多人也是这么想的，因为它是一个相当流行的库。

### 为什么这并不理想

它完全有效，但仔细想想，这有点傻。我们让客户端做了一堆额外的解析和编译工作，而这些工作实际上我们可以提前完成。当然，在浏览器中进行解析和编译 *也* 意味着我们必须向浏览器发送一个完整的、能够解析和编译模板的模板引擎。

#### 下一个迭代

我最终意识到，在客户端进行模板化时，你真正想要的其实就是 ICanHaz 提供的最终结果：一个你调用并传入数据就能返回 HTML 的函数。

通常，智能模板引擎，比如新版本的 mustache.js，会为你做这件事。一旦模板被读取，它就会被编译成一个函数，该函数会被缓存并用于后续渲染同一模板。

想到这里，我开始疑惑，为什么我们不直接将 JavaScript 模板函数发送给客户端，而不是在客户端进行所有的模板解析/编译呢？

嗯，坦白说，因为我不知道有什么好方法可以做到这一点。

我开始四处寻找，并意识到 [Jade](https://jade-lang.com/)（我们在 &yet 已经用得很多了）支持作为单独的进程进行编译，结合一个小的运行时代码片段，这使你可以创建只需要一个小型运行时而不需要整个模板引擎就能渲染的 JS 函数。这真是太棒了！

因此，为了更容易使用，我写了一个小工具：[templatizer](https://github.com/colinwren/templatizer)，你可以在服务器端运行它（使用 Node），它接受一个包含 Jade 模板的文件夹，并将它们转换成一个 JavaScript 模块，你可以将该模块包含在你的应用程序中，其中包含每个模板文件对应的一个函数。每个模板函数只需接受一个上下对象，并返回一个插入了这些值的字符串。

### 结果

根据我的测试，实际渲染模板的速度 **快了 6 到 10 倍**。此外，你向浏览器发送的代码 *少得多*（因为你没有发送整个模板引擎），而且你没有让浏览器去做一堆你本可以提前完成的工作。

### 我们能更快吗？

可能。一旦你身处浏览器环境中，使用 DOM 方法构建 DOM 元素，比发送必须与值进行插值然后被浏览器解析以创建 DOM 元素的 HTML 字符串要快。

如今，我们看到越来越多的模板语言编译成 DOM 方法，以获得额外的性能提升。

权衡之处在于，你无法在服务器端（那里没有 DOM）使用那些同样的编译好的模板，除非你模拟（shim）一大堆 DOM 方法。

此外，正如我在上一章所讨论的，你通常不仅仅想创建 DOM，还想更新它。所以还有整个数据绑定的方面，这可能在模板层就能处理。

同样，如果你对这种方法感兴趣，请查看 [domthing](https://github.com/philroberts/domthing) 或 [htmlbars](https://github.com/tildeio/htmlbars)。

好消息是，我们实际上不必做出这些权衡。通过对 Backbone 路由器和 HTML5 push state 的巧妙运用，浏览器应用可以征服世界。下面解释其工作原理……

### 换汤不换药的 URL

从服务器的角度看，我们实际上如何“将路由控制权交给客户端”？嗯……网络的工作方式并非如此，对吧？当用户在浏览器中输入你应用的 URL 时，服务器必须响应实际的 HTTP GET 请求。

所以我的意思仅仅是你在多个 URL 返回相同的应用 HTML。

例如，无论你访问的是：

https://andbang.com/andyet/chat

还是

https://andbang.com/basecamp

服务器都会返回这段 HTML：

```
<!DOCTYPE html>
<script src="/!.js"></script>
```

可以把它理解为一个 URL 块，它们都只提供该应用，这样可能更容易理解。

如果你使用 Express 和 Node，实现起来相当容易。

```
app.get('/other/thing', function () {
    // 你仍然可以在特定 URL 提供其他支持页面
    // 和简单的内容。
});

// 但你想要某种 catch-all 来匹配
// 你希望单页应用可用的 URL 范围：
app.get('*', function (req, res) {
    res.sendFile('sameSh*t.html');
});
```

当然，大多数框架都可以做到这一点，甚至通过 nginx 配置也可以。

但最大的区别在于，此时我们已经让浏览器应用而非服务器负责查找/获取正确数据和渲染正确视图。

### 如何处理客户端路由

And Bang 为每个任务都有一个详情页，其 URL 结构如下：

https://andbang.com/andyet/tasks/47

因此，如果用户在浏览器中输入该 URL，他们将看到该任务的详情视图。此外，如果他们在应用的其他地方，通过点击列表中的任务导航到该任务视图，页面不会重新加载，但当你查看浏览器中的 URL 栏时，你就在该页面上。

Backbone 的路由器对于处理所有这些事情非常方便。

但是，为了理解这在实践中如何运作，我们需要稍微谈谈应用的启动序列。

### 3... 2... 1... 发射！

通常，在你准备好“响应”客户端代码中的特定 URL 之前，会有一个相当具体的加载顺序需要完成。

通常，该顺序大致如下：

- 初始化你的主应用对象。（我一直在谈论的“app”全局对象。）
- 将几个模型集合附加到该 app 全局对象。
- 初始化并填充一个代表当前登录用户的单一“me”对象，并存储会话特定状态。
- 在 <body> 标签内渲染应用布局视图。
- 获取任何需要的应用范围数据。
- 然后触发客户端路由器

现在用代码表示：

```
module.exports = {
  // 主启动函数。这是
  // 你应用的入口点。
  launch: function () {
    // 显式创建一个名为 "app" 的全局对象。
    // 首先这样做意味着它*总是*存在
    // 如果我们需要从视图中访问它。
    window.app = this;

    // 附加一些模型集合
    this.tasks = new Tasks();
    this.chatMessages = new Messages();

    // 初始化一个 'me' 对象
    window.me = new Me();

    this.fetchStandardData(function (err) {
        if (err) {
            // 处理错误
        }
        // 渲染主视图
        app.view = new MainView({
            model: me
        }).render();

        // 启动我们的路由器。
        // 初始化我们的 URL 处理器和历史记录跟踪器
        new Router();
        app.history = Backbone.history;
        // 我们有了所需的一切，现在可以启动路由器并显示适当的页面
        app.history.start({pushState: true, root: '/'});
    });

  },
  fetchStandardData: function (mainCallback) {
    var self = this;
    async.parallel([
        function (cb) {
            self.tasks.fetch({success: cb});
        },
        function (cb) {
            me.fetch({success: cb});
        }
    ], mainCallback);
  }
}
```

如你所见，无论 URL 是什么，我们都会做几件事。一旦我们搞定了这些，我们就初始化路由器并开始历史跟踪（这启用了后退按钮支持）。

客户端路由器大致如下：

```
var Backbone = require('backbone');
var TaskDetailPage = require('pages/taskDetail');
var FourOhFourPage = require('pages/fourOhFour');

module.exports = Backbone.Router.extend({
    routes: {
      '': 'home',
      ':slug/:slug/task/:taskid': 'memberTaskDetail',
      ...
    },

    // --------- 路由处理器 ----------
    home: function () {
      app.navigate(app.teams.first().chatUrl);
    },

    memberTaskDetail: function (teamId, memberId, taskId) {
      var team = app.teams.get(teamId);
      var member = team && team.members.get(memberId)

      // 确保我们找到了模型，或者发送到内部
      // “未找到”页面。
      if (!team || !member) return this.fourOhFour();

      // 我们可能有也可能没有任务，所以我们只是传递它并尝试从视图中获取。
      app.renderPage(new TaskDetailPage({
        team: team,
        member: member,
        taskId: taskId
      }));
    },

    fourOhFour: function () {
      app.renderPage(new FourOhFourPage());
    }
});
```

因此，顶部列出的每个路由都被 Backbone 转换成正则表达式并链接到一个处理函数。

该函数被调用时带有“参数”，即你在路由中指定为动态的那些参数。

我通常将每个处理器的工作视为查找实际的客户端模型对象，然后创建一个“页面”视图，将其传递给应用程序。

应用负责采用该视图并按照应用的约定进行渲染。通常，我们只是让“页面视图”成为一种特殊类型的 Backbone 视图，该视图还具有一些用于“显示”和“隐藏”的标准方法。应用控制器只需对新页面调用“show”，对当前活动页面调用“hide”，视图会从应用布局的主要“页面”容器中添加/移除自身。

从这以后，我们永远不需要再次执行启动序列。我们只需更改路由，然后路由处理器会渲染适当的页面，页面将确保它拥有（或获取）所需的数据。

## 不糟糕的测试与质量保证（这样你的应用才不会糟糕）

### 正确界面质量保证的问题/挑战

我们都知道我们需要测试。在构建浏览器应用时，我发现构建一个广泛的测试套件不一定值得付出努力。界面本质上难以测试，因为人类输入的变异性是界面良好测试的一部分。

此外，有些事情就是有点难测试。例如，如果你的界面支持拖放操作，编写一个能正确验证其工作正常的测试并不容易。

然后还有 CSS 变化“问题”。DOM 可能完全正常，但如果样式有误，东西看起来可能非常破碎，或者可能出现布局问题，其中控件被遮盖或无法点击。

有些人构建非常复杂的质量保证系统，将他们的应用加载到无头浏览器中，并截取与参考图像等进行比较的截图。但在大多数情况下，所需的大量工作和设置根本不实用。

还有一些工具，如 Selenium，可以为你编写浏览器脚本，但这需要大量的工作和设置，然后每次你想更改某些内容时，如果你的测试太具体，它们就需要不断更新。而如果它们太笼统，它们又会遗漏一些东西。

虽然无头浏览器测试是一个非常酷的想法（PhantomJS 等），但它并不能真正帮助你了解你的应用在其他浏览器中的工作情况。

最终，我认为如果没有人类，你实际上无法进行适当的界面测试。

因此，必须在人类批准和监督与利用计算机擅长的事物（如流程、一致性、自动化）之间找到平衡点。

### 浏览器中需要的单元测试模块

对于那些不是QA而是实际单元测试的测试，你需要一种方法来编写将在浏览器中运行的测试，理想情况下，我们希望能够在命令行中运行它们。

事实证明，我们可以。使用一套主要由[James Halliday](https://github.com/substack)（又名“substack”）开发的工具。

这里是来自ampersand-state的一个示例：

```
var test = require('tape');
var State = require('../ampersand-state');

var Person = State.extend({
    props: {
        name: 'string'
    }
});

test('init with values', function (t) {
    var person = new Person({name: 'henrik'});
    t.ok(person);
    t.equal(person.name, 'henrik');
    t.end();
});

test('after init, change should be empty until a set op', function (t) {
    var person = new Person({name: 'phil'});
    t.deepEqual(person._changed, {});
    t.notOk(person.changedAttributes());
    t.end();
});
```

“tape”模块可以在浏览器或服务器上通过browserify运行。

所以，在一些便捷的开发依赖项的帮助下，我们可以在phantom.js或浏览器中运行我们的测试。

首先，运行以下命令安装我们需要的一些依赖项：

```
npm i --save-dev run-browser browserify tape-run
```

这将安装它们并将它们作为`devDependencies`保存在你的package.json中。

接下来，我们可以在package.json中添加一些脚本，像这样：

```
"scripts": {
  "start": "run-browser test/index.js",
  "test": "browserify test/index.js | tape-run"
},
```

有了这个设置，我们可以运行`npm start`，并在我们想要运行测试的任何浏览器中打开`localhost:3000`。

我们也可以直接运行`npm test`，它将使用phantom.js运行（如果你还没有安装，可能需要单独安装），你应该会在终端中看到相同类型的输出。

这种输出格式是一种名为[TAP](https://testanything.org/)的标准测试输出格式。

因此，有各种工具可以美化该输出。所以，如果你想要更漂亮的终端输出，你也可以从npm安装`tap-spec`，并将你的“test”脚本更新为如下所示：

```
"test": "browserify test/index.js | tape-run | tap-spec"
```

通过使用tape并以这种方式编写测试，我们还可以使用像[testling](https://ci.testling.com/)这样的服务，它可以在不同的浏览器中为我们运行测试。

Testling可以被配置为在我们每次推送到github时，使用我们指定的浏览器列表自动运行我们的测试套件。这种方法在开发用于浏览器的小模块时非常有用。有关如何为你的项目设置此功能的更多信息，请参阅[testling快速入门指南](https://ci.testling.com/guide/tutorial)。

要查看这些工具使用的完整工作示例，请参阅[ampersand-view](https://github.com/AmpersandJS/ampersand-view)或几乎任何[ampersand.js工具](https://github.com/AmpersandJS)。

## 应用设置与配置

### 问题

应用配置和环境设置总是很棘手，对吧？尤其是当你有配置设置要传递给你的单页应用时。如果我们已将所有内容构建为发送“静态”js文件，那么我们如何将动态值传递给它以用于配置等目的？

我们用一个简单的方法和两个特定的工具来解决这个问题：

- getconfig
- clientconfig

它们之间没有任何依赖关系，但它们确实可以很好地协同工作。（顺便说一句，两者都在npm上）。

### getconfig

首先，getconfig。这是一个用于配置Node web应用的工具。它遵循与[Express](https://expressjs.com/)相同的假设，即它查找一个环境变量（NODE_ENV，[参考](https://en.wikipedia.org/wiki/Environment_variable)）来确定其应运行的模式。

它只是使用该变量来查找与环境名称匹配的JSON配置文件。例如：dev_config.json或production_config.json。如果找不到，它默认为dev。

然后，从你的Node应用中，你只需引入“getconfig”并直接在返回的对象上访问设置，它会从正确的配置文件中提取设置。超级简洁/简单：

```
// 我们只需引入模块
var config = require('getconfig');

// 它实际上返回我们环境感知的配置
// 来自相应的配置文件。
config.mySetting;
```

它只是从正确的文件中提取正确的配置，没有“if”语句，没有混乱。

### clientconfig

在客户端，我们做非常类似的事情。

```
var config = require('clientconfig');

config.mySetting;
```

这一次，该模块不是查找环境变量，而是查找一个名为“config”的cookie，其中包含一个JSON编码的配置对象。它立即读取，然后销毁该cookie（以避免在后续任何请求中发送它的开销）。

Clientconfig读取并返回一个“冻结的”配置对象（如果可用，使用ES5 Object.freeze），其中包含我们的设置。因此，它基本上与getconfig具有等效的开发者体验，但适用于客户端。

### 结合使用它们

结合起来，它变得非常简洁：

假设我们在服务器上有这样一个dev_config.json：

```json
{
  "myProjectSetting": "someSetting",
  "clientAppSettings": {
    "apiUrl": "https://api.andbang.com",
    "trackMetrics": false
  }
}
```
*注意“clientAppSettings”部分。*

现在，在我们处理单页应用请求的主服务器文件中，我们然后使用一个非常简单的中间件，将配置cookie与来自getconfig的数据一起添加。

```javascript
// 设置我们的应用并引入getconfig
var app = require('express')(),
    config = require('getconfig');

// 构建一个设置cookie的小型中间件函数
var configMiddleware = function (req, res, next) {
  res.setCookie('config', JSON.stringify(config.clientAppSettings));
  next();
};
```



// 在服务于我们单页应用的代码中，使用该中间件
app.get('/app', configMiddleware, function (req, res) {
    res.send(clientApp.html());
});

就这样，我们在服务器上拥有了一个简单的统一配置文件，可以在其中存储整个应用的所有特定环境设置。基于我们的环境将设置传递给客户端应用程序变得非常简单，无需额外考虑。

这种方法的另一个好处是，它让我们能够将客户端 JavaScript 应用保持为完全静态的文件。我们不必进行自定义构建来写入设置或类似操作，同时还能避免获取设置的额外 HTTP 请求。

### 安全注意事项

如果通过此方式传输任何有价值的设置，请务必避免，尤其是在未使用 HTTPS 的情况下。Cookie 仅仅是 HTTP 头，因此最好假设它们不是安全信息，因此应仅用于非敏感数据。

## 注意事项/常见问题

### 函数绑定

我在教授 JavaScript 时，最常见的问题是理解 JavaScript 中函数执行的工作方式，即使是那些长期使用 jQuery 的人也是如此。

在 JavaScript 中，有 4 种调用函数的方式：

1. 作为独立函数：

```javascript
var myFunction = function () {
  console.log("this" is, this);
};

myFunction(); // 将输出 `window` 对象（或 Node 中的全局对象）
```

2. 作为对象的属性：

```javascript
var obj = {};
obj.myFunction = function () {
  console.log("this" is, this);
};

obj.myFunction(); // 将输出 'obj' 对象

// 现在情况变得棘手了（继续使用上面的代码）

var myFunc = obj.myFunction;

myFunc(); // 这个 'this' 会输出什么？

// 答案是 `window` 对象
```

3. 使用 call

```javascript
var myFunc = function () { ... };

// 使用特定的上下文和任意数量的参数进行调用
myFunc.call({any: 'object'}, 'someArgument', 'someOther');
```

4. 使用 apply

```javascript
var myFunc = function () { ... };

// 应用参数数组
myFunc.apply({any: 'object'}, ['someArgument', 'someOther']);
```

那么问题来了，为什么呢？

在 JavaScript 中，`this` 并不是魔法。它只是一个对象。它是你在调用函数时告诉它的任何东西。它只是该函数执行的上下文对象。

所以在第二个例子中，我们只做 `myFunc();`，我们没有给它任何东西作为上下文，所以它使用全局对象 "window"，因为函数体内总会有一个代表执行上下文的 `this`。

这些问题不是 JavaScript 开发者在使用 jQuery 构建应用时习惯思考的。jQuery 几乎总是将当前元素作为事件处理程序等的 'this' 交给你。但是...一旦我们开始使用 Backbone，很多人就会遇到麻烦。以下是我看到的几乎每个 Backbone 新手都会犯的一个例子：

```javascript
var Backbone = require('backbone'),
    templates = require('templates');

module.exports = Backbone.View.extend({
    initialize: function () {
        // 注册一个处理程序，以便每当模型发生变化时，
        // 调用 render 函数。
        // 这将无法工作！
        this.model.on('change', this.render);
    },
    render: function () {
        this.$el.html(template.thing());
    }
});
```

问题在于，如果 render 函数是由模型变化触发的，那么函数内部的 "this" 将不是 Backbone 视图。你可能会说，"嗯，我们把它指定为某个东西的属性。" 在某些方面，是的，你写了 `this.render`，但你实际上只是引用了结果函数，并将特定函数（没有上下文）提供给事件注册表。

事实上，你所做的与此并无二致：

```javascript
// 注册一个处理程序，以便每当模型发生变化时，
// 调用 render 函数。
// 这将无法工作！
var render = this.render;
this.model.on('change', render);
```

所以，当你只提供指向该函数的指针时，render 函数没有任何上下文（即使该函数可能“存在于”视图上）。

那么，你应该这样做。你可以在函数运行之前将其绑定到一个上下文，如下所示。

```javascript
// 这将按预期工作。
// Backbone 的事件系统接受第三个参数作为
// 执行函数的上下文。
this.model.on('change', this.render, this);
```

这引出了执行函数的另外两种方式：

```javascript
var myFunction = function () {
    console.log("\"this\" is", this);
};

var someOtherContext = {
    name: 'blah'
};

// 这两种方式都会输出 'someOtherContext' 对象
myFunction.apply(someOtherContext);
myFunction.call(someOtherContext);

// 在符合 ES5（即现代）的浏览器中，你也可以这样做
myFunction = myFunction.bind(someOtherContext);
myFunction(); // "this" 将是 someOtherContext

// 或者如果你使用 underscore，无论你是否在现代浏览器中。
// 你可以直接这样做：

myFunction = _.bind(myFunction, someOtherContext);
myFunction(); // 结果相同
```

这就是函数绑定的全部内容。它真的只是关于语言如何工作的信息。但这是 Backbone 新手或对 JavaScript 语言不熟悉的人非常常见的问题，因此我认为值得解释一下。

### 关于视图中 DOM 操作的注意事项（它们可能仍然处于分离状态）

另一个常见问题是理解 `this.$()` 在视图中的作用。

如果你的模板中有一个像这样的 div：`<div id="myDiv"/>`，而我们在 render 函数中这样做，你会遇到问题：

```javascript
var Backbone = require('backbone');

module.exports = Backbone.View.extend({
    render: function () {
        this.$el.html(templates.myTemplate());
    }
});

// 然后你尝试这样访问那个 div：
$('#myDiv').on('click', this.doSomething);

// ^^ 如果该视图的根元素尚未附加到 DOM，则 myDiv 将不会被找到！
return this;
}
});
```

许多人不知道的是，你可以向 jQuery 函数 $(selector) 传递第二个参数，该参数是要在其中查找的 DOM 树。因此，如果你在上面的例子中使用 $('#myDiv', this.el)，它总是有效的。

Backbone 试图为我们简化事情，而不是那样做。请记住，在视图内始终使用 this.$() 而不是仅使用 $()。这只是一个辅助函数，用于将视图的根元素传递给 jQuery 函数。在功能上等同于将 this.el 作为第二个参数传递。

### Ajax 请求失败

对于单页应用，不可避免地会遇到连接不良或数据过期和/或会话过期的问题。

如果我们使用 RESTful JSON API，我们将在应用程序的整个生命周期中发出请求。一种方法是为所有 Ajax 请求存根一个全局错误处理程序。jQuery 使这变得相当简单：http://api.jquery.com/ajaxError。通常，作为应用程序主视图的一部分，我会注册一个全局 Ajax 错误的处理程序，弹出一个对话框显示适当的消息。
