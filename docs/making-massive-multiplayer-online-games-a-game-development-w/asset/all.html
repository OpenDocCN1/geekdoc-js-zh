  • by Christer Kaitila: The McFunky-pants Method — “Challenge yourself to create a code-base that compiles and runs in the first few hours. Make it so that you can accept inputs, move around, animate something, and trigger some sounds. This prototype, lousy a game as it may be, is going to be your best friend. The sooner you can have a working early playable prototype, the more likely you are to succeed. No-art prototypes also have one other major advantage: in previous games, I would make beautiful mock-ups in PhotoShop and gather hundreds of lovely looking sprites in preparation for the game. After development was complete, the vast majority of the art had to be replaced, re-sized, or thrown out. “Why do I need a web server? Can’t I just open the html files with my browser?”

Answer: All JavaScript games, which load any assets or files, require launching themselves from a web server — either locally inside your workstation or remotely from the Internet. It’s all about browser security and the same-origin policies — prohibiting files loading from different “domains” and the protocols used to access your locally stored files. When you request anything from the Internet you’re typically using the “hyper-text transfer protocol” (http:// or https://). From a web server, security policies ensure you only access files that you are authorized to use. When you open any HTML file from your local operating system, your browser uses the file:// protocol. (technically a different protocol than http://), massive restrictions are triggered inside your browser, for the following obvious reasons. Under the file:// protocol, no concept of domains nor “server-level security policies” exists, just your computer’s “raw file system” and its operating system — identified as the localhost — using a local IP address(es) (0.0.0.0 or IPv6 ::1, or IPv4 127.0.0.0/8 to 127.255.255.255/8) per RFC 990, November 1986. This means that your HTML pages are not running on any domain nor public Internet IP address at all, and thus JavaScript is unable to load any game assets dynamically. Do you really want JavaScript to have that much control — to load anything from anywhere — off your computer? Well, I’m guessing your answer should be “… not ever!”. If JavaScript had unrestricted access using the file:// protocol, nothing could stop it from tapping into your information and sending it anywhere to anyone.

3.4 Network Concerns

This illustration above demonstrates the actual communications (i.e., “physical”) path used by two remote gamers. If we are building a “real-time” MMoG, this communications path would present several problems:

  • Lag and delayed (aka “latency”) responses. (Nothing is instantaneous!) This is the greatest problem outside of our control. Read more about network latency and how to compensate for its effects.
  • Lost data packets either going to or coming from each player. (TCP/IP corrupted packets are re-transmitted until they arrive “perfectly”.
  • network congestion — resulting in re-routing traffic toward longer communications paths.
  • discarded data packets due to WAN networked congestion.
  • jitter — delay which varies over time due to other background traffic from other users sharing the same communications path with higher differentiated services.

Network bandwidth is a limited resource based on contractual agreements; this will become a primary concern in later chapters. So, the server shouldn’t send new updated information packets to every game participant for each minuscule change in the game-board (aka gaming world). Instead, the central game server takes “snapshots of the current game state” at distinct intervals (far less than 60fps!), and then, “broadcasts” those samples to synchronized the game for every gamer. This is the same technique cable companies have when broadcasting movies to neighborhood subscribers. These network data packets take time to travel between the gamer and the server (i.e. half the ping time; see Network Tools Appendix). This means that the client-gamer’s time is always a little bit behind (aka lagging) the server’s time. Furthermore, clients’ incoming message packets are further delayed on their return path, so the game server is always processing gamers’ commands in a temporally delayed status. In addition, each client workstation has a unique amount of network delay coming toward the central server, because each game participant arrives at the server through different data connection at different data rates across the WAN. This delay dynamically varies over time due to other aggregated traffic on that path and the Internet Service Providers (ISP) access sampling frame-rates. These time differences — between server and each client through their ISP — causes logical processing problems, which become worse as network latencies increase inside the WAN. In a fast-paced action game (typically found in “first person shooters”), even the slightest network delay of a few milliseconds could cause “a laggy” (aka jerky, jitter) game-play feeling. This makes it difficult to target other players or interact with rapidly moving obstacles at 60 frames per second (fps or ~16.67 milliseconds per animation frame. Remember this for Chapter 5.) Beyond these bandwidth limitations, fragmentation, corruption and network latencies, game information also gets lost due to network congestion and rerouting.

Many game developers attempt to compensate for these fussy network problems by using statistical prediction — interpolation or/and extrapolation. What they do not include in their “prediction” is the Layer-4 Communications Management which is already in the network protocols.

In contrast to UDP, TCP over IP (TCP/IP) is connection-oriented in similar ways to a Phone call. A user dials a number (e.g., an IP (Internet Protocol) address), and waits for the destination to answer before starting their conversation. TCP/IP adds other convenient services to this communications path. Foremost is data recovery; if something get lost, corrupted, out of sequence, TCP/IP steps in and asks for a re-transmission and insert the pristine data into the correct place.

An often forgotten service that TCP/IP provides is the connection management. Each TCP/IP transmission must be acknowledged, or ACKed, by the destination device.

The source system will wait only a limited amount of time for those acknowledgments. That time interval is called the re-transmission time. If this timer expires before the sender receives an acknowledgment from the destination, TCP assumes that the IP packet was lost and asks for a re-transmission of that allegedly lost packet. Each packet contains a sequence numbers, as well as each acknowledgment. In this way, the sender knows which packet had been lost from the sequence stream.

You guessed it! The communication efficiency is highly sensitive to the time that TCP waits until it begins requesting a re-transmission. TCP calls this time interval the re-transmission timeout (‘RTO’). You could set RTO to a static value or it is often adaptive. Nearly all TCP/IP connection use an adaptive RTO. The point to learn is that any interpolation or extrapolation generated to compensate for network lag or latency will result in an exaggerated response.

Briefly let’s see how a static RTO would affect communications efficiently in a local area network (LAN). Both source and destination systems in a LAN are usually quite close, the bandwidth is quite high, and the time it would take for a packet to travel between them is very short. Clearly, when a packet is lost in a LAN, efficiency is accomplished with a very small RTO. However for a MMoG with players strewn around the world, and across the ocean, using a standard telephone line, those gamers and gaming server are not close at all, the bandwidth is quite small, and the time it would take for a packet to travel between them is significant. In this case, a small RTO becomes a barrier to communication efficiency. If RTO were too small, the source device might believe the packet was lost; when, in fact, the game server received that game turn packet and the acknowledged it; however, the ACK had not the time to travel back at the source.

It is not possible to set the value of RTO for each application. It would be much easier if TCP/IP could anticipate the response time and set a value for RTO in an adaptive manner. TCP performs this task by estimating the round-trip delay on each socket pair established. Since the network that lies between the two end systems is not static, the time for a packet to travel between any two systems is not static either. For that reason, the round-trip delay is constantly measured and adjusted to adapt to the changing conditions of the network. TCP starts a time counter when a packet is sent and stops it when the acknowledgment is eventually received — this feature is already embedded in the protocol. There no reason to waste CPU processing for these calculations in your gaming engine — something I’ve seen in several recent tutorials, books and articles. TCP/IP then writes that value into a variable called the round-trip time (RTT). As more packets are sent and received, the RTT value is continually updated (for your MMoG application) to adapt to the changing conditions of the Internet that lies between the two communicating end systems.

This connection management has a price at the receiving device. The destination holds all incoming data packets and verifies its completeness and re-orders them into the correct sequence. If the destination discovers data packet corruption or just simply missing packets, everything freezes in place (aka head of line blocking) while a re-transmission request is sent and the new bright shiny packets arrive. Nope! you can’t fix it; it’s how TCP/IP operates. So, Google developed an idea how to fix this — it’s called Quick UDP Internet Connection (QUIC). Their goal was to combine the best features of UDP and TCP and season it with a little security salt.

Layer 4 software ports are locations in computer memory that are dedicated for input and output (aka I/O buffers). The term “port” has many meanings aside from this one listed. For example, a “physical outlet in a network device” is often called a (hardware) “port”. Usually one can discern the difference from a hardware port or a software port from the context. When one of these 65,536 ports is tied (aka binding) to a layer 3 Networking IP address, they are collectively called a “socket” — “TCP/IP socket”.

New Kid on the Block

Transmission Control Protocol (TCP) and User Datagram Protocol (UDP) have been long-standing protocols used in data communications and video conferencing. But this wasn’t good enough; something changed all that — “WebSocket”! In 2011, a new standardized WebSockets protocol was introduced and finally stabilized by 2014. Unlike the former half-duplex HTTP/AJAX, WebSockets provide FULL DUPLEX communications over a single TCP connection. HTML5 Web Sockets is not just another incremental enhancement to the conventional HTTP communications protocol; it represents a exponential advance, especially concerning real-time, event-driven web applications. The old “convoluted” method fades in the light of Web Sockets’ full-duplex connection, and prompted Ian Hickson — Google’s HTML5 specification lead — to say, “Reducing kilobytes of data to 2 bytes … and reducing latency from 150ms to 50ms is far more than marginal. In fact, these two factors alone are enough to make Web-Sockets seriously interesting to Google.”

To summarize the key differences between an WebSocket server and a regular Web server is that as soon as you receive information from a Web server, the connection is broken. It may look as if you’re still connected to the Web server, especially with a “single web page application (SWPA)” that’s animating everything. However, that’s not the way it works. When you open a Web page, the Web server sends you that page along with all its associated graphics, text, and other media; and your browser sends an acknowledgment message back saying, “Got it!”, and then that connection request closes the network connection. In contrast, a WebSocket server’s connection stays active and “open” until you quit the application or trigger an event that cuts the connection (i.e., “hang up”). Because a WebSocket connection remains open, you can stream audio, video, text, and any other media available from the Internet — in real time bi-directionally! This is just not possible with a traditional Web server because it has an entirely different architecture.

Since a WebSocket is a bi-directional connection, there’s no technical distinction between a “server” and a “client”; they’re now point-to-point peers. “Senders” and “Receivers” are about the game content and messages. The server needs to adopt a new role: a “peer” which connects multiple “end-user clients”. The server transforms into something similar to a network “router”. So, instead of the game logic sitting totally on a server, the game logic can now sit on the end-user browser as a “proxy-server” which allows other remote end-users to access its local game functions. This concept is the begins of a “Distributed Application” (DApp) — clients calling game logic functions on other client participants directly while the server disappearing into a “cloud service”.

RFC6455 states:
A simpler solution would be to use a single TCP connection for traffic in both directions. This is what the WebSocket Protocol provides. Combined with the WebSocket API (WSAPI), it provides an alternative to HTTP polling for two-way communication from a web page to a remote server. …
The WebSocket Protocol is designed to supersede existing bidirectional communication technologies that use HTTP as a transport layer to benefit from existing infrastructure (proxies, filtering, authentication). Such technologies were implemented as trade-offs between efficiency and reliability because HTTP was not initially meant to be used for bidirectional communication (see RFC6202 for further discussion).
The WebSocket Protocol is designed on the principle that there should be minimal framing (the only framing that exists is to make the protocol frame-based instead of stream-based and to support a distinction between Unicode text and binary frames). It is expected that meta-data would be layered on top of WebSocket by the application layer, in the same way that meta-data is layered on top of TCP by the application layer (e.g., HTTP).

Conceptually, WebSocket is really just a layer on top of TCP that does the following:

  • adds a web origin-based security model for browsers
  • adds an addressing and protocol naming mechanism to support multiple services on one port and multiple host names on one IP address
  • layers a framing mechanism on top of TCP to get back to the IP packet mechanism that TCP is built on, but without length limits
  • includes an additional closing handshake in-band that is designed to work in the presence of proxies and other intermediaries

Other than that, WebSocket adds nothing. Basically it is intended to be as close to just exposing raw TCP to script as possible given the constraints of the Web.

Deeper Dive: WebSocket Frame

The base framing protocol defines bits 4 to 7 as the 4 bit Opcode, which defines the content type for the payload data. Here’s the Web Socket frame building blocks:

  • fin (1 bit): indicates if this frame is the final frame that makes up the message. Most of the time the message fits into a single frame and this bit will always be set. Experiments show that Firefox makes a second frame after 32K.
  • rsv1, rsv2, rsv3 (1 bit each): must be 0 unless an extension is negotiated that defines meanings for non-zero values. If a nonzero value is received and none of the negotiated extensions defines the meaning of such a nonzero value, the receiving endpoint must fail the connection.

  • opcode (4 bits): says what the frame represents. The first frame that transmits the data has an opcode on it that indicates what sort of data is being transmitted. This is necessary because JavaScript has pretty much nonexistent support for binary data at the time the specification was started. Most people will transmit JSON in which case you’d probably want to choose the text opcode. The following values are currently in use:

    - 0x00: this frame continues the payload from the previous.
    - 0x01: this frame includes utf-8 encoded text data.
    - 0x02: this frame includes binary data.
    - 0x08: this frame terminates the connection.
    - 0x09: this frame is a ping.
    - 0x0a: this frame is a pong. (As you can see, there are enough values unused; they’ve been reserved for future use).

  • mask (1 bit): indicates if the connection is masked. As it stands right now, every message from a client to a server must be masked and the spec would want to terminate the connection if it’s unmasked.
  • payload_len (7 bits): the length of the payload. WebSocket frames come in the following length brackets: 0–125 indicates the length of the payload. 126 means that the following two bytes indicate the length, 127 means the next 8 bytes indicate the length. So the length of the payload comes in ~7bit, 16bit, and 64bit brackets.
  • masking-key (32 bits): all frames sent from the client to the server are masked by a 32-bit value that is contained within the frame.
  • payload: the actual data which most likely is masked. Its length is the length of the payload_len.

Web MVC - Web Application Programming

In a web application, the server software runs on a server, and the user interacts with browser software running on a client. The Model’s data is stored on the server. The user interacts with software running on the client.

Client-server programming is difficult because the program is distributed across more than one network node. Some code has to run on the client to interact with the user. Other code has to run on the server to interact with the data store.

In the case of a web application, the code that runs on the client includes the user agent, or browser. The distributed nature of a web application creates two challenges. One is that the application has to render data from the server into a context where it can be displayed on the client. The other is that information about user events has to get back from the client to the server.

The architectural decision about client-server MVC is which components to deploy to which nodes, and how to manage the communication between them. Should the View and the Controller run on the server, or the client? What about the Model?

There’s a variety of ways to make these decisions. One solution is Server-Side MVC (below). Another is the Rich Internet Application architecture (also below). But all the solutions have some elements in comment, because of the following ground rules:

  • At least part of the Model has to run on the server. This is because the Model is responsible for maintaining the integrity of the business objects, and has to be immune from client spoofing. It also synchronizes changes requested by simultaneously executing clients if the changes are bottle-necked through code that runs on the server, although in a clustered server environment this doesn’t come for free.
  • The user has to be able to see the information presented by the View. This means the View, no matter where it runs, ultimately must control the display of this information on the client.
  • The Controller must be able to receive events that represent user activity.

The critical differences between a single-player game and its “big MMoG brother” is its distribution of common game information (i.e., inputs processing, variable state management, and the rendering outputs of game assets) and game “processes” (i.e., updates to our game’s status) among all players — who does what when with synchronization confirmation? We’ll study these various deployment options soon. Network delay (aka lag or latency) becomes our greatest concern when centralizing all game “processing logic” — that central portion from the “Update” phase — onto a remote server assuming you’re building a real-time MMoG. By doing so, we’ve just added the network delay into our typical 60 fps game loop. The tolerance for this newly introduced network interference depends greatly on the game mechanics we are using. For example, a turn-based game (a fix time interval with game turn order (GTO) submissions) have a better tolerance toward network latency, delay, jitter or lag than a “twitch-style” game play found in most “first-person shooters (FPS)”. In order for either to work, both approaches require a “middleman” — a “proxy” of our centralized authoritative server as suggested by Unreal Networking Architecture — to handle all network traffic among all participants. WebSockets is a wise choice for games that require a “reliable ordered” communication channel (i.e., TCP/IP), but real-time games require a lower latency solution — perhaps UDP/IP, or WebRTC UDP-based conduits. And most real-time games care more about receiving the most recent data than getting ALL of the game’s data in the proper sequence.

Writing Source Code Differently: “How vs What!”

Perhaps many of the problems found in MMoG is the manner in which we write our source code. Philip Roberts may have a suggestion for us in his article.

Imperative vs Declarative

Let’s generalize and say that there are two ways in which we can write code: imperative and declarative. We could define the difference as follows:

  • Imperative programming: telling the “machine” how to do something, and as a result what you want to happen will happen. (ed.: this is typical done in Phaser.js.)
  • Declarative programming: telling the “machine” what you would like to happen, and let the computer figure out how to do it.

So, why is this interesting?

Look through the code again and think about whether we are describing what we want our visualization to look like, or how to draw it? You’ll see that there is almost no how code at all. We are just describing at quite a high level what we want.

. . . Declarative programming allows us to describe what we want, and let the underlying software/computer/etc. deal with how to do it.

That’s the secret sauce we’re looking for! Locally, Phaser Canvas will do the drawing (imperative; how) and rendering as dictated from the MMoG App server (declarative; what). Sending game turn orders (GTOs) will be written in a declarative / what format, as JSON or XML, going toward the MMoG App server. The MMoG App Server will perform the imperative / how to apply the game logic from the submitted game turn order’s data. In summary, all transmissions take the “declarative format” (what) on either side of the WebSocket conduit. All incoming declarative information will convert that “data information” into “imperative actions” (how). The client will render the current visual display, the server will apply new game information into its game logic and data structures.

Construction Sequence and Regimen

I recommend you think of your game turn orders (GTO) and game turn results (GTR) as “end-points” in the communications — your protocols and API specifications. This hints at a sequence for writing our MMoG source code.

  1. Draft a list of client-side game turn orders (GTO), and the expected game turn results (GTR) of the server-side responses.
  2. Then determine how you will “serialize” that output for those GTOs and GTRs. In what formatted data structure will that information use? You have several choices. (i.e., XML, JSON, Binary, etc.) Start with server-side first so that you have something to talk to from the client-side.
  3. Finally, encode your “serializers”; these will become your “contracts” between the client and server as to what is expected from each side of the conduit. Yea, that sound like the most difficult part in the process; but, I have a surprise for you later in this chapter.

5.4 Encoding Formats for Game Turns

Summary: Any “horizontal traffic” — between the client and its server — will be “What” and “declarative data packets”. All vertical processes will be “How” and “imperative code”. This naturally leads us to the decision on how our horizontal data should be formatted. What form should our “messages” take? Data sent between the client and the server are not exchanged verbatim. Actually, those websocket data are formatted into frames — a package of bits (aka a “packet” or “Datagram”) with a specific arrangement and design. We must concoct that ordered arrangement to make any sense about what’s happening. The technical term for “type of the message” is “operation code or opcode”, and in our case, we will label messages “client to server (C2S)” and “server to client (S2C)”.

We do not have to re-invent the “wheel” in our packet formats. We can choose among several technology architectures that are available already in the “message-oriented middleware (MOM) categories. But which “web service” should we use? Web services fall into three camps; one which exposes it APIs as Remote Procedure Calls (RPC), Query Langugages (such as JSON:API or OData), and the other as “web consumer services” (aka Object Request Brokers) which supplies “document resources” (aka REST) and API interfaces.

QUOTE: Message Oriented Middleware (MOM) Asynchronicity

Using a MOM system, a client makes an API call to send a message to a destination managed by the provider. (See Inter-process Communication: Methods) The call invokes provider services to route and deliver the message. Once it has sent the message, the client can continue to do other work, confident that the provider retains the message until a receiving client retrieves it. The message-based model, coupled with the mediation of the provider, makes it possible to create a system of loosely coupled components.

MOM comprises a category of inter-application communication software (ed.: source code examples here) that generally relies on asynchronous message-passing, as opposed to a request-response architecture. In asynchronous systems, message queues provide temporary storage when the destination program is busy or not connected. In addition, most asynchronous MOM systems provide persistent storage to back up the message queue. This means that the sender and receiver do not need to connect to the network at the same time (asynchronous delivery), and problems with intermittent connectivity are solved. It also means that should the receiver application fail for any reason, the senders can continue unaffected, as the messages they send will simply accumulate in the message queue for later processing when the receiver restarts.

5.8 Managing Network Transports

Let’s review how other MMoGs approach the problems of network delay, lag, and jitter and see their solutions.

Skipping Rope! (Fixed Time Intervals)

Skipping Rope is a favorite activities for children, and it teaches us some lessons about developing a Multi-Player game. Each participant must jump at the precise time — technically called “lockstep synchronization”. Applying that idea to our game, each player must have exactly synchronized input and rendering of the game world for the participants to see same game reality. The central authoritative server(s) makes all the decisions and tells each clients “what to render” (i.e., declarative). The gamer’s browser contribute nothing to the game logic other than “how to render” (i.e., imperative) the current game world; their only contribution is collecting the gamers’ input and sending that information to the server. This is the simplest approach — and most naive solution — in MMoG development. Returning to our example, if one child falters and trips, their action affects everyone playing.

The lessons learned are:

  1. All the gaming participants can play only at the speed of the slowest gamer.
  2. No independent processing is allowed at any gamer’s browser other than rendering sprites. This is in stark contrast to the information you read in a previous exercise about how the UnReal Engine operates.
  3. Synchronization must be the same across all participants or else someone’s timing mistake will impact everyone.
  4. This approach does not favor “twitch-action” MMo-Game Mechanics.
  5. TCP/IP latency has the greatest impact on our WebSockets and game processing.

The problems using this approach are:

  1. Lack of persistence. All of the gamers must start a game together at the same time. New gamers coming or leaving causes problems for everyone remaining inside the game session.
  2. Lack of player scalability. The server coordination and chances of a network-induced error increases linearly with the number of participants due to this lock-step synchronization.
  3. Lack of frame rate scalability. All players must process the game at the same internal frame rate, making it difficult to support a wide variety of hardware speeds. Generating packets to send and processing the received packets can only be done as often as the client is able to update its local state. Although packets could theoretically be generated and sent faster than this, it would only result in sending redundant data if the game state cannot be updated between each packet. A low frame rate would therefore make the game less responsive to updates and may force it to skip outdated data.
  4. A gamer could send the location of where their character is or who their character shot in a FPS. This solution may work and might eliminate all but the most stubborn problems related to lag. Unfortunately, it relies on the naive assumption that the player is honest and has not tampered with the game turn.
  5. Greatly impacted by network delay and lag which are outside the game logic’s control. Fortunately, using tools such as latsub.js provides the Round-trip time for us to offset our server timing and adjust game turn submissions.

The lesson we should learn from RTMP / RTMFP is the size of their data packets transmitted, their “Action Message Format” (AMF) structure and their use of TCP / IP to manage packet interleaving and multiplexing.

“To deliver streams smoothly (ed., avoiding network jitter) and transmit as much information as possible, it (ed., RTMP) splits streams into fragments, and their size is negotiated dynamically between the client and server. (ed., this is a standard characteristic of TCP specifications. Nothing unique to their methods thus far.) Sometimes, it is kept unchanged; the default fragment sizes are 64 bytes for audio data, and 128 bytes for video data and most other data types. Fragments from different streams may then be interleaved, and multiplexed over a single connection. (ed. standard role of TCP/IP) With longer data chunks, the protocol thus carries only a one-byte header per fragment, so incurring very little overhead. However, in practice, individual fragments are not typically interleaved. Instead, the interleaving and multiplexing is done at the packet level, (ed., again nothing new here; this is standard IP Layer 3 networking!) with RTMP packets across several different active channels being interleaved in such a way as to ensure that each channel meets its bandwidth, latency, and other quality-of-service requirements. (ed., in other words, they are setting TCP/IP QOS and Differentiated services as defined in RFC 2474) Packets interleaved in this fashion are treated as indivisible, and are not interleaved on the fragment level.” quoted from Wikipedia

Our take away from Adobe RTMP is their dependency on networking Layers 3 & 4, their assembly of smaller Datagram size, their Action Message Format (AMF) and setting Maximum Transmission Unit (MTU). The Internet standard for MTU is 576. The maximum value of the packet_size is 65,464 bytes for IPv4 and 1,280 bytes for IPv6. When you connect to an Internet resource, your data goes through a router that has an MTU of 576. This results in fragmentation if your MTU is greater than 576, which can result in a Web resource being loaded slowly. Quoted from Wikipedia, “For example, according to IPv6’s specification, if a particular link layer cannot deliver an IP Datagram of 1280 bytes in a single frame, then the link layer must provide its own fragmentation and reassembly mechanism, separate from the IP fragmentation mechanism, to ensure that a 1280-byte IP Datagram can be delivered, intact, to the IP layer.”

Both server- and client-side WebSocket objects support the following API.

  • on(‘open’, function(event)) fires when the socket connection is established. Event has no attributes. Ensure your data is sent only when a connection exists; we should wrap our send() method with onopen event.
  • on(‘message’, function(event)) fires when the socket receives a message. Event has one attribute, data, which is either a String (for text frames) or a Buffer (for binary frames). The default data format is “blob” which is particularly useful when sending and receiving files.
  • on(‘error’, function(event)) fires when there is a protocol error due to bad data sent by the other peer. This event is purely informational, you do not need to implement error recover because WebSockets ride on top of TCP/IP. “So how do errors still creep in?” Superior question; the answer is found in RFC 6455 Section 5.1 Overview which you’ve already read (?) from the Networking Chapter exercises.
  • on(‘close’, function(event)) fires when either the client or the server closes the connection conduit. This event has two optional attributes — code and reason — that expose the status code and message sent by the peer that closed the connection. It also has three properties you can use for error handling and recovery: wasClean, code, and error.
  • send(message) accepts either a String or a Buffer and sends a text or binary messages over the connection conduit to the other remote peer.
  • ping(message, function()) sends a “ping” frame with an optional message and fires the callback when a matching answer (aka “pong”) is received. This is typically used to dynamically adjust the MMoG for network latency issues.
  • close(code, reason) closes the connection conduit, sending the given status code and reason text, both of which are optional.
  • version is a string containing the version of the WebSocket protocol the connection is using.
  • protocol is a string (which may be empty) identifying the sub-protocol the socket is using. We discuss various “sub-protocols” in the upcoming Server chapters.

Gamer’s client requests above are similar to HTTP requests, each line ends with \r\n and there must be an extra blank-line at the end. This is the standard format. The handshake resembles an HTTP request so that the game server can handle standard HTTP connections (port 80) as well as the new WebSocket connections across the same initial port 80 (or 443 for https). Once the new WebSocket request creates that connection, communications between the client and game server switches into a bidirectional binary protocol that does not conform to the former HTTP protocol. After a WebSocket connects, the gaming client and server can send WebSocket binary data or text frames in full-duplex mode — in either direction at the same time! This is a point-to-point connection as if client and server were peers. The data is minimally framed (for us by the WebSocket Protocol) with just two bytes. (Review Chapter 3 Network Basics) There’s no need to write code to package these frames as some tutorials lead us to believe. However, it is a “stream” of data; if your MMoG needs to understand discreet components, you might like to use a message format inside these WebSocket frames.

The WebSocket API allows for multiple types of data (UTF8 text, binary, and blob data), and unlike the browser, these messages on the server are stored using different properties based upon those data types. In the case of text frames, each frame starts with a 0x00 byte, ends with a 0xFF byte, and contains UTF-8 data in between. (Review Chapter 3 Network Basics page 62) This binary data stream is difficult for humans to read since it is bidirectional binary protocol. WebSocket text frames use a terminator, while binary frames use a length prefix.

In addition to Upgrade headers, the client sends a Sec-WebSocket-Key header containing base64-encoded random bytes, and the server replies with a hash of the key in the Sec-WebSocket-Accept header. This is intended to prevent a caching proxy from re-sending any previous WebSocket dialog, (see footnote 1) and does not provide any authentication, privacy or integrity. The hashing function appends the fixed string 258EAFA5-E914-47DA-95CA-C5AB0DC85B11 (a GUID) to the value from Sec-WebSocket-Key header (which is not decoded from base64), applies the SHA-1 hashing function, and encodes the result using base64. (see footnote 2)

Observe these WebSocket frames with Wire-shark. (Refer to the Network Appendix on where to get Wire-shark.) Registered IANA Sec-WebSocket-Protocol are referenced here. The server can’t send more than one Sec-Websocket-Protocol header. If the server doesn’t want to use any sub-protocol, it shouldn’t send any Sec-WebSocket-Protocol header. Sending a blank header is incorrect. The client may close the connection if it doesn’t get the sub-protocol it wants.

Thin Server

“An SWPA moves logic from the server to the client. This results in the role of the web server evolving into a pure data API or web service. This architectural shift has, in some circles, been coined “Thin Server Architecture” (SWPA or PWA) to highlight that complexity has been moved from the server to the client, with the argument that this ultimately reduces overall complexity of the system.”

Thick Server

The server keeps the necessary state in memory of the client state of the page. In this way, when any request hits the server (usually user actions), the server sends the appropriate HTML and/or JavaScript with the concrete changes to bring the client to the new desired state (usually adding/deleting/updating a part of the client DOM). At the same time, the state in server is updated. Most of the logic is executed on the server, and HTML is usually also rendered on the server. In some ways, the server simulates a web browser, receiving events and performing delta changes in server state which are automatically propagated to client.

This approach needs more server memory and server processing, but the advantage is a simplified development model because a) the application is usually fully coded in the server, and b) data and UI state in the server are shared in the same memory space with no need for custom client/server communication bridges.

Thick Stateless Server

This is a variant of the stateful server approach. The client page sends data representing its current state to the server, usually through Ajax requests. Using this data, the server is able to reconstruct the client state of the part of the page which needs to be modified and can generate the necessary data or code (for instance, as JSON or JavaScript), which is returned to the client to bring it to a new state, usually modifying the page DOM tree according to the client action which motivated the request.

This approach requires that more data be sent to the server and may require more computational resources per request to partially or fully reconstruct the client page state in the server. At the same time, this approach is more easily scalable because there is no per-client page data kept in the server and, therefore, Ajax requests can be dispatched to different server nodes with no need for session data sharing or server affinity.

Server Requirement Considerations

There are a few requirements we should consider no matter which middleware language we implement.

  1. Our middleware must be able to listen for incoming traffic on an available port(s). Typically, it will be the standard HTML ports 80 and/or 443 from its own chassis. Listening (aka binding) to these standard web ports because it gets around proxy and firewall concerns that we’re likely to encounter in a live production deployment — that’s how the big boys do it!
  2. You cannot run a WebSocket server and a WWW server on the same ports from the same IP address at the same time. You can either run it on a separate IP (aka server) on the standard ports of 80 or 443 or run it on the same box at a different unused port above 1023. What I’m saying is you might not be allowed to operate your WebSocket server on shared hosting accounts. I’m fortunate that my ISP allows WebSocket servers.
  3. If you elect to place your WebSocket server on a non-standard port, double check that your firewall will not block that traffic.
  4. You must have a way to run your middleware perpetually.

Deeper Dive: The CMS Game Shell

A game shell is merely a simple method toward building a Progressive Web App (PWA) that reliably and instantly loads game content, similar to what you would see in native mobile applications.

The game shell is the minimal required technologies of HTML, CSS and JS to display the game’s interface. When it is cached offline, it ensures instant, reliably good performance to gamers in their returning gaming sessions. The network provides the newest or updated gaming content and assets.

For games — “a single web-page application with heavy JavaScript architectures” — using a game shell is “THE go-to approach”. The game shell approach relies on aggressively caching the shell content using a service worker to get the game up and running. Next, the dynamic game content and assets loads for each game phase (aka roses). The secret sauce a game shell provides is: Getting the initial HTML to the user’s device and displayed without the anything from the network!

In other words, the game shell is similar to the code you’d publish to any “app store” when building a native mobile app. The game shell is a skeleton (aka Bare Bones Prototypes) of your game’s user interface (UI) and all those prototype components necessary to launch your game from the ground up … but doesn’t include the game “data logic.”

Note: Try the First Progressive Web App (PWA) to learn how to architect and implement your first generic mobile application shell. The “Instant Loading with the App Shell model” video also walks you through this design pattern.

Deeper Dive: When to use the game shell model

Building a PWA does not mean starting from scratch. If you are building a modern single-page app, then you are probably using something similar to a game shell already whether you call it that or not. The details might vary a bit depending upon which gaming libraries or frameworks you are using, but the concept itself is framework agnostic!

The game shell architecture makes the most sense for any game project with relatively unchanging navigation but changing internal content — the canvas! A number of modern JavaScript Gaming Frameworks and libraries already encourage splitting your game logic from its content (aka “Separation of Concerns”), making this game shell design appealing. For certain types of games —that only have static content— you can still follow the same idea but the game’s canvas tag becomes 100% of the game shell — this is the majority of published Phaser v2.x.x games and single-page games described earlier; they use a single static canvas tag and “within it are the various game “roses” (aka menus, parts, phases, sections, stages, states, scenes, screens, thingies, dumaflache, or “Ardvarks!”).” — Quoted from Phaser III Game Prototyping page 78.

The benefits of using this game shell architecture and a service worker are:

  • Reliable performance that is consistently fast across all your game projects. Repeat visits are extremely quick. Static assets and the UI (e.g. HTML, JavaScript, images and CSS) are cached on the first visit so that they load instantly on repeat visits. Content may be cached on the first visit, but is typically loaded as needed — “just in time!”
  • Native-like interactions. By adopting a game shell model, you can create experiences with instant, native-application-like navigation and interactions, complete with offline support.
  • Economical use of game assets. Design for minimal resource usage. Be judicious in what you immediately cache because loading non-essential files (i.e., large images that aren’t shown on every page) will result in browsers downloading more game assets than is used immediately. Even though WAN bandwidth is available in western countries, this may not be the case in emerging game markets where connectivity is expensive and data is costly.

Both the server and client will have “message packaging” and “unpacking” functions.

Creating MMoG API Prototypes — 4-Step method

I recommend you think of your game turn orders (GTO) and game turn results (GTR) as ultimate “end-points” destinations within the communications path — your REST or RPC protocols and API specifications — between your subscribing gamers and MMoG App server. This hints at a sequence for writing our MMoG App API source code.

  1. Draft a list of client-side game turn orders (GTO) (examples here) and the expected game turn results (GTR) of the server-side responses. This creates “contracts” between client and server.
  2. Then determine how you will “serialize” that output into a delivery format. In what formatted data structure will that information use? You have several choices. (i.e., Binary, CSV, JSON, TEXT, XML etc.)
  3. Begin encoding the server-side first so that you have something that will respond to the incoming client-side messages. Part II analyzed the various MMoG Engines and architectures.
  4. Finally, encode your “serializers”; these will become your “contracts” between the client and server as to what is expected from each side of the WebSocket conduit. Yeah, that sounds like the most difficult part in this process; but, I have some surprises for you.

8.3 Game Turn Responses

Server to Client Game Turn Results (S2C GTR) are, simply stated, for every command received from a game’s participant, the server will generate a data packet and return it. It is a common “command / response” found in WANs. The server could:

  • keep a virtual data structure of the game status.
  • keep a shadow map of all players’ locations.
  • calculate every combat round narrative details (blow by blow or key-press).
  • OR none of the above! If we chose to use a proxy server, then the gamer’s GTOs are broadcasted from each client as a “peer-to-peer” network. Our server would simple accept and record everyone’s information then broadcast a global GTR as confirmation using “Server-side Event (SSE)”. This should be tailored for each game envisioned. We have several design options at this point. We can have:
  1. a centralized authoritative server that does everything and returns GTRs. OR
  2. a “ghost server” that merely validates the client-side proxy server logic and calculations; then, sends confirmations to all participants about their proxy’s initiatives as “Server-side Events (SSE)”.

Furthermore, how our MMoG App responds is heavily dependent upon the server architecture we’ve chosen. Are we using Remote Procedure Calls (RPC) or Message Oriented Middleware (MOM)? We’ve discussed what those are in Part II; it’s now time to take our thoughts, preferences, and begin encoding them.
