## 服务端 JavaScript

JavaScript 的最初形态存在于浏览器中。但这只是一个上下文（context）。它定义了你可以用这种语言做什么，但并没有对语言本身能做什么做太多说明。JavaScript 是一门“完整”的语言：你可以在许多语境中使用它，并用它实现其他其他“完整”语言可以实现的所有功能。

Node.js 实际上只是另一个上下文：它允许你在后端、浏览器之外运行 JavaScript 代码。

为了执行你打算在后端运行的 JavaScript，需要对其进行解释和执行。这就是 Node.js 所做的，它利用了 Google 的 V8 虚拟机，这是与 Chrome 使用相同的 JavaScript 运行时环境。

此外，Node.js 自带了许多实用的模块，所以你不需要从头开始编写一切，例如在控制台输出字符串之类的代码。

因此，Node.js 实际上是两个东西：运行时环境和一个库。

为了使用这些功能，你需要安装 Node.js。这里不再在这里重复安装过程，请你访问官方安装指南⁴。在你安装好并运行后，请回来。

## 构建应用栈

```javascript
function say(word) {
  console.log(word);
}
```

```
function execute(someFunction, value) {
  someFunction(value);
}
```

execute(say, "Hello");

请仔细阅读这里！我们在这里做的是，将函数 `say` 作为第一个参数传递给 `execute` 函数。不是传递 `say` 的返回值，而是 `say` 本身！

因此，`say` 变成了 `execute` 内部的局部变量 `someFunction`，`execute` 可以通过调用 `someFunction()`（添加括号）来执行该变量中的函数。

当然，因为 `say` 接收一个参数，`execute` 在调用 `someFunction` 时传递这样一个参数。

我们可以像刚才做的那样，通过名称将函数作为参数传递给另一个函数。但我们不必通过这种重定向方式先定义再传递——我们可以直接在原地定义函数并将其作为参数传递给另一个函数：

```javascript
function execute(someFunction, value) {
  someFunction(value);
}
```

```javascript
execute(function(word){ console.log(word) }, "Hello");
```

构建应用栈

我们直接在 `execute` 期望第一个参数的地方，定义了想要传递给 `execute` 的函数。

这样，我们甚至不需要给函数命名，这就是为什么这被称为匿名函数。

这是我所说的“高级”JavaScript 的初次体验，但让我们循序渐进。现在，我们只需接受在 JavaScript 中，我们可以在调用另一个函数时将一个函数作为参数传递。我们可以通过将函数赋值给变量然后传递它，或者通过原地定义要传递的函数来实现。

### 事件驱动异步回调

为了理解为什么 Node.js 必须这样编写，我们需要理解 Node.js 是如何执行我们的代码的。Node 的方法并不是唯一的，但其底层执行模型与 Python、Ruby、PHP 或 Java 等运行时环境不同。

让我们看这段非常简单的代码：

```javascript
var result = database.query("SELECT * FROM hugetable");
console.log("Hello World");
```

请暂时忽略我们之前实际上还没有讨论过连接数据库——这只是一个例子。第一行查询数据库以获取大量行，第二行将“Hello World”打印到控制台。

构建应用栈

假设数据库查询非常慢，它必须读取大量的行，这需要几秒钟。

按照我们编写这段代码的方式，Node.js 的 JavaScript 解释器必须先从数据库读取完整的结果集，然后才能执行 `console.log()` 函数。

如果这段代码实际上是（比如 PHP），它的工作方式是一样的：一次性读取所有结果，然后执行下一行代码。如果这段代码是网页脚本的一部分，用户必须等待几秒钟页面才会加载。

然而，在 PHP 的执行模型中，这不会变成一个“全局”问题：Web 服务器为它收到的每一个 HTTP 请求启动自己的 PHP 进程。如果这些请求中的一个导致了慢速代码的执行，会导致该特定用户的页面加载缓慢，但请求其他页面的其他用户不受影响。

Node.js 的执行模型是不同的——它只有一个进程。如果该进程中某处有一个缓慢的数据库查询，它将影响整个进程——在慢查询完成之前，一切都会停滞。

为了避免这种情况，JavaScript（以及因此 Node.js）通过利用事件循环引入了**事件驱动异步回调**的概念。

我们可以通过分析我们问题代码的重写版本来理解这个概念：

构建应用栈

```javascript
database.query("SELECT * FROM hugetable", function(rows) {
  var result = rows;
});
console.log("Hello World");
```

在这里，我们不再期望 `database.query()` 直接返回结果，而是向它传递了第二个参数，一个匿名函数。

在之前的形式中，我们的代码是同步的：先执行数据库查询，只有当执行完成后，才向控制台写入内容。

现在，Node.js 可以异步处理数据库请求。只要 `database.query()` 是异步库的一部分，Node.js 就会这样做：像以前一样，它获取查询并将其发送到数据库。

它并不等待完成，而是在记下：“在未来的某一点，当数据库完成并发送结果时，我需要执行传递的匿名函数。”

然后，它立即执行 `console.log()`，之后进入循环。当没有其他事情可做时，Node.js 会不断循环这个循环，等待事件。例如数据库查询交付结果。

这也解释了为什么我们的 HTTP 服务器需要一个可以在接收请求时调用的函数——如果 Node.js 启动服务器后就暂停，只有当请求到达时才继续，将是非常低效的。如果在处理第一个请求时第二个用户请求了服务器，第二个请求只能在第一个请求完成后才能得到回答——一旦你每秒超过几个 HTTP 请求，这种方法就完全无法工作。

构建应用栈

需要注意的是，这种异步、单线程、事件驱动的执行模型并不是无限扩展的性能独角兽。它只是几种模型之一，并且有其局限性，其中一个是截至目前 Node.js 只有一个进程，并且只能运行在单个 CPU 核心上。对我个人而言，我觉得这种模型非常容易上手，因为它允许以高效且相对简单的方式编写处理并发的应用。

### 我们的服务器如何处理请求

好的，让我们快速分析服务器的剩余部分，即回调函数 `onRequest()`。

当回调函数触发且 `onRequest()` 函数被触发时，传入了两个参数：`request` 和 `response`。

这些都是对象，你可以使用它们的方法来处理发生的 HTTP 请求，并向请求的浏览器返回一些内容。

代码恰好这样做：每当接收到请求时，它使用 `response.writeHead()` 函数发送 HTTP 200 状态码和 content-type 头部，并使用 `response.write()` 函数在 HTTP 响应中发送“Hello World”。

最后，我们调用 `response.end()` 来完成我们的响应。

在这一点上，我们并不关心请求的细节，因为我们没有使用 `request` 对象。

# 阻塞与非阻塞

如所述，当我们在处理器中包含非阻塞操作时，问题就会出现。但让我们先谈谈阻塞操作，然后再谈非阻塞操作。

与其试图解释“阻塞”和“非阻塞”的含义，让我们亲自演示一下如果我们在请求处理器中添加一个阻塞操作会发生什么。

> ¹⁰http://localhost:8888/start
> ¹¹http://localhost:8888/upload
> ¹²http://localhost:8888/foo

## 构建应用堆栈

为了做到这一点，我们将修改 `start` 处理器，让它在返回 "Hello Start" 字符串之前等待 10 秒。因为 JavaScript 中没有 `sleep()` 函数，我们将使用一个巧妙的黑科技来实现。

请如下修改 `requestHandlers.js`：

```
function start() {
    console.log("Request handler 'start' was called.");

    function sleep(milliseconds) {
        var startTime = new Date();
        while (new Date().getTime() < startTime + milliseconds) {
            // 忙等
        }
    }

    sleep(10000);
    return "Hello Start";
}

function upload() {
    console.log("Request handler 'upload' was called.");
    return "Hello Upload";
}

exports.start = start;
exports.upload = upload;
```

只是为了弄清楚它的作用：当函数 `start()` 被调用时，Node.js 会等待 10 秒，然后才返回“Hello Start”。调用 `upload()` 时，它会立即返回，就像以前一样。

## 构建应用堆栈

（当然，你应该想象成不是睡眠 10 秒，而是在 *start() 中存在一个真实的阻塞操作，比如某种长时间的计算。）

## 构建应用堆栈

`exec()` 执行的是在 Node.js 内部执行 shell 命令。在这个示例中，我们将使用它来获取当前目录下所有文件的列表（"ls -lah"），允许我们在请求 start URL 的用户浏览器中显示此列表。

代码的作用非常直观：创建一个新变量 `content`（初始值为 "empty"），执行 "ls -lah"，用结果填充该变量，并返回它。

同样，我们将启动应用程序并访问 http://localhost:8888/start¹⁵。它加载了一个显示字符串 "empty" 的精美网页。这里出了什么问题呢？

嗯，正如你可能已经猜到的那样，`exec()` 以非阻塞的方式执行它的魔法。这是一好事，因为通过这种方式，我们可以执行非常昂贵的 shell 操作（例如，复制大文件或类似操作），而不会强迫我们的应用程序完全停止，就像阻塞的 `sleep` 操作那样。

（如果你想证明这一点，将 "ls -lah" 替换为更昂贵的操作，如 "find /"）。

但当我们的浏览器没有显示结果时，我们对这种优雅的非阻塞操作并不完全满意，对吧？

那么，让我们修复它。顺便说一下，让我们尝试理解为什么当前的架构行不通。

问题在于 `exec()` 为了实现非阻塞工作，使用了回调函数。

在我们的示例中，它是作为第二个参数传递给 `exec()` 函数调用的匿名函数：

> ¹⁵http://localhost:8888/start



```javascript
function (error, stdout, stderr) {
  content = stdout;
}
```

这就是我们问题的根源：我们自己的代码是同步执行的，这意味着在调用 `exec()` 之后，Node.js 会立即执行 `return content;`；此时，`content` 仍然是“空”，因为传递给 `exec` 的回调函数尚未被调用——因为 `exec()` 是异步操作的。

现在，`ls -lah` 是一个非常廉价且快速的操作（除非目录中有数百万个文件）。这就是为什么回调函数执行得相对迅速——但它仍然是以异步方式发生的。

考虑一个更耗资源的命令会让这一点变得更加明显：在我的机器上运行 `find /` 大约需要1 分钟，但如果我在请求处理器中将 `ls -lah` 替换为 `find /`，在打开 `/start` URL 时，我仍然会立即收到 HTTP 响应——显而易见 `exec()` 在后台执行某些操作，而 Node.js 本身继续运行应用程序，我们可以假设传递给 `exec()` 的回调函数只有在 `find /` 命令运行完成后才会被调用。

但我们如何才能实现我们的目标，即向用户显示当前目录下的文件列表呢？

好了，在学习了不怎么做之后，让我们讨论一下如何让我们的请求处理器以正确的方式响应浏览器请求。

## 使用非阻塞操作响应请求处理器

我刚刚使用了“正确的方式”这个词。这很危险。通常情况下，并没有单一的“正确方式”。

但此的一种可能的解决方案是，像 Node.js 中常见的做法，将函数向下传递。让我们检查一下。

现在，我们的应用程序能够将内容（请求处理器想要向用户显示的内容）通过应用层级（请求处理器 -> 路由器 -> 服务器）返回，从请求处理器传输到 HTTP 服务器。

我们的新方法如下：我们不再将内容带到服务器，而是将服务器带到内容处。具体地说，我们将响应对象（来自服务器的回调函数 `onRequest()`）通过路由器注入到请求处理器中。这样处理器就可以使用该对象的函数来自己响应请求了。

解释得足够了，这里是更改我们应用程序的逐步操作配方。

让我们从 `server.js` 开始：

## 构建应用程序栈

现在我们正成为“专家级新手”，对于“处理 POST 数据是通过使用异步回调以非阻塞方式完成的”这一事实不再感到惊讶了。

这是很有道理，因为 POST 请求可能非常大——没有什么能阻止用户输入几兆字节的文本。一次性处理整块数据会导致阻塞操作。

为了使整个过程变为非阻塞，Node.js 以小块（chunks）的形式为我们的代码提供 POST 数据，并在特定事件时调用回调。这些事件有 `data`（到达了新的 POST 数据块）和 `end`（所有数据块都已接收）。

我们需要告诉 Node.js 在这些事件发生时回调哪些函数。这是通过向每次接收到 HTTP 请求时传递给我们的 `onRequest` 回调请求对象添加监听器来实现的。

这基本上如下：

```javascript
request.addEventListener("data", function(chunk) {
  // 当收到新的数据块时调用
});
```

```javascript
request.addEventListener("end", function() {
  // 当接收到所有数据块时调用
});
```

问题出现了，应该在哪里实现这些逻辑。目前我们只能在服务器中访问请求对象——我们并没有像处理响应对象那样将其传递给路由器或请求处理器。

在我看来，HTTP 服务器应该为应用程序提供执行任务所需的所有请求数据。因此，我建议我们直接在服务器中处理 POST 数据处理，并将最终数据传递给路由器和请求处理器，然后由它们决定如何处理。

## 构建应用程序堆栈

因此，这个思路是将 `data` 和 `end` 事件回调放在服务器中，在 `data` 回调中收集所有的 POST 数据块，并在接收到 `end` 事件时调用路由器，同时将收集的数据块传递给路由器，由路由器再将其传递给请求处理器。

我们开始吧，从 `server.js` 开始：

```javascript
var http = require("http");
var url = require("url");

function start(route, handle) {
  function onRequest(request, response) {
    var postData = "";
    var pathname = url.parse(request.url).pathname;
    console.log("Request for " + pathname + " received.");

    request.setEncoding("utf8");

    request.addEventListener("data", function(postDataChunk) {
      postData += postDataChunk;
      console.log("Received POST data chunk " + 
      postDataChunk + ".");
    });

    request.addEventListener("end", function() {
      route(handle, pathname, response, postData);
    });
  }
}
```

```javascript
http.createServer(onRequest).listen(8888);
console.log("Server has started.");
}

exports.start = start;
```

我们在这里基本上做了三件事：首先，我们定义了接收的数据编码为 UTF-8；我们为“data”事件添加了事件监听器，每当有新的 POST 数据块到达时，它就会逐步填充我们的新变量 `postData`；最后我们将对路由器的调用移动到 `end` 事件回调中，以确保它只在所有 POST 数据收集完毕后才被调用。我们还将 POST 数据传递给路由器，因为我们在请求处理器中会需要它。

在每个收到的数据块上都添加控制台日志对于生产代码来说可能是个坏主意（记住有几兆字节的 POST 数据！），但看看发生了什么是有意义的。
